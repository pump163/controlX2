## §2 Tandem 7.1–7.5 事实表（逐章）

### 2.1 §7.1 Bolus Helpers（p.80–81）

| 事实 | 内容 |
|---|---|
| 最小/最大大剂量 | 最小 **0.05 U**（p.80）；**Max Bolus 默认 10 U，可设 1–25 U**（§7.7 p.88） |
| 步进 | **0.05 U**（与用户核实的 X2 精度一致；Mobi 待核实） |
| 碳水开关 | `Carbs` 开 → 按克数输入；关 → 只能按单位输入（没有「按克数」入口） |
| 向导前置条件 | 必须已设置 Basal、Correction Factor、Carb Ratio、Target BG；**没有基础率时段时泵不计算校正大剂量**（§5.2 p.62） |
| 手动大剂量对 CIQ | CIQ 开启时，手动大剂量后 **60 分钟内暂停自动校正**（p.80） |

### 2.2 §7.2 Correction Bolus（p.81–83）——本章即「向导核心」

| 项 | 事实 |
|---|---|
| 输入项 | 当前 BG（可手输，或 CIQ 开启时用 CGM 当前值自动带出）、碳水（克数或单位，取决于入口） |
| 血糖来源 | **只有当前 CGM 值**；**不使用趋势箭头**做外推；CGM 自动带出要求：CIQ 开、CGM 会话活跃、有当前读数、有趋势箭头 |
| 可覆盖 | 用户可手动改 BG 值（覆盖自动带出的 CGM 值） |
| BG 高于目标 | 校正 = 高于目标的部分；**IOB 只从「校正」里扣，不扣食物部分** |
| BG 在 70 与目标之间 | 校正为 0；提示用户**可自行减少食物大剂量**；**IOB 也会用于减少总量** |
| BG 低于 70 | **自动减少食物大剂量**（按低血糖校正）；**IOB 也参与减少**；提示先补快速碳水 |
| BG 恰好等于目标 | 不弹 Above/Below 确认页 |
| 未输入 BG | 不做校正（等价于只算食物）——Tandem 未明写，按 Medtronic 公式 4 与操作流推断 |
| 计算后 | 显示总剂量并回到 Bolus 界面；可接受或修改 |

### 2.3 §7.3 Bolus Override（p.85）

| 项 | 事实 |
|---|---|
| 覆盖入口 | 始终可用（正常大剂量、扩展大剂量、向导算完后都可进入） |
| 覆盖方式 | 按单位或按克数直接改总量 |
| 覆盖后 | 回到主 Bolus 界面继续输注；**IOB 仍生效**（下一次计算照常扣） |

### 2.4 §7.4 By Units（p.86）

- 只输入单位数，不经过向导；适合已知剂量。
- 与「直接输入」同义。

### 2.5 §7.5 By Grams（p.86–87）

- 输入碳水克数 → 走向导计算（需要 BG / ICR / ISF / 目标 / IOB）。
- 支持多次加碳水（逐个累加）；每次都可查看计算明细。

### 2.6 泵上操作顺序（Tandem，p.81–87）

1. 主界面 → Bolus → 选「Correction Bolus / 校正大剂量」。
2. 输入或确认 BG（CGM 可自动带出；可改）。
3. 输入碳水（克数）或直接进入下一步（仅校正）。
4. 泵计算 → 显示总剂量（可 View Calculation 查看计算过程；手册未说明分项字段，也无公式）。
5. 若 BG 高于 / 低于目标，出现 Above/Below 确认页（说明为何被调整）。
6. 可 Override（按单位或克数）改总量。
7. 设定扩展比例 / 时长（可选）→ 输注。

### 2.7 参数与范围（Tandem §5.2–5.3，p.54–57）

| 参数 | 范围 | 增量 | 备注 |
|---|---|---|---|
| Correction Factor（ISF） | 1:1 – 1:600 mg/dL/U | 1 | 1 U 降低的 mg/dL |
| Carb Ratio（ICR） | 1:1 – 1:300 g/U | <1:10 时 0.1 g；≥1:10 时 1 g | 1 U 覆盖的碳水克数 |
| Target BG | 70 – 250 mg/dL | 1 | **单值**（不是高低双目标） |
| Insulin Duration | 2 – 8 h，默认 5 h | — | CIQ 开启时**固定 5 h，不可改**（p.54–55） |
| Carbs | 开 / 关 | — | 关时无「按克数」 |

### 2.8 CIQ 开启时的差异（Tandem p.55、57、80）

- Insulin Duration **固定 5 h**；主界面不显示作用时间。
- Target BG **默认 110 mg/dL**（CIQ 打开后默认值）。
- IOB **包含所有高于/低于基础率的基础胰岛素**（不只是大剂量）。
- 手动大剂量后 **60 分钟暂停自动校正**。
- CGM 当前值可自动带出到向导 BG 框；**只看当前值，不看趋势**。
- 扩展大剂量时长 **最长 2 小时**（§7.6 p.87）；**校正部分永远计入 NOW（立即）段**（§7.6 p.88）。

## §3 公式来源与差异

### 3.1 美敦力 670G 附录公式（PDF p.381–384，逐条）

> 原文标题：`Bolus Wizard feature specifications / 大剂量向导功能规格`。原文明确：**以下公式仅在碳水单位为「克」时适用**。

**参数定义（p.381）**

| 参数 | 范围 | 增量 |
|---|---|---|
| Carb units | 克（仅克） | — |
| Insulin to carb ratio（ICR） | 1–200 g/U | 1–9.9 为 0.1 g/U；10–200 为 1 g/U |
| Insulin Sensitivity Factor（ISF） | 5–400 mg/dL | 1 mg/dL |
| BG Target | 60–250 mg/dL | 1 mg/dL |
| Active Insulin Time | 默认 4 h，范围 2–8 h | 15 min |

**公式 1：当前 BG > 高 BG 目标（p.382）**

```text
食物估计 = 碳水克数 ÷ 碳水系数（ICR）
校正估计 = (当前 BG − 高 BG 目标) ÷ 胰岛素敏感系数（ISF） − 活性胰岛素
总大剂量 = 食物估计 + 校正估计
```

补充（p.382 原文）：**若「校正估计 − 活性胰岛素」为负（<0），总量只按食物估计**。

**公式 2：当前 BG < 低 BG 目标（p.382–383）**

```text
总大剂量 = 碳水克数 ÷ 碳水系数
         + (当前 BG − 低 BG 目标) ÷ 胰岛素敏感系数
         − 活性胰岛素
```

> **原文自相矛盾**：p.382 的公式含 `− 活性胰岛素`，但 p.383 的脚注写「当前 BG 低于低 BG 目标时，大剂量向导计算中**不考虑活性胰岛素**」。实现时需选定一种并实测。

**公式 3：当前 BG 在目标范围内（p.383）**

```text
总大剂量 = 碳水克数 ÷ 碳水系数
```

**公式 4：未输入 BG（p.383）**

```text
总大剂量 = 碳水克数 ÷ 碳水系数
```

**其它规则（p.384）**

- 双波大剂量若因 Max Bolus 或用户修改而小于估计值：**先减方波（Square）部分**。
- 活性胰岛素按 Active Insulin Time 记录；曲线改编自 Mudaliar 等（Diabetes Care, 1999, 22(9):1501），**只有曲线图，没有逐点公式**。

## §4 不可直接照搬的美敦力专有部分

1. **高低双目标**：Medtronic 用 Low/High BG Target 两个值决定正/负校正；Tandem 只有一个 Target BG。照搬会多出一个我们泵上不存在、也无法下发的参数。
2. **活性胰岛素时间曲线**：Mudaliar 曲线是美敦力的 IOB 模型；Tandem 用自己的 IOB 计算（CIQ 下还包含基础胰岛素）。**不能**用美敦力曲线在本地算 IOB 再与泵的 IOB 混用。
3. **0.025 U 网格与 Max Bolus 语义**：670G 的步进可配 0.025/0.05/0.1；Tandem X2/Mobi 是 0.05（Mobi 待核实）。取整必须按**当前型号步进**，不能照抄 0.025。
4. **参数范围**：Medtronic 的 ISF 5–400、ICR 1–200、BG 60–250 与 Tandem 的 1:600 / 1:300 / 70–250 不同；校验按 Tandem（或直接以泵下发值为准，不二次校验）。
5. **「低于低目标不考虑 IOB」**：与 Tandem §7.2 相反；按 Tandem。
6. **碳水单位**：Medtronic 公式只适用「克」；Tandem 允许「单位」。v2 向导只做克，单位输入继续走直接输入。

**建议**：只借「四情形分支 + 食物/校正/IOB 三段式」的结构，所有参数、阈值、取整、IOB 来源都以 Tandem 与我们现有实现为准。

## §5 与本项目现状对照

### 5.1 上游 `BolusWindow` 的血糖框与 `BolusParameters.glucoseMgdl`

事实（代码）：

- `BolusWindow` 的血糖框是**向导的 BG 输入**，不是校准：
  - 手输 → `glucoseMgdl`；
  - 自动带出 → 取自 `bolusCalculatorBuilder.value?.glucoseMgdl`（其来源是 `BolusCalcLastBG`：用户刚输入的 BG，或泵里最近的 BG 值）。
  - 提交时走 `RemoteBgEntryRequest(bgValue, useForCgmCalibration = false, autopopBg, ...)`——**明确不是 CGM 校准**。
- 上游用 `BolusParameters(units, carbsGrams, glucoseMgdl)` 把三项一起交给 `InitiateBolusRequest`，泵端据此记录食物/校正/IOB 拆分。
- **可复用性**：语义正确（向导 BG），可继续作为「BG 输入」使用；但它绑定旧 UI 与旧计算链，v2 建议**只复用字段语义与 `BolusCalcLastBG` 的取数思路**，不直接复用整个 `BolusWindow`。
- **已知疑似 bug，不要照抄**：上游计算 `autopopBg` 时用了 `bgValue != dataSnapshot.correctionFactor → false`（拿血糖值和校正系数比较）。这几乎恒为 false，疑似字段误用。v2 不复刻该判定。

### 5.2 泵到底能给什么（pumpx2 1.9.0 已核实）

> `BolusCalcDataSnapshot` 的请求 opcode 是 **114**、响应是 **115**；**48 是 `LastBolusStatus` 的请求 opcode（响应 49）**，与向导快照无关。此前文档把 48 写成快照，是错的，本版已改正（完整对应表见 §5.4）。

| 参数 | 报文 / 字段 | 结论 |
|---|---|---|
| ICR（碳水比） | `BolusCalcDataSnapshotResponse.carbRatio`（115） | **能给**；单位是「1 U : N g」的**千分之一**（1U:6g → 6000），`/1000` 得到 g/U |
| ISF（敏感系数） | `BolusCalcDataSnapshotResponse.isf`（115） | **能给**；`int`，mg/dL per U，无缩放 |
| 目标血糖 | `BolusCalcDataSnapshotResponse.targetBg`（115） | **能给**；`int` mg/dL，当前生效值 |
| IOB | `BolusCalcDataSnapshotResponse.iob`（115） | **能给**；**毫单位**（1000 = 1 U），见 §7 |
| 当前 BG（CGM） | `BolusCalcDataSnapshotResponse.correctionFactor`（115） | **是当前 CGM 血糖**（pumpx2 源码注释明确），**不是 ISF**；此前的疑点已澄清 |
| 最大大剂量 / 每小时上限 | `maxBolusAmount`（毫单位）/ `maxBolusHourlyTotal`（115） | **能给** |
| 碳水开关 | `carbEntryEnabled`（115） | **能给** |
| 快照是否有效 | `isUnacked`（115） | **能给**；`true` = 数据没取到或为空，可直接作为「不可用」判定 |
| 胰岛素作用时间 | **115 里没有**；`IDPSettingsResponse.insulinDuration` 有 | **需额外请求**；但按 §7 的结论，向导**不需要**它 |
| 分段 ICR / ISF / 目标 | `IDPSegmentResponse` 有 | 可选；若用 115 的「当前生效值」就不需要自己算时段 |
| 当前 CGM 血糖 | `BolusCalcDataSnapshotResponse.correctionFactor`（115） | **能给**（用于 BG 框自动带出） |
| 当前 BG（指尖） | `BolusCalcLastBG` / `LastBGRequest` | 可读，需走历史或 `LastBG` |

**结论：向导需要的参数（ICR / ISF / 目标 / IOB）都能从 115 快照拿到；唯一曾以为缺的「作用时间」，在本轮结论下向导根本不需要。**


### 5.3 现有代码里已有的东西

- `DataStore` 已缓存：`bolusCalcDataSnapshot`（115）、`bolusCalculatorBuilder`、`bolusFinalCalcUnits`。
- 上游已向泵发 `BolusCalcDataSnapshotRequest()`（114），并用 `pumpx2` 的 `BolusCalculatorBuilder` 本地算过。
- **pumpx2 自带 `BolusCalculator`**（本地纯计算，不依赖泵）：
  - 食物 = 碳水 ÷ ICR（g/U）
  - 校正 = (BG − targetBg) ÷ ISF
  - IOB = −iob（作为负项）
  - 中间 `double` 结果统一 **HALF_UP 保留 2 位小数**
  - 条件分支与 Medtronic 四情形高度一致（正/负校正、IOB 超校正、无 BG 等）
- **可直接复用**：参数来源（115）+ 计算器（`BolusCalculatorBuilder`）。v2 不必从零写公式。
- **注意**：pumpx2 的 `BolusCalculator` 没有做「0.05/0.025 网格量化」，也没有 Tandem 的「70 以下 IOB 参与」细分；v2 需要在其外层包一层「Tandem 口径 + 步进量化」。

## §6 初步设计

### 6.1 与「直接输入」的关系

- **同一个出口**：向导最终只产出 `BolusDraft`（`nowMilliunits` / `laterMilliunits` / `extendedSeconds` / `BolusShape` / `BolusSource.CALC`），后续形状页、确认页、发送链路**完全复用**。
- 入口：第 1 步的「碳水计算」从只读预留改为可用；进入后是一个**计算输入页**（碳水克数、BG、来源标注、计算明细），算出总量后进入第 2 步（形状/时长），用户仍可改。
- **向导不做发送、不做上限拦截**；所有上限仍在确认页统一判断（与预设、直接输入一致）。

### 6.2 输入项、来源与默认值

| 输入/参数 | 来源优先级 | 默认值 | 用户可否改 | 备注 |
|---|---|---|---|---|
| 碳水克数 | 用户每次输入 | 空 | 是 | 0–300 g；空 = 无碳水 |
| BG（mg/dL） | ① 用户手输 ② CIQ 开启且 CGM 新鲜时自动带出 | 空 | 是 | 显示来源「手动 / CGM」；**不用趋势** |
| ICR（g/U） | ① 泵 115 `carbRatio`（÷1000）② 本地配置 | 无 → 阻止向导 | 否（只读展示） | 泵值优先 |
| ISF（mg/dL/U） | ① 泵 115 `isf` ② 本地配置 | 无 → 阻止向导 | 否 | **`isf` 就是 ISF**；`correctionFactor` 是当前 CGM 血糖，别混用 |
| Target BG | ① 泵 115 `targetBg` ② 本地配置 | 无 → 阻止向导 | 否 | 单值；CIQ 默认 110 由泵给 |
| IOB | ① 泵 115 `iob`（毫单位）② 泵 109/39 | **不可用**（不是 0） | 否 | 过期/无效 → 禁用向导；不本地估算（§7） |
| Insulin Duration | 不需要 | — | 否 | 只在展示「IOB 模型」时作为说明文字，**不参与计算** |
| 最大大剂量 | 泵 115 `maxBolusAmount`（毫单位） | 25 U | 否 | 仅确认页使用 |
| 碳水开关 | 泵 115 `carbEntryEnabled` | 开 | 否 | 关时向导入口置灰并说明 |

**必须本地配置的只有**：ICR / ISF / 目标值的离线兜底、低血糖阈值（70）、CGM 新鲜度（20 min）、量化规则、向导总开关。**不需要作用时间。**

### 6.3 计算链（按 Tandem 语义，参考 Medtronic 公式结构）

> **精度原则**：全程用高精度（Double / 毫单位），**只在最终总量落到步进网格时量化一次**；中间不做四舍五入。这与现有 `BolusForm` / `splitByPercent` 的量化口径一致。

1. 校验：ICR > 0、ISF > 0、Target 在 70–250；否则向导不可用。
2. 食物估计（U）= carbsGrams ÷ ICR。无碳水 → 0。
3. 校正估计（U）= (BG − Target) ÷ ISF。无 BG → 0。
4. IOB（U，正数）= 泵给的值 ÷ 1000；**取不到则判定不可用、不给结果**（不要拿 0 冒充）。
5. 分支：
   - **BG > Target**：`校正部分 = max(0, 校正估计 − IOB)`；`总量 = 食物 + 校正部分`。
   - **70 ≤ BG ≤ Target**：`校正部分 = 0`；`总量 = 食物`（可选项：给用户一个「按差额减少食物」开关，见 6.5）。
   - **BG < 70**：`校正部分 = 校正估计（负）`；`总量 = 食物 + 校正估计 − IOB`；若结果 < 0 → 0。（Tandem：IOB 参与；Medtronic：不参与 → 以 Tandem 为准）
   - **无 BG**：`总量 = 食物`。
6. 量化：`totalMilliunits = roundToStep(totalU * 1000, limits.bolusIncrementMilliunits)`，HALF_UP。
7. 输出 `BolusCalcOutcome(totalMilliunits, foodMilliunits, correctionMilliunits, iobMilliunits, flags)`，供「计算明细」展示。
8. 总量为 0 或低于最小步进 → 不允许进入下一步，提示「计算为 0，请检查输入」。

### 6.4 参数配置存哪（沿用阈值配置外置体系）

在现有外置 JSON（`pump_limits.json` 体系）新增 `bolusCalculator` 段，**一条一条列**：

```json
"bolusCalculator": {
  "enabled": true,
  "carbRatioGramsPerUnit": null,      // null = 只读泵 115；数值 = 离线兜底
  "isfMgdlPerUnit": null,
  "targetBgMgdl": null,
  "insulinDurationMinutes": null,     // 默认不使用；仅「自算 IOB 备选」启用时才读
  "iobMaxAgeSeconds": 120,            // IOB 快照最大可用时长；超时即禁用向导
  "lowBgThresholdMgdl": 70,
  "cgmFreshnessMinutes": 20,
  "maxCarbsGrams": 300,
  "rounding": "half_up",
  "showBreakdown": true
}
```

- **优先级**：泵 115 有值 → 用泵值；泵值缺失且配置有值 → 用配置；都无 → 向导置灰并写明缺哪一项。
- **IOB 例外**：IOB **没有本地兜底值**，只有「读泵」或「不可用」两种状态；配置里只配「最大可用时长」。
- 不把 ICR/ISF/目标写死进代码；配置只作兜底与调试覆盖。
- 配置加载沿用现有 `PumpLimits` 读取路径（`assets/pump_limits.json` → 类型化对象），不新造读取机制。

### 6.5 与扩展大剂量、预设、CIQ 的交互

## §7 活性胰岛素来源：读泵 vs 自算

> 本节回答用户的问题：**「直接读泵上报的 IOB，不自己实现衰减曲线，可行吗？」**
> 一句话：**代码层可行**——泵确实直接上报 IOB（毫单位），两种模型并存，且有专门的 IOB 报文；**但真机尚未验证**，下文凡属推断的地方都单独标了「待实测」。

**设计理由（用户判断）：两类 IOB 模型都是理想化近似。**

- 美敦力那条吸收曲线是**用函数画出来的理想图**，不是真实胰岛素吸收；真实吸收曲线与它明显不一致（670G 手册 p.384 也只给曲线图，没有逐点公式）。
- IOB 算法大致两类：**线性斜线**（匀速衰减）与**美敦力那类函数曲线**。用户判断：**两类都不对**，都只是近似。
- 因此自算 IOB 再「精确」也只是换了一种理想化；而泵上报的 IOB 至少与**它自己的输注节奏、CIQ 行为**一致，不会出现「App 算的和泵屏幕不一致」。
- **结论**：若泵能可靠给 IOB，本方案**不实现任何 IOB 曲线**；自算只作为泵取不到时的**备选**，且必须标注「属于近似，计算结果不能声称比泵更准」。

### 7.1 结论

- **可行，且优于自算。** 泵给的是「泵自己向导也会用的那个数」，我们只做 `食物 + 校正 − IOB` 和最终量化即可。
- **不需要**在 App 里实现衰减曲线，**也不需要**作用时间（Insulin Duration）参与计算——作用时间只是泵内部 Mudaliar 模型的参数。
- 推荐的读取优先级：**115 快照的 `iob`（主）→ 109/39 专用 IOB 报文（备）→ 不可用则禁用向导**。
- 这样做之后，必须本地配置的只剩 **ICR、ISF、目标血糖**（离线兜底）以及低血糖阈值、CGM 新鲜度、量化规则、向导总开关。

### 7.3 两种模型意味着什么

- **Mudaliar**：衰减曲线跟随 profile 的 Insulin Duration（Tandem 2–8 h；CIQ 下固定 5 h）。
- **Swan 6h**：固定 6 小时模型，与 Mudaliar 数值不同。
- `iobType` 决定泵屏幕显示哪一个；`getPumpDisplayedIOB()` 已封装该选择逻辑。
- **对我们的意义**：用户说的「Tandem 抄 AAPS、锁定 ≥5h、不同闭环初始值不同」这些争议，**全部留在泵内部**。我们只取「泵此刻认为的 IOB」，不参与模型选择、不重算曲线，因此不会与泵屏幕对不上。

### 7.4 触发方式与新鲜度

| 项 | 现状（已核实） | 对向导的要求 |
|---|---|---|
| 是否推送 | **不是推送**。只有两类触发：① 首页刷新按钮 `BUST_CACHE` 发 `dashboardCommands`；② `CommService` 周期任务每 **5 分钟**发一次 `ControlIQIOBRequest` | 向导进入时必须**主动请求一次**，不能只依赖缓存 |
| 断连后保留多久 | `DataStore.iobUnits` **没有任何清空路径**（仅预览代码置 `null`），理论上可无限期保留旧值 | 必须本地记录 `receivedAt`，断连即视为不可用 |
| 有无自带时间戳 | **没有**。109/115 都不带采集时间 | 只能在收到时本地打时间戳 |
| 泵复位 | `DataStore.timeSinceResetResponse` 有 `pumpTimeSecondsSinceReset` | 该值变化即清空 IOB 缓存 |
| 快照有效性标志 | 115 有 `isUnacked`（`true` = 未取到/为空） | 直接用；109/39 **没有**等价字段，只能靠「本次请求是否在超时内收到响应」 |
| 建议过期阈值 | — | 连接中 > 2 分钟视为过期；断连/复位/`isUnacked` 直接不可用。**阈值为设计建议，需真机调** |

### 7.5 可行性与替代方案对比

| 方案 | 做法 | 风险 | 结论 |
|---|---|---|---|
| **A. 读泵（推荐）** | 115 `iob` 为主，109/39 为备；只做减法 | 与泵口径完全一致；风险是「拿旧值算」——用时间戳 + `isUnacked` + `timeSinceReset` 三重守卫 | **采用** |
| B. 本地实现衰减曲线 | 用作用时间 + Mudaliar / Swan 公式自算 | **属于近似，不能声称比泵更准**（用户判断：函数曲线与线性斜线两类模型都是理想化）；还必须精确复刻模型选择、扩展大剂量摊销、CIQ 基础胰岛素，稍有偏差就与泵屏幕不一致 | 仅作泵取不到时的备选，且必须标注「近似」 |
| C. 线性扣减 | 按剩余时间线性递减 | 与泵数值必然不一致；误差随剂量放大 | 不采用 |
| D. 先不做向导 | 维持直接输入 | 无风险，但缺功能 | 备选（若真机证明 IOB 不可靠） |

**关键取舍**：读泵方案里，「IOB 含不含扩展大剂量未输完部分」「含不含 CIQ 自动基础量」这些问题**不需要我们回答**——因为泵的向导用的是同一个数。我们只需保证「不拿过期/无效的值算」。

### 7.6 边界情形与「不可用」判定

| 情形 | 现状能拿到什么 | 能否明确判定「不可用」 | 建议 |
|---|---|---|---|
| **扩展大剂量正在输注** | `ExtendedBolusStatusRequest`(46) 能告诉有没有扩展在跑；但**没有任何字段说明 IOB 是否含未输完方波** | 不能从 IOB 报文本身判定 | 不禁止向导；在明细里标注「IOB 来自泵，含/不含扩展未输完部分**待实测**」；若实测泵的 IOB 不含未输完部分，再决定是否提示 |
| **CIQ 刚自动校正过** | 没有「刚才发生过自动校正」的显式标志；`HomeScreenMirrorResponse` 的基础率图标只能说明升/降/暂停，不能说明 bolus | 不能实时判定 | 以泵 IOB 为准；`IobSnapshotPreBolus/PostBolus` 历史日志可事后对账，但**1.9.0 没有这两个类**，需升级 pumpx2 才可用 |
| **泵复位 / 重新连接** | `TimeSinceResetResponse` 变化；连接断开可由 CommService 状态得知 | **能**（复位值变化 / 断连） | 清空缓存并禁用向导，重新请求成功后再启用 |
| **快照取不到** | 115 `isUnacked == true` | **能** | 禁用向导并提示「未获取到泵参数」 |
| **IOB 恰为 0** | 合法值（刚输完或长时间未输注） | 不能当缺失 | 按 0 参与计算，**不要**显示为「不可用」 |
| **泵不支持 115（老 API）** | 115 的 `minApi = API_V2_5` | **能**（按 API 版本判断） | 退到 109/39；两者都不可用则禁用向导 |

> **重要限定**：以上「能给 / 能判定」均来自 **pumpx2 1.9.0 的类定义与源码注释**（jar 反编译 + 本地源码核对），**没有在真机上跑过**。特别是「109 的 17 字节快照在 X2 / Mobi 上都可稳定获取」「`iob` 是否含扩展未输完部分」「非 CIQ 泵 39 的单位」三项，必须实测后才能写成「已确认可行」。
