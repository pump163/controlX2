## 2. 事实清单

### 2.1 断连的形态分布

[已证实] 24h 去重口径 172 次，`live.jsonl` 19h 口径 133 次，两者形态一致：

| 对端/本方终止 | 19（11%） | 22（16.5%） | `statusCode=null`，库侧记为 `REMOTE_USER_TERMINATED_CONNECTION`；其中 **5 次是本方主动剪线**（`WRITE_CUT` 紧邻） |

连接存活时长：24h 去重口径中位 **33.7s**、**33.1% ≤20s**；live 口径中位 47.7s、30.8% ≤20s（差别来自 1MB 环形覆写丢掉了较早的长连接）。最长一次 20,521,872ms（约 5.7 小时）。

### 2.2 第一条：连接后 15–17 秒的窄窗口（28 次）

[已证实] 24h 去重后，**28 次**的 `connectedForMs` 落在 15,000–17,500ms（占 16.3%），**全部是 `code 8`**。

- 该窗口内 **10 次 `rxLastMinute=0`**（连上后一条数据都没读到就掉），其余为个位数到几十条。
- 时序上紧挨着的例子（09:57–09:59）：09:58:58.6 连上 → 09:59:14.3 断（15.7s）；09:57:01.8 连上 → 09:57:17.9 断（16.2s），重连后到 09:57:27.9 又断。

[已证实-源码] pumpx2 1.9.3 在 `TandemBluetoothHandler.onConnectionUpdated` 的注释里写明：**对端会在连接后约 15 秒把连接参数降到低功耗档（interval=30ms, latency=29, timeout=2s），这个 2 秒监督超时会造成频繁 `CONNECTION_TIMEOUT`**；因此库提供了 `TandemPump.enablePeriodicConnectionPriorityReassert()`（每 10s 重新请求 HIGH，泵忙时跳过）。

[已证实-本仓] 全仓检索 `enablePeriodicConnectionPriorityReassert` **零调用**（只有 `docs/bug/bug-蓝牙断连.md` 一句"保持关闭，先只验证 5s 重试链"）。也就是说：**降档一定会发生，但我们从来没有把它拉回 HIGH。** 这是本轮最便宜的一个开关。

> 反证/限制：库注释写的是 Mobi；X2 是否同样 15s 降档没有直接观测（诊断包不记 interval/latency/timeout）。所以这条是**强推断**，不是定论；但改动成本只有一行、可观测指标清楚，值得先试。

### 2.3 第二条：一次写失败就剪线（60–90 秒周期链）

[已证实] 16:58:06 / 16:59:19 / 17:00:32 / 17:01:32 / 17:02:32 / 17:03:34 / 17:05:05 形成一条**约 60–90 秒一轮**的链，每轮结构完全相同：

```
CRITICAL_ERROR  pump  ERROR_RESPONSE
CRITICAL_ERROR  pump  CHARACTERISTIC_WRITE_FAILED
WRITE_CUT       write-failed  非授权特征写失败 → 主动剪线
DISCONNECTED    callback（status=null；库侧随后记 REMOTE_USER_TERMINATED_CONNECTION）
```

- 代码位置：`pumpcomm/.../PumpCommHandler.kt:954-966`。除 `AUTHORIZATION_CHARACTERISTICS` 外，**任何一次**写失败都执行 `cancelConnection()` + 手动 `onPumpDisconnected()`，没有重试、没有计数、没有"泵忙"豁免。
- 写失败的 uuid 全部是 `7B83FFF6-9F77-4E5C-8064-AAE2C24838B9`（CURRENT_STATUS，即命令下发通道）——16 份带 `writeFailures` 的快照（去重后）里 16/16 都是它。
- 全窗口 `CHARACTERISTIC_WRITE_FAILED` 去重后 **49 次**，但 `WRITE_CUT` 只有 5 次（只在 `pumpConnectedPrecondition` 成立时剪线）。也就是说多数写失败被泵端拒绝后靠重连自愈，只有少数把链路剪断。

[推断] CURRENT_STATUS 写失败通常是**泵忙**（大剂量/装药/菜单）或**写队列拥塞**（`WITH_RESPONSE` 串行，前一条没回包后一条就吃 ERROR）。这解释了为什么链的周期恰好是 60–90 秒：一轮重连 + 首页/大剂量轮询把队列重新填满。

### 2.4 第三条：屏灭静默期的掉线

[已证实] 119/172 份断连快照是**屏灭**状态（69%）；`deviceIdle` 全为 false、`powerSave` 全为 false，心跳每 60s 一条不断——排除 Doze、省电、进程被杀、服务被回收。

[已证实] 09:52–09:59 那一段连续 9 次掉线，存活依次约 118s → 59s → 27s → 36s → 16s → 26s → 21s → 53s → 15.7s，其中 **5 次 `rx=0 且 tx=0`**：App 在屏灭时几乎没有收发，链路自己超时。

[推断] 屏灭 + 无流量时，低功耗档的 2s 监督超时更容易被触发（手机侧省电调度、射频共存都会放大丢事件概率）。保活一次读取（30–60s）或保持 HIGH 档，都能显著降低这类掉线。

### 2.5 建立阶段失败（次数少但都直接导致重连）

[已证实] 24h 去重后：`SET_MTU_FAILED` **8**、`BT_CONNECTION_FAILED` **3**、`NOTIFICATION_STATE_FAILED` **3**、`CONNECTION_UPDATE_FAILED` **3**、`ERROR_RESPONSE` **15**、`disconnected ... before completing service discovery` **3**。

[已证实] 09:57:27.944 `SET_MTU_FAILED` 后立刻断（该轮从未到达 CONNECTED 之后的稳定态），随后 09:57:32 又重新 connect。

[推断] 250ms 的首次重连延迟太激进：上一条链的 GATT/CCCD 还没完全释放就重连，MTU/notification 阶段容易拿到失败。

### 2.6 重复断开通知（剪线路径的副作用）

[已证实] 5 次「1.5s 内两条 DISCONNECTED」，全部发生在剪线场景：App 手动 `onPumpDisconnected` 之后，库回调又触发一次。两条通知会各自排一次重连（250ms 与 375ms），造成同一时刻两条 `CONNECT_START`，进一步放大 MTU/连接阶段的竞争。

### 2.7 已排除项

| 怀疑项 | 结论 | 证据 |
|---|---|---|
| 进程被杀 / 崩溃 / 被冻结 | **排除**（本轮窗口内） | 01:45 起单 session 存活 8.4h，心跳连续；`processAgeMs≈30,389,000`、`bootCount` 未变 |
| Doze / 省电 | **排除** | 172 份快照（去重）`deviceIdle=false`、`powerSave=false` |
| 服务被回收 / FGS 失效 | **排除** | `fgsRunning=true`，每次重连都伴随 `FGS_START`（正常，不是重启） |
| 电池白名单 | **未加白名单**，但不是本轮元凶 | `batteryWhitelisted=false`；同时进程存活、心跳不断，说明 MIUI 没冻进程 |
| 距离过远 | **不能单独解释** | 69% 断连发生在屏灭；且 15–17s 簇里 10 次 `rx=0`，连"读到 RSSI 变差"的机会都没有 |

> 需要说明：12-10 16:36–01:45 之间有 19 次 `SESSION_OPEN`（`上次会话未正常关闭`）。这段时间正好在装包/重启大剂量修复版，不能算作崩溃证据；包里没有 crash buffer，无法进一步区分。

### 2.8 诊断包本身的三个缺口

1. `CRITICAL_ERROR` 只记错误名，不记 uuid/opCode/status；uuid 只能从 `snapshot.writeFailures` 聚合里反推（本次恰好全同一个 uuid）。
2. `DISCONNECTED` 不记连接参数（interval/latency/timeout），**无法把 15–17s 簇与降档直接对上**——这是本轮结论只能停在"强推断"的原因。
3. 没有 HCI/系统蓝牙日志、没有 crash buffer，只能证明"App 侧发生了什么"，不能证明"控制器/射频侧发生了什么"。

## 3. 修改意见（按优先级，均可独立验证）

### P0-1 启用连接参数复位（1 行，收益最大）

- 改哪里：`pumpcomm/.../PumpCommHandler.kt:313` 的 `Pump.init{}`，在 `Timber.i("Pump init")` 前加 `enablePeriodicConnectionPriorityReassert()`。
- 为什么：库已实现「每 10s 检查一次，不在 HIGH 档且泵不忙就重新请求 HIGH」，本仓从未调用；28 次 15–17.5s 掉线正对着"连接后 15s 降档"的已知行为。
- 验收：同一监控开 1 小时，**15–17.5s 窗口的断连应显著下降**（基线 28 次 / 24h ≈ 1.2 次每小时），`code 8` 总数下降；若 1 小时后该窗口仍占多数，说明 X2 不是这条路径，立即回滚这一行。
- 风险：每 10s 一次参数请求，耗电可忽略；泵忙时库已自动跳过；`onConnectionUpdated` 里对泵忙有豁免，不会打断大剂量。

### P0-2 写失败分级处理，不再"一刀剪线"

- 改哪里：`PumpCommHandler.kt:954-966` 的 `WRITE_CHARACTERISTIC_FAILED_CALLBACK` 分支。
- 建议规则（保持 AUTHORIZATION 分支原样）：
  1. 非授权特征写失败 → 先**不剪线**，记录 uuid + 次数，250ms 后重发同一条（同 txId 或按现有协议重同步）；
  2. 同一 uuid 在 10s 内连续 ≥3 次失败，或失败同时收到明确 `ERROR_RESPONSE` 且泵不处于忙态 → 才 `cancelConnection()`；
  3. 剪线后**先去重**，500ms 内不再重复通知 `onPumpDisconnected`（见 P1-4）。
- 为什么：16:58–17:11 那条 60–90s 周期链，每一轮都是一次瞬时写失败把链路剪断；`ERROR_RESPONSE` 已经说明泵"听到了但拒绝"，属于可重试语义，不是链路故障。
- 验收：`WRITE_CUT` 计数从 5/24h 降到 0–1；`CHARACTERISTIC_WRITE_FAILED` 之后连接仍保持；断连次数（每小时）下降。
- 风险：不剪线可能让某条写永久失败（队列堵死）。所以保留"连续 3 次"兜底，并给重发加超时（例如 2s 内没回包就作废这条请求）。

### P1-3 写通道单飞 + 1s 轮询降频

- 改哪里：`PumpCommandPort` / `PumpCommHandler` 的发送入口（与"查询器"主线的单飞同一处）。
- 建议：同一 characteristic 同时只允许 **1 条 `WITH_RESPONSE`** 在飞；`CurrentBolusStatus` 这类 1s 轮询在「上一条未回包」或「页面不可见」时直接跳过本次，不排队。
- 为什么：97/172 次断连时 `bolusPoll1s>0`（56%），`txBySourceLastMinute` 里 `other` 常到 7–56；写队列拥塞本身就是 CURRENT_STATUS 写失败的来源之一。
- 验收：`txLastMinute` 峰值下降；`CHARACTERISTIC_WRITE_FAILED` 次数下降；大剂量细条与通知页刷新频率不变（用户可见行为不变）。

### P1-4 重连节律：有界退避 + 去重 + 合并定时器

- 改哪里：pumpx2 侧 `TandemBluetoothHandler.java:1150`（`reconnectDelay *= 1.5`，无上限）与 `:1092`（`onConnectionFailed` 固定 5s 重试）；App 侧手动 `onPumpDisconnected`（`PumpCommHandler.kt:964`）。
- 建议：
  1. 首连延迟 250ms → 500ms（给上一条链留释放时间）；
  2. 退避上限 10s、加 ±20% 抖动，连上后重置；
  3. `onConnectionFailed` 的重试并入同一个退避状态机，不要和库内 `postDelayed` 并行；
  4. 500ms 内重复的断开通知只处理第一条。
- 为什么：当前连续失败时 250→375→562→…→9.6s→14s 无上限，同时还有一条固定 5s 的并行重试；叠加 5 次重复通知，制造了多余的 `CONNECT_START`（09:57 那一段 4 秒内两次 `initial`）。
- 验收：`CONNECT_START` 次数 / 断连次数 比值下降（理想 ≤1.2）；`SET_MTU_FAILED`、`CONNECTION_FAILED_ESTABLISHMENT` 归零。
- 风险：这是**库内改动**（`pumpx2`），需要本地 `use_local_pumpx2` 或上游 PR；若想先只改 App 层，可先做第 4 条（去重）与首连 500ms（在 App 调 `onPumpDisconnected` 前 sleep 不可取，只能在库侧）。

### P1-5 建立失败后重扫，而不是只重连同一条链路

- 改哪里：`onConnectionFailed` 路径（库侧）+ App 的 `INIT_PUMP_COMM` 入口。
- 建议：`SET_MTU_FAILED` / `BT_CONNECTION_FAILED` / `NOTIFICATION_STATE_FAILED` 后先 `cancelConnection()`，等 1–2s，再 `startScan()`（而不是 `immediateConnectToPeripheral`）。
- 为什么：这 8 + 3 + 3 次失败全部卡在"GATT 已建立但初始化没走完"；此时直接重连同一条 peripheral 最容易再次拿到同样的失败。
- 验收：连续失败次数下降；单轮恢复耗时（断→稳定 >60s）下降。

### P2-6 屏灭静默保活（可选，先看 P0 效果）

- 建议：若 P0-1 上线后 15–17s 簇消失、但屏灭段仍有 `rx=0` 掉线，再加「连接存活且 60s 无收发 → 发一条轻量读取（电池或当前状态）」。不要做成高频轮询。
- 验收：屏灭段 `code 8` 次数下降，`rxLastMinute=0` 的断连比例下降。
- 风险：多一条周期性请求，需并入单飞队列；耗电可测量（`rx/min` 基线 9）。

### P2-7 监控补三个字段（让下一轮不用再猜）

1. `CRITICAL_ERROR` 事件带 `uuid` 与 `opCode`/`status`（现在只有错误名）；
2. `DISCONNECTED` 事件带连接参数 `interval/latency/timeout`（库内 `onConnectionUpdated` 已收到这些值，落一条即可）；
3. `WRITE_CUT` 带上被剪线时的 `txBySourceLastMinute` 快照。
- 这三项都不改 BLE 行为，只改 `DiagMonitor.onCriticalError/onDisconnected` 的入参，属于"下一轮取证的最低成本补强"。

## 4. 不建议现在做的事

- **不升级 pumpx2**：BolusType 语义重构仍是硬阻塞（11-02 试升编译失败已回滚），且本轮三条根因都在 App/库内可改范围内。
- **不重写重连机制**：先把 P0-1/P0-2 跑一轮，有数据再谈。
- **不用"关开蓝牙"当修复**：它是外部重置，只能证明重连链断了，不解决降档与剪线。

## 6. 决策与落地状态（2026-11-11）

用户按编号表态后的实际落点。原则：X2 本机实测作为**平行于 pumpx2 的补充证据**，用于我们自己的程序设计；pumpx2 基于 Mobi 与网上资料的说法不轻易否定，库保持原样。

| P0-2 | 同意，先做 | `WRITE_CHARACTERISTIC_FAILED_CALLBACK` 改为分级：同 uuid 在 10s 内累计 ≥3 次才 `cancelConnection()`；单次失败只记 `WRITE_FAILED` 并进入 500ms 只读冷却 |

### 8.5 底栏细条「展开时核对」与 reassert 的联动副作用

**细条展开补一条只读查询（已实现）**：点细条露出「取消」的瞬间，向查询器补一次

  `BolusSessionController` 自己推进会话（ACTIVE → 立即段结束 / UNKNOWN → 自愈 IDLE），
  细条随之改文案或消失，按钮逻辑不变。

**`enablePeriodicConnectionPriorityReassert()` 的联动副作用（此前未说透）**：

### 8.6 口径修正：「静默」不是监督超时的触发条件（2026-11-11 14:08 实测）

连续采样 10 分钟（13:58:39–14:08:47，20s 一次，`/api/diag/state`）：

- `connected` 全程 true，`connectedForMs` 从 329.8s 连续涨到 916.7s，**0 次断开**；
- 参数恒为 `15ms / latency=0 / timeout=5s`，`blePolicy.source=asset`，`writeFailures={}`，
  `incidentCount` 保持 55 不变（没有新事件）；
- **App 层 `lastRxAgo` 反复到 ~59s**（每 60s 一次心跳前的最长空窗），链路仍然没断。

由此修正本文 §8.3 / 前文对「保底心跳」的表述：

1. 监督超时看的是**链路层是否有任何包（含空包）**，不是 App 侧有没有查询回包。
   所以「App 静默 59s」本身不会触发 `code 8`——实测 10 分钟内出现了三次 59s 空窗，全部存活。
2. 低功耗档真正的脆弱点是**余量**：`timeout=2s`、`latency=29`、`interval=30ms` 时
   规范下限 `(latency+1)×interval×2 = 1.8s`，只剩约 200ms 余量；泵忙/系统调度抖一下
   就跨过 2s，表现为 `code 8`。这才是「连上 15s 后降档 → 15–17.5s 掉线簇」的合理解释，
   而不是「App 没发查询」。
3. 因此轴 B（查询频度）的价值是**省电与降负载**，不是用来兜监督超时；
   兜超时靠的是轴 A 把参数维持在 HIGH（`driver=library` 的每 10s + 事件纠偏已在做）。
   保底心跳仍需存在（保证数据新鲜度与泵侧交互不断），但它的上限由业务时效决定，
   不再声称「必须小于 2s×(latency+1)」。

#### 8.10 待复核两项（不单独立项，随查询器改造一并推进）

这两项都不影响「距离/RF 路径是主因」的结论，只影响「还有没有次要放大器」，
因此不单独开调查，挂在查询器改造里一起做。

**（1）同泵地址多 GATT clientIf（疑似 `connectDevice` 未 close 的多开泄漏）**

- 现象：bt_stack 掉线时同一泵地址 `CD:F7:E3:22:9B:47` 同时存在 7 个 clientIf
  （3/4/5/7/10/13/16），reason 全为 `0x0008`。
- 核查方式：复现时抓 `bta_gattc_conn_cback`，按 MAC 统计 clientIf 新增与关闭事件；
  对照 `TandemBluetoothHandler` 的 `connectDevice` / 断开路径是否成对调用。
- 判据：同一泵地址同时存活的 clientIf ≤ 1，且断开后 60s 内归零。
- 与查询器的关系：若确为多开，每次重连会新增一条通道，查询并发与重发都会被放大，
  必须在协调器转 `LIVE` 前排除，否则 `EDGE` 判定会被假并发污染。

**（2）应用不在电池优化白名单（`batteryWhitelisted=false`）**

- 核查方式：`adb shell dumpsys deviceidle whitelist` 确认包名是否在内。
- 为什么要查：不在白名单时，Doze 会延迟 App 定时器，表现为「查询没发出去」，
  与「链路断了」在外部观测上难以区分——这正是早期把「屏灭」误判成成因的一类混淆源。
- 判据：同一「静止 + 屏灭」场景下，加入白名单前后 `PUMP_VITALS` 实际间隔对比；
  若加入后间隔明显收紧，说明 Doze 确实在压查询节拍。
