# 蓝牙链路策略：P1-4 / P1-5（独立文件，暂不改 pumpx2）

> 生成日期：2026-11-11。对应《断连诊断包分析-20261111.md》里的 P1-4（重连节律）与 P1-5（建立失败后重扫）。
> 用户决定：这两条**只落成独立文件 / 配置**，不改 `pumpx2` 库——因为目前还无法确认 Mobi 的真实行为。

## 1. 为什么单独成文

- 本仓对 X2 的实测（诊断包 2026-11-11，24h 去重 172 次断开）是**平行于 pumpx2 项目的补充证据**：
  它能证明「X2 上发生了什么」，但推不出「Mobi 也这样」。
- pumpx2 里关于 15 秒降档、`busyWorkflowReason()` 豁免等说法，来源是 Mobi 与网上收集的资料。
  在拿到 Mobi 侧证据之前，**不否定、也不盲从**：库保持原样，把策略参数写成我们自己的配置项，
  等行为确认后再决定「改库 / 用配置喂给库 / 只在我们这层兜」。
- 因此本文件描述的是**设计参数与验收口径**，不是已生效的代码。是否接入、何时接入，单独立项。

## 2. 支撑这两条策略的实测数字

| 现象 | 24h 去重口径 | 说明 |
|---|---|---|
| 断开总数 | 172（≈7.2/h） | 中位存活 33.7s；33.1% 不到 20s |
| `WRITE_CUT` | 5 | 均为「一次写失败即剪线」 |
| 重复 `DISCONNECTED`（<1.5s 内两条） | 5 | 全部发生在剪线场景：App 手动通知 + 库回调各一次 |
| 建立阶段失败 | `SET_MTU_FAILED` 8 / `BT_CONNECTION_FAILED` 3 / `NOTIFICATION_STATE_FAILED` 3 / `CONNECTION_UPDATE_FAILED` 3 | 均卡在「GATT 已建立、初始化没走完」 |
| 单次快速重连 | 09:57 段 4 秒内两次 `CONNECT_START`（`initial`） | 250ms 重连与库内 5s 固定重试并行 |

对应库位置（只读核对，未改动）：
`TandemBluetoothHandler.java:1150`（`reconnectDelay *= 1.5`，无上限）、
`:1084-1096`（`onConnectionFailed` 固定 `postDelayed(immediateConnectToPeripheral, 5000)`）、
`:1080`（连上后 `reconnectDelay` 重置 250ms）、`:1135-1143`（`maxRetryCount(3)` 后 `ReconnectPaused`）。

## 3. 建议参数（配置草案，**尚未被代码读取**）

```json
{
  "reconnect": {
    "initialDelayMs": 500,
    "maxDelayMs": 10000,
    "jitterPct": 20,
    "resetOnConnect": true,
    "singleOwner": true
  },
  "disconnectNotify": {
    "dedupeWindowMs": 500
  },
  "establishFailure": {
    "cancelThenRescanDelayMs": 1500,
    "rescanInsteadOfReconnect": true,
    "appliesTo": ["SET_MTU_FAILED", "BT_CONNECTION_FAILED", "NOTIFICATION_STATE_FAILED", "CONNECTION_UPDATE_FAILED"]
  },
  "connectionPriority": {
    "reassertEnabled": true,
    "reassertIntervalMs": 10000,
    "skipWhenPumpBusy": true
  }
}
```

取值的依据：

- **首连 500ms**：给上一条链路留释放时间。现在 250ms 首连叠上库内 5s 固定重试，会产生成对的 `CONNECT_START`。
- **上限 10s + ±20% 抖动**：现在的 ×1.5 无上限，连续失败会退到 14s 以上且没有抖动，容易和其它重试节拍撞在一起。
- **500ms 去重**：实测重复通知间隔 110–140ms；500ms 足够合并，又不会吞掉「真断两次」。
- **建立失败后 1.5s 重扫**：`SET_MTU_FAILED` / `NOTIFICATION_STATE_FAILED` 说明 GATT 已建立但服务发现/订阅没走完，直接重连同一条 peripheral 最容易复现同样的失败。
- **reassert 10s / 泵忙跳过**：沿用库内默认（`periodicConnectionPriorityReassertInterval = 10_000L`），不另造节拍。

## 4. 接入前提（现在故意不做的事）

1. **不改 `pumpx2` 库**：上面 4 组参数里，`reconnect` 与 `establishFailure` 的落点都在库内
   （`TandemBluetoothHandler` 的 `onConnectionFailed` / `onDisconnectedPeripheral`），App 层拿不到这些钩子。
2. **不伪造「已生效」**：本文件的 JSON 目前没有消费者。谁先接入，谁负责在
   `PumpQueryService` / 诊断页里暴露一个「策略版本 + 实际生效值」字段，避免出现「改了配置但没人读」。
3. **接入方式三选一**（按成本从低到高）：
   - 上游 pumpx2 增加 `TandemConfig.setReconnectPolicy(...)`，我们只传值；
   - 在本仓 fork 一份 `TandemBluetoothHandler` 子类（需评估维护成本）；
   - 只在 App 侧做「去重 + 首连延迟」（第 3 节里唯一不依赖库的两项）。
4. **未确认项**：Mobi 是否同样在连接约 15s 后降档到 `interval 30ms / latency 29 / timeout 2s`。
   在拿到 Mobi 日志前，任何「Mobi 也适用」的表述都只能标为**假设**。

## 5. 验收口径（接入后按此复测）

| 指标 | 当前基线（24h） | 目标 |
|---|---|---|
| `CONNECT_START` / 断连次数 | ≈1.4（09:57 段 4s 内 2 次） | ≤1.2 |
| 重复 `DISCONNECTED`（<1.5s） | 5 | 0 |
| `SET_MTU_FAILED` + `BT_CONNECTION_FAILED` | 8 + 3 | 归零或 ≤1 |
| 断→稳定（>60s 不掉）耗时 | 未单独统计 | 单轮 ≤10s |
