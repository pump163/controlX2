# 断连临时监控（阶段性设施：默认保留，可暂停）

> 状态：**阶段性成果**。用于定位当前这次蓝牙断连；「抓现场」这条路已验证可用，**代码保留，不整体删除**。
> 暂停方式：**注释入口 + `diag_monitor/enabled` 默认关**（不建线程、不写盘）；需要时按 §7.2 逐步恢复。
> 不做长期归档：普通 incident 只留 24h / 50MB（先到先清）；`PAUSED`/`WRITE_CUT`/`CONNECT_FAILED` 单独永久保留；不写公共目录镜像、不加密。
> 不改 BLE 库（blessed / `TandemBluetoothHandler`）、不改重连策略与退避逻辑、不记泵序列号。

## 1. 为什么做、怎么定位

上次断连等了数小时，最后因「App 无法启动」卸载重装，本地证据被清空。那是孤立事件，不值得为它建永久设施；这次改为**阶段性监控**：只在调试页开一个开关，抓断连现场；验证完成后**暂停（不删代码）**，需要时再开。

要区分的三种情况：

| 现象 | 判据 |
|---|---|
| 射频/链路超时（正常物理断链） | `DISCONNECTED` 且 `status=CONNECTION_TIMEOUT`(0x08) |
| 写失败主动剪线（工程问题，本方案重点） | `WRITE_CUT`：非授权特征写失败 → `cancelConnection()` + 手动 `onPumpDisconnected(null)` |
| 进程/服务被杀 | 心跳断档 + `processStart` 变化 / `UNCLEAN_EXIT` / `ON_TASK_REMOVED` |
| 重连策略失效/停手 | 断开后长时间无 `CONNECT_START`，或旁采到 `ReconnectPaused` / `manual_reinit` |

关键点：**写失败剪线不等射频 supervision timeout**，所以「断开」不一定等于「离得远」；必须靠 `WRITE_CUT` 与 `HciStatus` 区分。`HciStatus` 此前只进了 Toast，现已补进日志（见 §6）。

## 3. 页面（调试页一行进入）

顶部状态卡三态（按证据判定，不是布尔默认值）：

- **链路活**：已连接且 `lastBleRx` ≤ 30s
- **链路在但没数据**：已连接但 ≥ 30s 无真实回包（假连接/静默）
- **已断开**：未连接，显示距断开时长、`HciStatus`、断法来源
- `NO_LINK` / `OFF`：本进程未连过 / 采集未开启

其余项：进程 pid 与存活时长、会话 id、最近断开（status+来源）、`lastBleRxAgo`/`lastBleTxAgo`、心跳间隔、FGS 是否在跑、屏幕/Doze/省电/电池白名单/电量、深睡累计（`elapsedRealtime - uptimeMillis`）、最近一分钟 rx/tx、按来源拆分（`bolusPoll1s`/`actions1s`/`historylog`/`bulk`/`other`）、近 10 秒 bolus 轮询次数（≈并行循环数）、写失败计数（按 uuid）、incident 份数与 live 字节数。

按钮：**冻结当前**、**复制摘要**、**导出诊断包**、**清理已导出**（采集开关已移至「危险指令」）。页面 1Hz 刷新，**只读内存，不触发写盘**；导出与清理是显式动作（见 §5.2）。

## 4. 落盘

目录 `filesDir/diag/`：

- `live.jsonl`：常规流水，写满 **1MB 覆写重来**（不保留 prev，不报错、不停止采集）
- `incident-<yyyyMMdd-HHmmss>.json`：断连现场快照（普通区），保留规则见 §4.1
- `protected/incident-<yyyyMMdd-HHmmss>.json`：三类严重事件专用（见 §4.1），**永不自动清理**
- `last_state.json`：原子替换（tmp + rename），30s 或关键事件后更新，带 `clean` 标记
- `export-marker.json`：最近一次导出记录（`at` + 普通 incident 文件名列表），供清理时按名单删除

写盘时机：

- GATT 回调线程只做**内存 append**（ring 上限 2000 条 + 计数器），绝不 IO
- 常规 15s 合并 flush（单线程 `diag-store`，有界队列）
- 关键事件立即入队并触发 flush：`DISCONNECTED` / `WRITE_CUT` / `CONNECT_FAILED` / `PAUSED` / `AWAIT_USER` / `ON_TASK_REMOVED` / `SERVICE_DESTROY` / `APP_EXIT` / `UNCLEAN_EXIT` / `SESSION_OPEN`
- incident 冻结的去抖**只作用于非 force 事件**（见 §4.2），避免一次断连写一堆文件
- 心跳 60s 一条；`onTaskRemoved → Runtime.exit(0)` 前**同步落盘**（`flushSync` + clean 状态），避免最后几条丢队列
- 不做 1s 落盘、不做常规 fsync；单条事件落盘最坏丢 15s，断连现场已单独冻结成文件

### 4.1 保留策略（24h + 50MB，严重事件永久保留）

普通区（`filesDir/diag/incident-*.json`）两条上限，**先到先清**：

| 规则 | 值 | 说明 |
|---|---|---|
| 时间窗 | **24 小时** | 文件名时间戳早于「现在 − 24h」即删 |
| 总容量 | **50MB** | 先清过期，再按最旧优先删到 ≤50MB |

判定顺序（每次写新 incident 后、以及启动时执行一次）：

1. 按 24h 时间窗删除过期普通 incident；
2. 剩余总量 > 50MB 时，从最旧开始删，直到 ≤50MB；
3. protected 区不参与以上任何一步。

永久保留区（`filesDir/diag/protected/`）：`PAUSED` / `WRITE_CUT` / `CONNECT_FAILED` 三类 incident（trigger 前缀匹配）写入此目录，**不参与时间窗与容量清理**，也不会被诊断页的「清理已导出」删掉。

- 理由：这三类是「重连策略停手 / 写失败剪线 / 连接建立失败」的直接现场，丢弃后无法复盘，而它们在正常夜里只有个位数，体积不是问题。
- 旧版本已经写在普通区的这三类文件，`diag-store` 启动时会读 JSON 的 `trigger` 并 `rename` 到 `protected/`，避免被新策略误清。

永久保留区的软阈值：**10MB**（约 160 份 60KB 快照）。

- 只提示、不删除：超过阈值时写 `SharedPreferences("diag_monitor")` 的 `protected_over_at` / `protected_over_bytes` / `protected_over_count`，并打一条 `Timber.w`；24 小时内最多提示一次，避免刷日志。
- 选 10MB 的理由：一整夜严重事件约 10–30 份（≈0.6–1.8MB），10MB 能容纳约一周的极端量；超过说明清理/收敛机制该介入了，但证据不能自动丢，所以只报警。
- 当前只能靠日志/prefs 感知，页面不展示该提示（保持页面只读）。

### 4.2 去抖到底作用在谁（修正旧文档）

旧文档写「incident 冻结有 20s 去抖」，与代码不符。实际规则（`freezeInternal(trigger, force)`）：

| 事件 | force | 是否受 20s 限制 |
|---|---|---|
| `DISCONNECTED` | true | **否** |
| `WRITE_CUT` | true | **否** |
| `CONNECT_FAILED` | true | **否** |
| `PAUSED` | true | **否** |
| `ON_TASK_REMOVED` / `SERVICE_DESTROY` | true | **否** |
| 手动冻结 `freezeNow("MANUAL")` | true | **否** |
| `AWAIT_USER` | false | 是 |
| `FGS_STOP` | false | 是 |

为什么 `DISCONNECTED` 这类要 `force=true`：断连/剪线/建连失败/停手本身就是本次要抓的现场，宁可多写几份也不能因为「20 秒前去抖过」而漏掉真正的首次断点；去抖只用来压制高频、信息量低的伴随事件（等配对码、FGS 停）。


## 5. 取回与导出

### 5.1 HTTP 取回

复用现有 `HttpDebugApiService`（端口 `18282`，Basic auth，与 `192.168.8.52` 同一套）：

- `GET /api/diag/state` → 与页面同款摘要 JSON
- `GET /api/diag/files` → 目录路径 + incident 列表（含 `protected` 标记）+ live 字节数 + `exportedCount`
- `GET /api/diag/incident/latest`（或 `?name=incident-...json`）→ 原始快照（普通区与 protected 区都能按文件名取）
- `GET /api/diag/live?tail=500` → 常规流水末尾

注意：HTTP 只在采集开启且进程存活时可用。进程被 `Runtime.exit(0)` 杀掉后，文件仍在 `filesDir/diag/`，重新打开 App 或 `adb pull` 可拿。

### 5.2 导出与清理（诊断页）

入口在**诊断页**（调试页 → 断连监控），不新开页面。

**导出**：按钮「导出诊断包」→ 后台线程打包 `filesDir/diag-export/diag-bundle-<yyyyMMdd-HHmmss>.zip`，随后直接走系统分享（`FileProvider` + `ACTION_SEND`，MIME `application/zip`）。

- 选择「分享 intent」而非「写外部目录」的理由：一是与调试页现有的 Support Bundle 导出方式一致，用户已经熟悉；二是 Android 10+ 分区存储下写公共目录需要额外权限/MediaStore 适配，而分享可以交给用户自己选（发微信、存文件、发邮件都行），不留权限包袱；三是导出包含完整现场，适合「发出去」而不是「留在机器上」。
- 只保留最近 **5 个**导出 zip，更旧的自动删除，避免导出目录自己膨胀。
- 打包内容：
  - `incident/…`（普通区）+ `incident/protected/…`（永久保留区）原文
  - `live.jsonl`（当日事件线）
  - `state.json`（`/api/diag/state` 同款状态快照）
  - `summary.txt`（`复制摘要` 同款文本）
  - `manifest.txt` / `manifest.json`（可读清单：文件名、字节数、trigger、是否 protected、mtime，以及 incident 时间范围）
- 导出成功后写 `filesDir/diag/export-marker.json`：`{"at": 导出时间, "files": [普通 incident 文件名…]}`。protected 文件**不进名单**。
- 没有可导出文件（无 incident 也无 live）时返回失败，不产生空包。

**「已导出，可清理」状态**：诊断页在导出按钮下方显示
- `exportedCount > 0`：`已导出，可清理：N 份普通 incident（protected 不计入、不会被删）`
- `exportedCount == 0`：`未导出则不可清理；导出成功后此处显示「已导出，可清理」`

**清理触发条件（必须同时满足）**：

1. **用户显式点击**「清理已导出」按钮，并二次确认对话框；
2. 存在 `export-marker.json`（即至少成功导出过一次）；
3. 只删 marker 名单里的、且位于普通区 `filesDir/diag/` 的 `incident-*.json`。

不满足条件的文件一律不动：**不存在「没导出就静默删」**。时间窗/50MB 的自动清理只作用于普通区，且与导出无关（它保护的是「即将写爆」而不是「可删」）；protected、`live.jsonl`、`last_state.json`、`export-marker.json` 永不自动删。

防误删保护：

- 名单项必须是 `incident-` 开头、且不含 `/` 或 `\`（防路径穿越）；
- 目标必须是普通区存在的普通文件（`protected/` 下的同名文件不会被命中；若文件已被迁移到 protected，普通区不存在则跳过）；
- 删除失败的文件会留在 marker 名单里，下次还能再试；
- 删除完成后重写 marker（只留未删成功的），`exportedCount` 随之归零/减少，页面立即回到「未导出则不可清理」。


## 6. 字段与判读

每条事件（JSONL）：`t`（wall 格式化）、`wall`、`el`（elapsedRealtime）、`kind`、`src`、`detail`、以及可选 `statusCode`/`uuid`/`messageClass` 等。

会话头 `SESSION_OPEN` 带：`device`、`sdk`、`processStartWallMs`、`processStartElapsedMs`、`bootCount`。

时间基的意义：

- `elapsedRealtime` 单调，跨进程重启也连续（除非重启手机）
- `processStartElapsedMs` 变化 = **进程重启**，不是断连
- `elapsed - uptime` = 深睡累计，判断是否被冻结
- `bootCount` 变化 = 手机重启

判读规则：

| 日志特征 | 结论 |
|---|---|
| `DISCONNECTED` + `statusCode=8`（CONNECTION_TIMEOUT） | 射频/链路超时（离得远）——正常物理断链 |
| `WRITE_CUT` 紧邻 `DISCONNECTED`（`status=null`） | 写失败主动剪线——工程问题，不是射频 |
| `DISCONNECTED` + `statusCode=0x13`（REMOTE_USER） | 泵侧/对端主动断开 |
| 心跳连续、`processStart` 不变 | 进程一直活着 → 排除「被杀」 |
| 心跳断档 + `processStart` 变 / `UNCLEAN_EXIT` | 进程被杀/崩溃/重启 |
| 断档 + 屏灭 + Doze + 省电，且 `uptime` 远小于 `elapsed` | 被系统冻结，定时器被推迟 |
| `PAUSED` / 旁采 `ReconnectPaused` / `manual_reinit` 后无 `CONNECT_START` | 重连策略停手 |
| 断开后无 `CONNECT_START`、`attemptCount` 推断停滞 | 重连未启动（pending connection 丢失） |
| 已连接但 `lastBleRxAgo` 持续增长、无 `DISCONNECTED` | 回调缺失/链路静默（只记录，不改库） |

已知局限：**重连尝试次数与退避发生在 pumpx2 内部，项目侧没有回调可直接观测**。方案用两个替代：连接/断开时间戳反推，以及 `DebugTree` 关键字旁采（`reconnect` / `backoff` / `ReconnectPaused` / `manual_reinit` / `await_user` / `onConnectionFailed` / `INITIAL_AUTH_NO_REPLY` / `cancelConnection` / `CONNECTION_TIMEOUT` / `CONNECTION_FAILED` / `resetInstance` / `getInstance`）。旁采是文本匹配，pumpx2 改文案会失效，属可接受的临时折中。

## 7. 暂停与恢复（代码不删）

> 原则：这套设施是阶段性成果——「抓现场」这条路已经走通，以后遇到类似问题还要用。**暂停只做两件事：注释入口 + 开关默认关；不删文件、不留半删状态。**

### 7.1 如何停

1. **入口注释**：把 26 处 `// DIAG-TEMP` 埋点用 `//` 注释掉，保留代码文本。最低限度要注释掉会建线程/写盘的入口：
   - `PumppanApplication.kt:30` `DiagMonitor.initialize(this)`
   - `CommService.kt` 的 `SERVICE_CREATE` / `SERVICE_START` / `FGS_START` / `ON_TASK_REMOVED` / `SERVICE_DESTROY`
   - `PumpCommHandler.kt` 的 `onConnected` / `onDisconnected` / `onConnectStart` / `onAwaitUser` / `onCriticalError` / `onRx` / `onTx` / `onWriteCut`
   - `DebugTree.kt:55-56` `onLogLine` 旁采
   - `HttpDebugApiService.kt:340-346` 路由（不注释也能停写盘，但会继续暴露 `/api/diag/*`；若不想暴露，一并注释）
2. **开关默认关**：把 `diag_monitor/enabled` 的默认值改回 `false`（暂停态）；采集期再改 `true`。
3. **确认不建线程/不写盘**：`enabled=false` 时 `record()` 在入口 `if (!enabled) return` 直接返回，`DiagStore` 不启动、不建 `diag-store` 线程，不写 `live.jsonl` / `incident-*.json` / `last_state.json`。
4. **页面保留**：调试页与诊断页可保留（只读内存；采集关时显示 `OFF`），不必删入口。

### 7.2 如何恢复

按依赖顺序逐步反注释，每步用 `/api/diag/state` 验证：

1. `PumppanApplication` 的 `initialize` + `CommService` 的 service 事件 → 确认 `enabled=true`、`liveBytes` 开始增长。
2. `PumpCommHandler` 的 BLE 回调（连接/断开/初始化/错误/rx/tx/剪线）。
3. `DebugTree` 旁采（用于 `INITIAL_AUTH_NO_REPLY`、`ReconnectPaused` 等关键字）。
4. `HttpDebugApiService` 的 4 个 `/api/diag/*` 路由。
5. 打开调试页开关，确认 1Hz 刷新与「冻结当前」「导出诊断包」可用。

### 7.3 停用后的残留

| 项 | 停用后 |
| --- | --- |
| `filesDir/diag/` | `live.jsonl`（≤1MB）、`last_state.json`、普通 incident（24h + ≤50MB）、`protected/`（永不清理）、`export-marker.json` 保留，**不再增长**；可手动删或卸载清除 |
| `SharedPreferences("diag_monitor")` | `enabled=false` 保留，无害；不需要迁移 |
| 数据库 | 无写入、无表、无迁移 |
| 权限/资源 | 无新增危险权限（通知/前台服务沿用现有）；无额外 so/资源文件 |
| 线程 | `diag-store` 单线程不再创建；已存在的随进程重启消失 |
| 其他功能 | `debugLog-*.txt`、Support Bundle、HTTP 其余端点、BLE 连接与重连均不受影响 |

### 7.4 停用验收（怎么确认真的不写了）

停用 24 小时后逐项核对：

- `/api/diag/files`：incident 列表数量与时间戳不新增；`liveBytes` 不增长；`last_state.json` mtime 不变。
- `shared_prefs/diag_monitor.xml`：`enabled=false` 且文件 mtime 不再变化。
- 线程：`ps -T -p <pid>` 或 `dumpsys` 中无 `diag-store` 线程。
- 落盘目录：无新的 `incident-*.json`；`live.jsonl` 大小不变。
- 日志：无 `diag_store` / `DIAG-TEMP` 相关输出。
- 任一项仍在变化 → 说明还有入口没注释或开关未生效。

### 7.5 停用不等于遗忘：何时重新打开

出现下列任一情况就重新打开（反注释 + 开关 `true`）：

- 再次出现「连上就掉」「长时间不恢复」「GATT 连上但 INIT 未完成」的现场，且现有日志不足以定位；
- 看门狗上线后的「远离→返回」验收，需要 incident + live 做前后对照；
- 任何一次需要判断「是射频余量还是软件缺陷」的复测。

## 8. 什么时候可以停

- **现在还不能停**。要等：看门狗实现 + 一次「远离→返回」验证通过（≤60s 自愈、全程无 `manual_reinit_required`、无二次进程重启）。
