## 背景问题

当前大剂量流程用 5 个独立 AlertDialog 串行切换（权限确认 → 进行中 → 成功/取消中/已取消），存在两个问题：
1. **弹窗被覆盖**：5 个 `mutableStateOf<Boolean>` 理论可同时为 true；zh 新增的 BackHandler 在对话框显示时 collapse bottom sheet 会销毁 BolusWindow，丢失全部状态
2. **发了不管 + 泵警告丢失**：`BolusPermissionResponse.nackReason`（INVALID_PUMPING_STATE、PUMP_HAS_PERMISSION 等）和 `InitiateBolusResponse.statusType` 完全不展示给用户；权限被拒时确认按钮只是 disabled，用户不知道原因

---

## 总体流程：一个入口、输入态 → 执行态两段

```
底部导航栏中间"大剂量"动作按钮（或 FAB，二者同一入口）
  ↓
全屏 BolusFlow 覆盖层（非 tab，完成后自动回 Dashboard）
  ├─ 输入态：剂量框 + 大剂量向导（折叠）+ 扩展开关（折叠）+ 预设 chips
  │     ↓ 点"输注"，产出不可变 BolusDraft
  └─ 执行态：单窗口流式状态机，三结局
```

**入口决策（2026-09-29）**：
- 大剂量是最高频单手操作，入口保留在底部导航栏正中间（zh 现状：FAB 开启时用可拖动 FAB，关闭时在 navItems 中间插入动作按钮，见 Landing.kt:662-691）
- 保持**动作按钮身份，不做成真正的 LandingSection tab**：tab 是可停留浏览的目的地，大剂量是有始有终的事务，输注完不存在"停在大剂量 tab"
- **承载升级**：BottomSheet → **全屏流程页**。理由：① 输入内容增长（向导明细 + now/later 滑块 + 时长 + 流式消息）sheet 空间/滚动打架；② 数字键盘弹起压缩 sheet 高度；③ sheet collapse 销毁 BolusWindow composition 正是弹窗覆盖 bug 的结构根源，全屏页根除
- BackHandler：输入态 = 关闭；执行态 = "取消当前输注？"；输注进行中离开给二次确认

## 输入态布局

```
┌──────────────────────────────────────┐
│  大剂量                           [×] │
├──────────────────────────────────────┤
│  常用  [单次10U] [5+5/30分] [＋保存]  │  ← 预设 chips
│                                      │
│  ① 剂量                              │
│         2.5 单位          [−] [+]    │  ← 最终值，唯一权威，永远可直接编辑
│                                      │
│  ▸ 大剂量向导（可选，默认折叠）        │
│    ┌ 碳水化合物 [  60 ] g  → +1.2U  │
│    ├ 血糖 [12.8]  当前CGM 12.9       │
│    │   目标 6.0 · ISF 2.2 → +0.8U   │
│    ├ 活性胰岛素 IOB          −0.3U   │
│    └ 建议合计 1.7U       [采用建议]   │  ← 明细全可见，采用后仍可手改
│                                      │
│  ② 扩展大剂量              [开关 关] │  ← 默认关
│     （打开后展开）                    │
│     立即  50%  ●────○    1.25U       │
│     延展  50%            1.25U       │
│     时长  [ 2 小时 ▾]                │
│     （总量 < 0.40U 时开关置灰）        │
│                                      │
├──────────────────────────────────────┤
│  [取消]        [输注 2.5 单位 →]      │  ← 扩展开启时按钮显示两段明细
└──────────────────────────────────────┘
```

**设计原则——一个剂量框为中心，其余都是"往框里填数/决定怎么发"的途径：**
1. 主流路径零干扰：直接输剂量 → 输注，两步完成；向导折叠、扩展关闭不挡路
2. **三个入口不是三选一**：手动直接输入是剂量框本身能力；碳水、血糖是两个可叠加的辅助计算器（可同时吃碳水又高血糖：食物 + 矫正 − IOB）。向导产出是**建议**非最终值，"采用建议"是唯一写入动作，写入后可手改（标"已手动调整"）
3. 医疗软件不给黑盒数字：食物/矫正/IOB/合计明细全部展示
4. 扩展默认关、就地折叠（手机有空间，用折叠替代官方泵的"下一步"跳页）；now/later 百分比联动锁定和为 100%，右侧实时显示换算单位数
5. 确认按钮随状态变化：普通"输注 2.5 单位"；扩展时"立即 1.25U / 8 小时内延展 1.25U"

## BolusDraft：输入态与执行态的唯一契约

输入窗口产出不可变草稿，流式窗口只消费、不关心剂量来源：

```
BolusDraft(
  totalUnits,                 // 总量（用户最终确认值）
  source: { carbs, bgUsed, foodUnits, correctionUnits, iobDeducted, manualAdjusted },
  extended: { enabled, nowPercent, laterPercent, durationSeconds,
              immediateUnits = total × now%,
              extendedUnits  = total × later% }
)
```

将来上游加大剂量向导时只替换输入窗口内部，执行页不动；source 明细可留作历史审计。

## 扩展大剂量（Extended/Combo，远期，需真机取证）

**协议已就绪（pumpX2 已核实，2026-09-28）**：无独立消息类，复用 opcode -98 `InitiateBolusRequest` 的 11 参数构造器：
- `extendedVolume`（延展段毫单位）、`extendedSeconds`（延展秒）、`extended3`（未知恒 0）；类型位 `BolusType.EXTENDED=4`，combo 抓包 bitmask=12(EXTENDED|FOOD2)
- 最小量 `MIN_EXTENDED_BOLUS_MILLIUNITS=400`（0.40U），允许 0 立即段纯延展
- 配套：状态查询 opcode 46/47、V2 -74/-73；取消 -96（V2.5，javadoc 明说适用 extended）；历史 opcode 59 激活/21 完成/280（requestedNow/requestedLater/duration）/65（standardPercent）
- **无 MOBI_ONLY 注解（ALL/API_V2_1），但抓包样本仅来自 Mobi**

**X2 真机证据（用户实测官方 app，2026-09-28）**：官方 app 确有此功能，两步式：确认总量 → 下一步开"扩展大剂量"开关 → <0.40U 不执行 → Deliver Now/Later 两百分比 + Duration → 确认。
- **UI 百分比 → 协议绝对值换算由 App 完成**（pumpX2 不做）：`extendedVolume = total × later%`，立即段 = total × now%
- **待取证保留项**：官方 app 有功能证明固件支持，且 -98 是 controlX2 已在用通道（X2 唯一可用输注控制），先验概率高；但按同步时间/查找泵黑名单教训，第三方 BLE 发送仍须真机验证（型号+固件版本+opcode+响应+cargo）。无风险先验：用户在官方 app 发起后，controlX2 历史应见 opcode 59/21，可只读取证
- controlX2 main 现状三零：零发起（全用 8 参数构造器）、零 UI、零查询；仅 db 模块 Nightscout ProcessBolus 读 opcode 280 上传 "Combo Bolus"，App 自身历史不区分

**协议缺口与取证项（2026-09-29 pumpX2 核查）：**
- **延展段实时已输量无字段可读**：ExtendedBolusStatus 46/47、V2 -74/-73 只有 requestedVolume + duration + bolusStatus 裸字节（无枚举），没有 deliveredVolume / 已耗时；执行态与横幅**不做速率×时间估算展示**（医疗数据不展示估算值），只显示计划值/剩余时间，实际剂量让用户看泵端输注记录
- 结局不显示剂量后，以下枚举/字段缺口在阶段 1-3 **均不构成阻塞**，仅阶段 4 做历史解析时才需要：`BolusStatus(0-6)` 库作者自标 "guesswork and is incomplete"（0=STOPPED_USER_TERMINATED、3=COMPLETE 有抓包证实）；opcode 21 BolexCompleted、59 BolexActivated 测试 `@Ignore("needs historyLog sample")` 无真实样本；LastBolusStatusV3（MOBI_API_V3_5，一条响应含 standard+extended 双块）仅 Mobi，X2 不用
- X2 阶段 3 前需自行抓包补证：combo 发送接受流 + -96 中断流的型号+固件版本+原始 cargo；阶段 4 再补 opcode 20+21 历史样本

## 预设大剂量（纯 App 层，可规避泵端专利限制）

泵因专利未提供预设，但**预设不碰任何泵协议**：预设只是保存好的输入参数（命名的 BolusDraft 固定配方），发送仍走同一个 opcode -98，泵不知道"预设"存在。

- **v1 只存最终配方，不存碳水/血糖**：碳水/血糖是时变输入（IOB、profile 时段会变），医疗预设必须是确定值——点"5+5"发的就是 5+5。"60g 碳水模板实时算"留 v2
- 数据模型：`BolusPreset(id, name, totalUnits, extended{...})`；mobile 用 Room 加 `bolus_presets` 表（id/name/各字段/排序/使用次数）
- 交互：点 chip = 预填 + 自动展开扩展区显示明细（不是直发）；[＋保存] 命名保存当前配方；长按 chip 重命名/删除；chip 文案自带摘要（"5+5/30分"）
- **安全铁律：预设只预填，绝不直发**——不减少任何确认环节，误触 chip 零输注风险。风险完全继承底层通道：单次预设现在就能做（走已验证普通大剂量）；组合预设待扩展大剂量取证通过后开放，取证前发送置灰
- wear：预设在手表价值更大（表圈选 chip 快于输数字），列表小，经现有 DataClient 从手机同步，远期

## 执行态：单窗口流式状态机

输入态产出 BolusDraft 点输注后进入。

**取消语义按阶段区分（2026-09-29 补，pumpX2 已核实）——"普通取消"与"中断输注"是两件事：**

| 阶段 | 用户点取消的行为 | 协议指令 |
|------|----------------|---------|
| 等待用户确认（未发权限） | 直接关闭，无警告 | 无 |
| 权限已授予、输注未开始 | 普通取消 | `BolusPermissionReleaseRequest` opCode -16（签名 CONTROL，V2_5） |
| **输注进行中（now 或 extended）** | **弹警告"这将中断大剂量输注，确认？"** → 确认后中断 | `CancelBolusRequest(bolusId)` opCode -96（即 BolusTermination，签名 CONTROL，minApi V2_5，ALL 设备，javadoc 明说 "Works for extended boluses"） |

- 警告对话框与普通取消视觉区分：普通"取消输注"是中性；中断警告是危险确认（error 色确认按钮），文案明确"已输注的胰岛素无法撤回"
- 中断响应 `CancelBolusResponse(-95)`：`wasCancelled()` = status SUCCESS(0) + reason NO_ERROR(0) 即泵已确认终止；失败典型 reason=2 INVALID_OR_ALREADY_DELIVERED（已全部输完，此时转完成结局）
- **结局简化（2026-09-29 决策）：不做已输注剂量显示**。不轮询 LastBolusStatusV2 对账、不展示 delivered/requested——避开枚举 guesswork、opcode 21 无样本、单位换算等全部协议缺口；实际剂量只信泵端输注记录。结局固定两句：
  - **"输注已中止，请查看输注记录"**
  - **"输注已完成，请查看输注记录"**

**延展期间允许叠加普通大剂量（原泵功能，2026-09-29 确认）——决定执行态不能占屏：**
- 延展段持续数小时，流式窗口在**立即段输完、延展段转入后台后即可关闭**，末条消息"扩展大剂量已开始，延展段将在 X 小时内持续输注，可在首页中断"
- Dashboard 增加"扩展大剂量进行中"横幅/卡片：计划总量、剩余时间（ExtendedBolusStatus 轮询，opcode 46/47 或 V2 -74/-73）；**不显示"实时已输量"**——协议无 delivered 字段，不做速率×时间估算展示（避免估算值被当成实测医疗数据），只显示计划值与剩余时间
- **大剂量入口在延展期间保持可用**：用户可再开 BolusFlow 发普通大剂量，泵允许叠加
- **中断按 bolusId 精确指向**：普通大剂量是新 bolusId、延展是原 combo bolusId，`CancelBolusRequest(bolusId)` 不会误伤另一个；Dashboard 横幅上的"中断延展"与导航栏"大剂量"是两个独立动作，各自警告
- **向导避让（阶段 2 依赖项）**：延展未输完的胰岛素属未来 IOB，大剂量向导计算时必须扣减"延展剩余量"，否则重复建议剂量；阶段 1 无向导不涉及

状态机（成功 / 取消 / 失败 三结局；中断归入取消结局，剂量一律不显示）：

```
[等待用户确认] ──普通取消──→ 结局②取消（未发任何指令/已 Release 权限）
  ↓ 确认
请求权限
  ↓
[等待泵权限响应] ──普通取消(-16 释放权限)──→ 结局②取消
  ↓ 权限被拒(nackReason) ──→ 结局③失败（显示原因）
  ↓ 权限授予
发送输注请求
  ↓
[等待泵输注响应] ──普通取消(-16)──→ 结局②取消
  ↓ 泵拒绝(statusType) ──→ 结局③失败（显示原因）
  ↓ 泵接受
泵开始输注
  ├─ 普通大剂量：窗口停留，轮询 CurrentBolusStatus 至结束
  │    ├ 用户取消 → 中断警告 → -96(该 bolusId)
  │    │    ├ wasCancelled → 结局②"输注已中止，请查看输注记录"
  │    │    └ reason=2 已输完 → 结局①"输注已完成，请查看输注记录"
  │    └ 自然完成 → 结局①"输注已完成，请查看输注记录"
  └─ 含延展段：立即段输完 → 提示"延展段将持续 X 小时，可在首页中断"→ 窗口关闭，转 Dashboard 横幅
       （延展期间可从导航栏再发普通大剂量；横幅可中断延展，同样走警告+-96+两句结局）
```

流式界面（类似聊天窗口，消息逐步追加，自动滚动到底）：

```
┌─────────────────────────────────────┐
│  大剂量输注                    [×]  │
├─────────────────────────────────────┤
│  你    请求输注 2.5 单位            │
│  泵    正在确认权限...              │
│  泵    ✓ 权限已确认                  │
│  你    发送输注指令                  │
│  泵    ✓ 已接受，正在输注...         │
│  泵    ✓ 输注完成（2.5 单位）         │
├─────────────────────────────────────┤
│  [取消]                  [完成]     │
└─────────────────────────────────────┘
```

设计要点：
- 消息模型：`sealed class BolusLogMessage`（UserMessage / PumpStatus / PumpSuccess / PumpError）
- 全屏流程页内 `LazyColumn` 显示消息流，自动滚动到底
- 泵警告直接入流：`nackReason` → `PumpError("权限被拒绝：${原因}")`，`statusType` → `PumpError("输注被拒绝：${原因}")`
- 结局只有固定两句话（中止/完成 + 请查看输注记录），**不显示实际剂量、不做 V2 对账**
- 底部按钮随状态变化（确认输注 / 取消输注 / 中断大剂量输注[危险] / 完成 / 确定）；进行中点取消先弹"这将中断大剂量输注，确认？"，不直接发 -96
- BackHandler 语义与取消按钮一致（按阶段：关闭 / 释放权限 / 中断警告），不直接关闭 window
- 替代现有 5 个 boolean + 5 个 AlertDialog

## 数据依赖与实施顺序

| 阶段 | 内容 | 依赖 |
|------|------|------|
| 1 | 全屏流程页 + BolusDraft 模型 + 流式执行态（固定两句结局，中断走 -96 不对账剂量）+ **单次预设**（纯本地无新依赖，可最早做） | 无，X2 普通大剂量已验证 |
| 2 | 大剂量向导：先核实 IDPManager/Profile 能否取**当前生效时段**的碳水系数/目标血糖/ISF（分时段表按泵当前时间落区间），再做折叠计算器；单位 mmol/L↔mg/dL 跟泵设置不写死；若阶段 3 已上线，向导须扣减延展剩余未来 IOB | profile 数据核实 |
| 3 | 扩展大剂量输入区 + 11 参数构造器 + Dashboard "扩展进行中"横幅（计划值/剩余时间，不显示估算已输量）+ 横幅中断延展（-96 原 bolusId）+ 延展期间可叠加普通大剂量；**先只读历史 59/21 取证再试发** + **组合预设**随之开放 | 阶段 1 + 真机取证 |
| 4 | 历史记录区分扩展大剂量（wear 历史屏不再显示裸类名，opcode 20/21/280 解析，此时才依赖 delivered/completionStatus 字段及 21 号抓包补证）、wear 预设同步 | 协议已就绪 |

公式风险备忘（实施时对着 pumpX2 profile 消息逐字段核实，不凭记忆写）：标准公式是**食物 = 碳水 ÷ 碳水系数、矫正 = (BG − 目标) ÷ ISF**（除不是乘；用户口语说"系数×"指配置项含义）。

> **⚠️ 单位与缩放铁律（2026-09-29 用户强调，极重要）**：
> 1. **配置文件（profile）读出的全是原始值，不是显示值**：碳水系数按 **1/100 缩放**（如存 1000 = 10.0 g/U），血糖目标、ISF 同样是缩放整数，使用前必须按 pumpX2 profile 消息定义的比例还原
> 2. **协议原生按美标 mg/dL 存储血糖类数值**，不是 App 看到的 mmol/L
> 3. **地区/固件差异不可假设**：同型号泵销往不同地区、不同固件版本，读出来可能是 mmol 而非预期的 mg/dL。绝不能写死"读出值 ÷ 某常数 = mmol"；必须先查询泵的单位设置（units 消息），在同一单位体系内计算，只在显示层换算
> 4. 实施向导前，先写一轮 profile/单位消息的真机抓包取证（型号+固件版本+原始 cargo+解码值+泵屏显值三方对照），确认缩放比例与单位后再写公式；单元测试用真机抓包样本，不用臆造数据

触碰文件：BolusWindow.kt + BolusDialogs.kt（执行态）、Landing.kt（入口承载）、新增输入态/预设/向导 composable；预设新增 Room 表。
