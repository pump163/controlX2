# 通知查询归查询器 — 施工方案

> 状态：**方案 / 未写代码**。照此施工。
> 参考：`查询层收敛-设计.md`（§3.3 调用形态、§3.5 策略表、§3.7 登记表、§4.1 落地形态、§4.4.3 接入点表、§6 订阅制、§8.2 并入）、`通知页-流水账-设计.md`（§0 硬前提 1、§3 数据来源、§5 刷新归属）。
> 范围：把「通知类 7 条请求」的**发送决策**从页面 `LaunchedEffect` 收归查询器。不改渲染、不改消除、不改角标口径、不改写路径。

---

## 0. 一句话

通知页不再自己发查询：**页面只订阅 `PumpTopic.NOTIFICATIONS`，发不发、什么时候发由查询器按策略 + 订阅者年龄决定**；同时把 Dashboard 批里的 7 条通知请求移出，避免双份。

---

## 1. 现状（as-is）

```
Notifications.kt:140-142   LaunchedEffect(60s)
  → sendPumpCommands(STANDARD, notificationsCommands)
       = [HomeScreenMirrorRequest] + NotificationBundle.allRequests()   ← 7 条
  → CommService → PumpCommHandler.command()      ← noteLegacyRequest(NOTIFICATIONS)
  → 泵
  → AlertStatusResponse / AlarmStatusResponse / ... → DataStore.notificationBundle
  → NotificationBundle.get() → notifications 列表 → NotificationItem 渲染
```

同时 Dashboard：

```
Dashboard.kt:146-149   LaunchedEffect(60s) → dashboardCommands（18 条）
  = dashboardCommands(11) + 通知类(7)        ← 与通知页重复
```

**三个问题**：

1. **双份**：同一批 7 条通知请求，首页可见时每 60s 发两次（Dashboard 一次 + 通知页一次）。§3.7 L282 已把 #4（通知页）列为「与 #1 高度重叠」。
2. **决策散落**：发送时机由页面 `LaunchedEffect` 决定，查询器无法合并/去重/预算。
3. **切页冻结**：X2 切到流水账页后 `Notifications.kt` 不再组合 → ticker 停 → 报警区冻结（流水账设计 §5「刷新归属」已指出）。

## 2. 目标（to-be）

```
角标/Landing ──subscribe(NOTIFICATIONS, maxAge=60s, P1_STATE)──┐
通知页（报警面板 / 流水账）──subscribe(NOTIFICATIONS, 60s, P1）──┤ 合并取最严格
                                                              ↓
                     PumpQueryService（shared，纯逻辑调度）
                     年龄 = now - lastRxAt[NOTIFICATIONS]
                     策略 = pump-query-policy.json 的 NOTIFICATIONS
                     硬闸：连接态 → 静默 → 预算 → 合并/单飞
                                                              ↓ 该发
                     PumpCommandPortImpl（pumpcomm）
                     topic → List<Message> 映射 + 既有 command() 发送
                                                              ↓ 响应（既有路径）
                     DataStore.notificationBundle（写入方不变）
                     + lastRxAt[NOTIFICATIONS] 更新
```

事件路径：

```
泵推 [ALERT] → PumpCommHandler.onReceiveQualifyingEvent
  → queryService.onPumpEvent(events, bitmask, atMillis)
  → scheduler 把 NOTIFICATIONS 的年龄门槛置 0（仍需订阅者 + 连接态 + 预算）
```

## 3. 关键设计决策

### 3.1 通知批 = 一个 topic，不是 7 个

`NOTIFICATIONS` 代表**整组 7 条请求**，一起发、一起算年龄。
理由：`NotificationBundle.get()` 需要 7 条才能产出完整 5 类条目；单条响应没有独立语义。

### 3.2 topic → 请求集的映射放 pumpcomm，不放 shared

§4.1.2 明确 shared 不得依赖 pumpx2。所以：

| 层 | 职责 |
|---|---|
| `shared` | `PumpTopic` + `PumpQueryService`（订阅表、年龄、合并、单飞、预算、硬闸）——**只看 topic，不认请求类** |
| `pumpcomm` | `PumpCommandPortImpl`：持有 `topic → List<Message>`；NOTIFICATIONS → `NotificationBundle.allRequests().toList()`；用既有 `PumpCommHandler.command()` 发送 |
| `mobile` | 组装 + 生命周期（跟随 `CommService`） |

### 3.3 响应聚合复用既有路径，不新建 adapter

现有 `PumpCommHandler` → `DataStore.notificationBundle` 的写入**一行不改**；查询器只需在收到响应时更新 `lastRxAt[NOTIFICATIONS]`。

- 复用已有的 `PumpQueryService.noteLegacyReply(topic, opCode)`（桩里已有）更新年龄。
- 好处：`NotificationBundle` 合并逻辑、`DataStore` 写入、`CartridgeActions` 读取、角标读取**全部不动**。

### 3.4 角标需要常驻订阅者

角标（`Landing.kt:631` `notificationBundle.get().count()`）是硬职责；X2 上报警只能看不能消 → 角标必须始终新鲜。

`NOTIFICATIONS` 策略是 `onlyWhenVisible: true`，所以：

> **决定：`Landing`（或角标本体）常驻订阅 `NOTIFICATIONS`**，保证永远有订阅者；报警面板 / 流水账页再各自订阅（合并取最严格 maxAge）。

效果：`onlyWhenVisible` 语义不变（永远有一个可见订阅者），角标不再依赖「通知页是否打开」。

### 3.5 事件只当输入信号

`onPumpEvent` **不直接发请求**；只把对应 topic 的年龄门槛置 0，仍走「有订阅者 + 连接态 + 预算」检查（§4.1.7）。

**已知缺口**：策略 JSON 的 `events.ALERT_CHANGE` 与泵实推 `ALERT` 不匹配（已裁决暂不动）→ 事件驱动这条**暂时不生效**，靠 60s 轮询兜底。本轮不改键名。

### 3.6 tick 来源

查询器需要一个时间基准。**不新增线程**：在 `CommService` 既有 Handler 上挂一个 `postDelayed` 自续循环，间隔取所有 topic 的 `min(intervalMs)`；每次 tick 检查全部订阅 topic 的年龄。页面进入/退出只改订阅表，不改定时器。

## 5. 开关与回滚

- `pumppan-query-engine`（默认 **false = LEGACY**），一个总闸不分域（§4.4.4）。
- **LEGACY**：`Notifications.kt` 的 `LaunchedEffect` 保留原样；查询器不参与发送。
- **V2**：`LaunchedEffect` 换成订阅；查询器接管。
- **切换时必须先 cancel 旧定时器**（否则首分钟双份请求）。
- `/api/query/stats` 增 `engine: LEGACY|V2`（observed）+ `switch: {configured, observed}`；V2 下 `noteLegacyRequest` 仍涨 → `SWITCH_MISMATCH` 告警。
- **回滚**：开关切回 LEGACY，行为回到现状。

---

## 6. 与流水账页的关系

- 流水账页的报警区**订阅同一 `NOTIFICATIONS`**，数据源仍是 `DataStore.notificationBundle`。
- 刷新归查询器 → 不依赖 `Notifications.kt` 是否被组合 → 解决「切到 LEDGER 后报警区冻结」（流水账设计 §5）。
- 流水账页**不自己发任何请求**（流水账设计 §0 硬前提 1）。

---

## 7. Mobi 保护

- `Notifications.kt` 的**渲染、消除、`canDismissNotifications` 一行不改**。
- `NotificationItem.kt` 一行不改。
- 变化只在「数据怎么来」：页面自己发 → 查询器按策略发。
- 写路径（`DismissNotificationRequest`）完全不动 → **Mobi 真机消除不受影响**。
- 验证：Mobi 上通知消除仍工作。

## 8. 风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| 角标不新鲜 | 报警漏看 | §3.4 常驻订阅 |
| 切换期双发 | 请求翻倍、预算超 | 先 cancel 旧定时器；stats 观测 |
| 7 条只回来部分 | `NotificationBundle` 不完整 | 复用既有「按已到响应合并」逻辑；缺的那条等下一轮 |
| 事件键不匹配 | 事件驱动刷新不生效 | 已知；60s 轮询兜底；本轮不改键名 |
| 查询器发送失败 | 通知页空白 | 订阅者收 `Stale`/`Unavailable`，页面显示「可能不全」 |

---

## 9. 验收

1. **回归（已通过判据）**：泵推报警 → 手机报警区出现；泵上取消 → 手机同步消失。
2. **不双发**：`GET /api/query/stats` 的 `NOTIFICATIONS` 计数 ≈ 每 60s 一组（7 条），不因 Dashboard + 通知页各发一份而翻倍。
3. **角标**：停留在 Dashboard 时角标仍随报警变化。
4. **切页不停**：X2 切到流水账页后，报警区仍随泵状态更新。
5. **回滚**：开关切回 LEGACY，`Notifications.kt` 的 60s 刷新恢复，行为回到现状。
6. **Mobi**：真机消除仍工作。

---

## 10. 明确不做

- 不改 `NotificationItem.kt` / `Notifications.kt` 的渲染与消除。
- 不改角标口径（仍只读 `NotificationBundle`）。
- 不改事件键名（`ALERT_CHANGE` vs `ALERT`）。
- 不给流水账页加任何独立查询。
- 不动 `wear/`。
- 不让查询器写 `DataStore`、不落盘。
