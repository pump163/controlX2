# 查询层收敛设计（BLE 指令预算）

> 状态：设计稿（2026-11-08）。**只写文档，未改代码、未出包、未 push。**
> 范围：`mobile` / `pumpcomm` 里所有会向泵发指令或轮询的位置，以及横幅（#64）以后新增状态需求的接入方式。
> 不在范围：BLE 库、重连策略、PumpX2 报文定义。

---

## 0. 一句话结论

现在的问题不是「某一条查询写错了」，而是**每个功能各自带一条定时器**：周期任务 5 分钟、首页/各分区 60 秒、旧通知 1 秒×60、v2 立即 10 秒、延展 5 分钟、向导进页面再查一次、历史回补 500ms 突发。功能越多，BLE 链路上并行的请求越多；弱信号下这些请求还会互相挤占、拖长单次往返，反过来放大断连。

收敛方向：**功能只声明「要哪类状态、能忍多久」，由统一调度器合并、去重、单飞、按优先级降级**；定时器不再负责「催数据」，只负责「承认数据已旧」。

---

## 1. 设计原则：数据年龄是一等公民

泵是黑箱，链路不保证时刻通。可信度只能锚在**最后一次真实收到**的本地时刻，不能锚在「我刚发过查询」。

### 1.1 每个对外提供的泵状态字段都带 `lastRxAt`

- 泵报文（`Message`）头没有可信时间戳，时效只能用**本地接收时刻**。这一点在 IOB 采样里已被证实：同一个 `iobUnits` 字段，断连时值不变、年龄一直在涨，界面却完全看不出来。
- 因此 `DataStore` 里对外提供的每个泵状态字段，都应带一个**本地接收时刻**（`lastRxAt`），而不是只有值：

```kotlin
// 目标形态（示意）
data class PumpReading<T>(
    val value: T,
    val lastRxAtMillis: Long,   // 本地时间；收到报文的那一刻
    val source: ReadingSource,  // PUMP / CACHE / DERIVED
)
```

- 过渡期可以沿用现在的 `xxxUpdatedAtMillis` 旁挂字段（IOB 已经这么做了：`iobUnits` + `iobUpdatedAtMillis`），但新字段一律按上面的形态加。
- 界面必须能拿到年龄：`N 秒前 / N 分钟前`。没有年龄的字段，不许出现在「看起来是实时」的位置。

### 1.2 定时器的角色翻转

- **旧角色**：定时器到点就发请求，默认「发了 = 新了」。
- **新角色**：定时器只做两件事 —— ① 让 UI 承认数据已旧（刷新年龄文案、把状态降级）；② 通知调度器「有消费者在等、且数据超过容忍度」。
- **催不来就降级展示，不得制造新鲜感**。请求失败 / 超时不是错误弹窗，而是把该字段切到「最后已知 + 年龄」并标明来源。

### 1.3 断连时不清零、不装实时

- **不清零**：保留最后已知值。清零会让用户以为「泵上现在就是 0」。
- **不装实时**：不能继续按固定节奏重绘成正常状态；必须显示「已断开 / 最后更新 N 分钟前」。
- 理由：**一个标了「12 分钟前」的旧值，比伪装成实时的旧值安全**。用户能做决策的前提是知道自己在看旧数据。
- 同理，断连恢复后不能把缓存值直接当新值广播；首个真实读数到达前，一律按「年龄未知/偏旧」处理。

### 1.4 和 IOB 那件事的关系

IOB 的病根**不是值错，而是字段没有年龄**：

- `/api/pump/current.iobUnits` 只跟 `ControlIQIOBResponse` 更新，断连整块冻结（实测 23.9 分钟；恢复后首个新值低 1.80 U）。
- 泵本身每次被真查询都给随时间推进的新值（60 秒间隔中位数 −94 mU），所以「泵在算」这件事成立。
- 真正的缺陷是：这个字段只存了值，没存「最后一次真实收到」的时刻，于是界面无法区分实时/缓存，向导也无法判断能不能扣。
- 修法不是「多查几次」，而是**给字段补年龄 + 消费方按年龄决策**：向导先真查一次，查不到才看 ≤3 分钟的缓存；首页继续显示旧值，但必须标年龄（当前实现仍不标，记为疑点，暂不改）。

这条原则适用于所有泵状态，不只 IOB。

## 3. 推送 vs 轮询（实测优先）

### 3.1 实测数据

- 数据源：工作区外取证目录 `_tmp_pumpx2/messages_20261108.jsonl`，**1685 条**泵报文，覆盖 **12:42–15:55（3h12m）**，被动记录 App 实际收到的报文（不含 App 发出的请求）。
- 典型计数（opCode / 报文 / 条数）：

| opCode | 报文 | 条数 | 说明 |
|---|---|---|---|
| -127 | `HistoryLogStreamResponse` | 203 | 历史日志**流式**返回，由 `HistoryLogRequest` 触发 |
| 59 | `HistoryLogStatusResponse` | 115 | 周期性/按需查询 |

| -91 | `LastBolusStatusV2Response` | 33 | 最近一笔大剂量 |

### 3.2 能得出的结论（实测）

- **没有任何证据表明 `45` / `47` / `-91` 会被泵主动推送。** 它们在数据里总是**成簇出现**：同一秒级窗口里 `45 → 47 → -73 → -91` 依次到达（例：`13:05:02–13:05:05`、`14:14:01–14:14:05`），形态与「一次批量查询的连续应答」一致，而不是各个字段独立、按自身节奏推送。
- 3U 方波运行期间（`14:09:32–14:25:39`）存在 **5 分钟空窗**（`14:19:32 → 14:24:31`）：这 5 分钟里**其他报文共 116 条**（含 `LastBolusStatusResponse`、`ControlIQIOBResponse`、`HomeScreenMirrorResponse` 等）仍在正常应答，但 `45` / `47` / `-91` **一条都没有**。如果是状态变化推送，不会出现这种「其他状态照常、唯独输注状态沉默」的空窗。
- **唯一真正「流式」的是 `HistoryLogStreamResponse`（-127）**，但它由请求触发（`HistoryLogRequest` 发起后泵连续返回），不是无条件主动推。
- 泵上发起的大剂量（方波 6874）在 App 侧 `45` 里始终是 `bolusId = 0`（没有立即段），延展信息只在 `47` / `-73` 里 —— 说明**只看 `45` 会漏掉延展**，这也是 IOB 否决必须读 `47` 的原因。

### 3.3 推断（未证实，不得当依据）

- 有资料/经验认为 `45`、`47` 在 BLE 通知特征上可能被动上报；**本次采样不支持这个说法**，至少在当前连接方式下没有观察到。要证实需要一次「全程不查询、只记录」的采样（见 §9）。
- 因此下面所有策略都按**「这些状态必须主动问」**设计。若将来证实某类确实会推，再把该类从「轮询」搬到「该来没来才补」，而不是提前假设。

### 3.4 「该来没来才补」的适用范围与静默阈值

- 适用前提：**该类状态已被证实会主动推**（目前只有「历史流」是请求触发的流，不是主动推）。
- 对必须主动问的状态，改成**按年龄调度**：只有当「有订阅者」且「当前年龄 > 该订阅者容忍度」时才发；发一次后进入单飞等待，超时才算失败并降级。
- 建议静默判定阈值（从现状与安全需求推导，标 **建议**）：

| 状态 | 建议容忍度（最严格消费者） | 静默判定 | 依据 |
|---|---|---|---|
| `45` 立即段 / 确认中 | **10 秒** | 发出后 10 秒无应答 → 判失败、降级 | 与 `BolusPollScheduler.requestTimeoutMs = 10 s` 一致 |
| `47` / `-73` 延展运行中 | **5 分钟** | 发出后 10 秒无应答 → 判失败；下一次兜底 5 分钟 | 现有 `extendedPollIntervalMs = 300000`；延展本身按 5 分钟记账 |
| `47` 延展「预期该结束」窗口 | 10 秒 | 到 `expectedEndAt` 后 10 秒一次，最多 3 次 | 结束时刻需要较快确认 |
| `45` 空闲期（无会话） | 5 分钟 | 无应答不重试，等下一轮 | 空闲期只为首页状态 |
| `-91` / `48` 最近一笔 | 5 分钟 | 同上 | 只用于「最近输注」判定 |
| `109` IOB | 后台 5 分钟 / 向导 3 分钟可用 | 发出后 10 秒无应答 → 本次不可用 | 已定稿：查询优先，缓存 ≤3 分钟 |
| `59` 历史状态 / `-127` 流 | 回补期 10 秒 | 500ms 本地轮询改为「有进展才继续」 | 低优先级，可暂停 |

## 4. 订阅制形态

### 4.1 目标接口（草案）

```kotlin
enum class PumpTopic { IOB, BOLUS_CURRENT, BOLUS_EXTENDED, LAST_BOLUS, BATTERY, BASAL, CGM, ALERTS, HISTORY_STATUS }

enum class QueryPriority { P0_CONFIRM, P1_STATE, P2_DECORATION }

data class PumpSubscription(
    val topic: PumpTopic,
    val maxAgeMillis: Long,        // 该功能能忍多久
    val priority: QueryPriority,
    val onReading: (PumpReading<*>) -> Unit,
)

interface PumpStateBus {
    /** 订阅；返回取消句柄。重复订阅同一 topic 由调度器合并。 */
    fun subscribe(sub: PumpSubscription): Cancellable

    /** 只读快照：值 + lastRxAt + 来源。UI 用它渲染年龄/降级。 */
    fun reading(topic: PumpTopic): PumpReading<*>?

    /** 断连/恢复由 BLE 层回调；不在这里发请求。 */
    fun onConnectionChanged(connected: Boolean)

    /** 诊断：最近 N 秒真实发出的请求数与合并/丢弃数。 */
    fun stats(): QueryStats
}
```

调度规则：

1. **合并**：同一 `topic` 的多个订阅取**最严格的 `maxAgeMillis`**，只发一次。
2. **去重**：`now - lastRxAt < min(maxAge)` 时**不发**，直接把现有 `reading` 回调给订阅者（带 age）。
3. **单飞**：同一 `opCode` 同时只允许一个请求在飞；超时才允许重发（沿用 `BolusPollScheduler` 的做法）。
4. **优先级**：发送队列按 `QueryPriority` 排序；P0 可以抢占，P2 在预算不足时直接推迟。
5. **降级**：请求失败 / 超时 / 断连 → 回调「最后已知 + age + 不可信原因」，由订阅者决定文案；**不在调度器里重试轰炸**。

### 4.2 需求表

| 需求 | 要哪类状态 | 最严格新鲜度 | 可用来源 | 能否降级 |
|---|---|---|---|---|
| 首页 IOB | `IOB`（`ControlIQIOBResponse`） | 视图刷新 ≤ **3 分钟**（超过不采信） | 本次查询 / 缓存（带 age） | 可：标「缓存 · N 分钟前」或「本次不可用」 |
| 横幅「正在输注什么」(#64) | `BOLUS_CURRENT` + `BOLUS_EXTENDED` + `LAST_BOLUS` | 输注中 ≤ **10 秒**；空闲 ≤ **5 分钟** | 泵真相层 `45` / `47` / `-73` / `-91` | 可：最后已知 + age；不确定时写「状态未知」 |
| 立即确认（发起/取消大剂量） | `BOLUS_CURRENT` | ≤ **10 秒**，发出后 10 秒无应答即失败 | `45` | **不可降级**：拿不到证据就不许报「成功/已取消」 |
| 延展输注 | `BOLUS_EXTENDED` | 运行中 ≤ **5 分钟**；结束窗口 ≤ **10 秒** | `47` / `-73` | 可：最后已知 + age；不得显示「未在输注」冒充 |
| 向导（一次性） | `IOB` + 泵参数 + CGM + `BOLUS_*` | 按下「计算」时必须**本次查询** | `ControlIQIOBRequest` + `BolusCalcDataSnapshotRequest` + `CurrentEGVGuiDataRequest` + `45` + `47` | 可：IOB 缓存 ≤3 分钟；输注证据不新鲜则本次不扣 |
| 历史回补 | `HISTORY_STATUS` | ≤ **10 秒**（仅回补期） | `59` / `-127` | 可：随时暂停，恢复后继续；绝不与 P0/P1 抢预算 |

## 5. 预算与优先级

### 5.1 降级顺序（用户确认口径）

**确认 / 取消（P0） > 状态类（P1） > 装饰类（P2）**

- P0：立即确认、取消、权限应答。**永不排队等待**，预算不足时抢占 P1/P2。
- P1：`45` / `47` / `-91` / IOB / 告警状态 / 基础率。允许 1 个轮次的延迟。
- P2：电池、CGM 图表刷新、历史回补、诊断面板、装饰性倒计时。可无限期推迟，断连时直接显示「暂停」。

### 5.2 硬闸（建议：先观测，再启用）

- 建议设**每分钟报文上限**：持续 **10 条/分钟**、突发 **20 条/分钟**（Bulk 请求按「1 次发送、N 条应答」计为 1 次发送）。
  - 依据：当前最坏组合（Dashboard 8 条 × 60 秒 + 旧通知 1 条/秒×60 + 周期 4 条/5 分钟 + 延展 1 条/5 分钟）在确认窗口内可轻易超过 60 条/分钟；而 BLE 往返在弱信号下会到秒级，10 条/分钟是保守上限。**该数值是工程推测，需用 `DiagScreen` 的「近 10 秒查询次数」观测校准后再定。**
- 硬闸的落点：**调度器发送前**统一计数；超限时 P2 直接丢弃（记诊断），P1 延后一个轮次，P0 仍然放行并记录「预算超限下的 P0」。
- 硬闸必须带**诊断计数**（合并次数 / 去重命中 / 丢弃次数），否则无法复查是否真的省下了请求。

## 6. 与现有代码的关系与迁移

### 6.1 保留

- `BolusPollScheduler`（`BolusPollScheduler.kt`）：单飞、超时、10 秒去重已经正确，**直接改造成 `BOLUS_CURRENT` / `BOLUS_EXTENDED` 两个订阅的内部实现**，不要重写。
- 向导的一次性查询（`BolusWizardTab.kt:125-145`）：保持「用户触发 + 强制查询」，只是把发送入口换成 `PumpStateBus.requestNow(topic, P0)`。
- `PumpCommHandler.CacheSeconds = 30` 的新近度判断：升级为调度器的「去重」依据，不再区分 `CACHED` / `STANDARD` 两条路径。

### 6.2 并入（按顺序）

1. **旧通知 1 秒×60**（`BolusNotificationBroadcastReceiver.kt:570-584`）→ 订阅 `BOLUS_CURRENT`（确认期 10 秒），满足即停；legacy 与 v2 共用同一订阅，删除固定 60 次窗口。
2. **各页面 60 秒刷新**（`Dashboard.kt:146`、`Notifications.kt:140`、`Actions.kt:214` 等 7 处）→ 订阅各自 topic，按「数据年龄 > 容忍度」才发；页面可见只影响「是否渲染年龄」，不再直接决定发送。
3. **周期任务 5 分钟**（`CommService.kt:165-186`）→ 改为对 `BATTERY` / `HISTORY_STATUS` 的低频订阅 + 全局年龄兜底；`ControlIQIOBRequest` 从周期任务移除（向导/首页各自订阅）。
4. **历史回补**（`HistoryLogFetcher.kt` + `HistoryLogSyncWorker.kt`）→ 挂到 P2 预算，回补期 500ms 轮询改为「有新增才继续」，断连即暂停。
5. **Dashboard 初始 250ms 补齐循环**（`Dashboard.kt:108-123`）→ 改为等待各 topic 的首个 `lastRxAt`，到齐即停，不设固定次数。

### 6.3 迁移可分步

- **A 步（只加观测，不改行为）**：`DataStore` 关键字段补 `lastRxAt`；`DiagScreen` 展示每 topic 的年龄与近 1 分钟请求数；页面先把年龄显示出来。
- **B 步（只改「何时发」）**：引入 `PumpStateBus`，先接管旧通知 1 秒×60 与 7 处 60 秒刷新；周期任务保持原样做兜底。
- **C 步（收编周期任务与历史）**：周期任务改为订阅；历史回补进 P2 预算；启用硬闸（先告警模式，再拦截）。

每一步都可独立回滚；A 步不改变任何发送行为，风险最低。

### 6.4 轮次收尾定义（先写死，避免「差不多完成了」）

- **B 轮（发送态）收尾 = 四段全通**：向导能算 → 用户可改写 → 确认页 → 真的把 `-98` 发到泵；并由真机实际打一笔、核对泵侧记录与回执，才算 B 轮收尾。缺任何一段（尤其「真机打一笔」）都只能算「能算不能发」。
- **C 轮开工第一件事 = 「只收不发」实验**：先关掉全部主动查询（向导查询、页面刷新、周期任务、历史回补一并停），只记录收到的报文与时间戳，验证输注状态类报文（`45` / `47` / `-91` 等）在没有主动请求时是否会自己到来。
  - 结论直接决定横幅 / 输注状态观测层能否按「推送优先」设计：若确认自发推送，按 §3.4「该来没来才补」；若确认为纯请求-响应，则该层必须保留主动查询，只做去重与年龄调度。
  - 实验期间不启用硬闸、不改 BLE 库；只观测并留证，把 §9 的对应项从推断升级为实测。

## 7. 复查机制（必须随推进定期复查）

这套整理不是一次做完就完事。用户明确要求：**随着功能推进定期复查**。

### 7.1 触发点（准入规则）

- **任何新功能若需要泵状态，必须先在 §4.2 需求表里占一行**：要哪类状态、最严格新鲜度、能否靠推送满足、可否降级。
- **没有这一行，不许新增定时器、不许新增 `postDelayed` / `LaunchedEffect(intervalOf(...))` / 固定次数重试**。
- 新增订阅必须声明 `PumpTopic` + `maxAgeMillis` + `QueryPriority`；能复用已有 topic 的，禁止另开。

### 7.2 节奏

- 按迁移 **A / B / C 每轮收尾时复查一次查询清单**（§2.1 表）。
- 复查问法是「**这条现在还必要吗**」，不是「这条有没有坏」。
- 复查产出：删除 / 合并 / 降级 / 保留 四选一，并更新 §2.1 与 §4.2；没有结论的条目要写明「暂留原因」。

### 7.3 判定口径

- **以推送为准**：只有实测证实的主动推送才允许「该来没来才补」；未证实的，一律按必须主动问处理。
- **只在「该来没来」时补查询**：先看 `lastRxAt`，再看容忍度；不满足就不发。
- **弱信号下降级顺序**：确认/取消 > 状态类 > 装饰类；P2 可静默暂停，P1 可延后一轮，P0 不降级。
- **复查时同时看预算诊断**：合并率、去重命中率、丢弃次数。如果某项功能让 P0 开始排队，直接判为设计错误。

## 8. 不做什么

- **不改 BLE 库**（`pumpx2-android` / `TandemBluetoothHandler`）与连接参数。
- **不改重连策略**（断连判定、退避、配对流程保持现状）。
- **不改泵报文定义**、不新增 opCode 解析。
- **不为了减少请求而自己推算泵状态**（例如按时间外推 IOB）；宁可用带年龄的旧值。
- **不用「多发几次」掩盖「没有年龄」**：先补 `lastRxAt`，再谈调度。

## 9. 证据等级与待验证

### 有实测支撑

- `45` / `47` / `-91` 在 3h12m、1685 条被动报文里**没有独立周期出现的证据**，总是成簇（同一秒级窗口 4 条依次到达，例：`13:05:02–13:05:06`、`14:14:01–14:14:05`）。
- 延展运行期间存在 **5 分钟空窗**（14:19:32 → 14:24:31），期间其他报文 116 条正常应答，`45` / `47` / `-91` 为 0。
- `-127 HistoryLogStreamResponse` 是请求触发的流式返回（203 条）。
- 泵上发起的大剂量，`45` 的 `bolusId = 0`，延展只在 `47` / `-73` 可见。
- IOB 字段断连冻结 23.9 分钟、恢复后新值低 1.80 U；用 `iobUpdatedAtMillis` 才能表达年龄。

### 属于推测 / 待验证

- 「`45` / `47` 会被主动推送」——**未证实**；需要一次「全程不查询、只记录」的采样（至少覆盖一笔立即段 + 一笔延展）。
- 每分钟 10 条持续 / 20 条突发的预算上限——工程推测，需用诊断计数校准。
- 各页面 60 秒是否真的都需要——需按 §7.2 逐条复查（尤其 Dashboard 8 条 Bulk 是否可拆成不同容忍度）。
- 「延展结束窗口 10 秒」是否够快——需实测结束时刻的 `47` 应答延迟。
