## 0. 一句话结论

现在的问题不是「某一条查询写错了」，而是**每个功能各自带一条定时器**：周期任务 5 分钟、首页/各分区 60 秒、旧通知 1 秒×60、v2 立即 10 秒、延展 5 分钟、向导进页面再查一次、历史回补 500ms 突发。功能越多，BLE 链路上并行的请求越多；弱信号下这些请求还会互相挤占、拖长单次往返，反过来放大断连。

收敛方向：**功能只声明「要哪类状态、能忍多久」，由统一调度器合并、去重、单飞、按优先级降级**；定时器不再负责「催数据」，只负责「承认数据已旧」。

## 1. 设计原则：数据年龄是一等公民

泵是黑箱，链路不保证时刻通。可信度只能锚在**最后一次真实收到**的本地时刻，不能锚在「我刚发过查询」。

### 1.1 每个对外提供的泵状态字段都带 `lastRxAt`

- 泵报文（`Message`）头没有可信时间戳，时效只能用**本地接收时刻**。这一点在 IOB 采样里已被证实：同一个 `iobUnits` 字段，断连时值不变、年龄一直在涨，界面却完全看不出来。
- 因此 `DataStore` 里对外提供的每个泵状态字段，都应带一个**本地接收时刻**（`lastRxAt`），而不是只有值：

```kotlin
// 目标形态（示意）
data class PumpReading<T>(
    val value: T,
    val lastRxAtMillis: Long,   // 本地时间；收到报文的那一刻
    val source: ReadingSource,  // PUMP / CACHE / DERIVED
)
```

- 过渡期可以沿用现在的 `xxxUpdatedAtMillis` 旁挂字段（IOB 已经这么做了：`iobUnits` + `iobUpdatedAtMillis`），但新字段一律按上面的形态加。
- 界面必须能拿到年龄：`N 秒前 / N 分钟前`。没有年龄的字段，不许出现在「看起来是实时」的位置。

### 1.2 定时器的角色翻转

- **旧角色**：定时器到点就发请求，默认「发了 = 新了」。
- **新角色**：定时器只做两件事 —— ① 让 UI 承认数据已旧（刷新年龄文案、把状态降级）；② 通知调度器「有消费者在等、且数据超过容忍度」。
- **催不来就降级展示，不得制造新鲜感**。请求失败 / 超时不是错误弹窗，而是把该字段切到「最后已知 + 年龄」并标明来源。

### 1.3 断连时不清零、不装实时

- **不清零**：保留最后已知值。清零会让用户以为「泵上现在就是 0」。
- **不装实时**：不能继续按固定节奏重绘成正常状态；必须显示「已断开 / 最后更新 N 分钟前」。
- 理由：**一个标了「12 分钟前」的旧值，比伪装成实时的旧值安全**。用户能做决策的前提是知道自己在看旧数据。
- 同理，断连恢复后不能把缓存值直接当新值广播；首个真实读数到达前，一律按「年龄未知/偏旧」处理。

### 1.4 和 IOB 那件事的关系

IOB 的病根**不是值错，而是字段没有年龄**：

- `/api/pump/current.iobUnits` 只跟 `ControlIQIOBResponse` 更新，断连整块冻结（实测 23.9 分钟；恢复后首个新值低 1.80 U）。
- 泵本身每次被真查询都给随时间推进的新值（60 秒间隔中位数 −94 mU），所以「泵在算」这件事成立。
- 真正的缺陷是：这个字段只存了值，没存「最后一次真实收到」的时刻，于是界面无法区分实时/缓存，向导也无法判断能不能扣。
- 修法不是「多查几次」，而是**给字段补年龄 + 消费方按年龄决策**：向导先真查一次，查不到才看 ≤3 分钟的缓存；首页继续显示旧值，但必须标年龄（当前实现仍不标，记为疑点，暂不改）。

这条原则适用于所有泵状态，不只 IOB。

## 3. 统一查询器（QueryService）

> 本节把 §2 的清点收成一个**可落地的模块边界**：所有「向泵要数据」的行为只能经过查询器，模块不再自己发请求。
> 与 §6「订阅制形态」、§7「预算与优先级」是同一件事的三个面：§6 定接口，§7 定降级与预算，本节定**职责、状态维度和归属**。

### 3.1 问题定义

- §2.1 列的 17 个发起方，各自带定时器、各自判断断连、各自决定缓存；同一时刻可能有三路在问同一个字段。
- 结果是：**请求量不可预算、新鲜度不可解释、断连时仍在发**。
- 查询器要解决的只有一句话：**「什么时候、向泵问什么、问多密」只能有一处知道答案。**

### 3.2 职责边界

**管：**

| 职责 | 说明 |
|---|---|
| 何时问 | 由「订阅者 + 数据年龄 + 优先级」决定，不由页面定时器直接决定 |
| 问几条 | 同 topic 合并；已在飞的不重复发；一次能批量就批量（Bulk 算 1 次发送、N 条应答） |
| 问多密 | 全局预算与硬闸（§7.2），超限时按优先级推迟/丢弃 |
| 缓存多久 | 每个 topic 的 `maxAgeMillis`；命中即回放，不发请求 |
| 谁能订阅 | 只有登记过的 `PumpTopic`；新增 topic 需在 §6.2 需求表占一行 |
| 断连/静默怎么降级 | 断开即挂起全部非 P0；`LINK_SILENT` 时只允许探活与 P0；恢复后先标「年龄未知」 |

**不管：**

- **不做业务判断**：能不能扣 IOB、能不能发起大剂量、警告文案是否该出现 —— 仍由向导/确认层/UI 决定。
- **不做呈现**：文案、颜色、图表、倒计时都是 UI 的事。
- **不持有 UI 状态**：页面可见性只是**输入信号**，查询器不保存「当前在哪个页面」。
- **不解析报文**：报文的编码/解码仍归 PumpX2。
- **不管重连**：断连判定、退避、配对仍归 BLE 层；查询器只接收「连上/断开/静默」通知。

### 3.3 调用形态：要「数据」，不要「发请求」

**为什么这是解耦的关键**：只要调用方还能「发请求」，它就会顺带决定时机、频率、要不要重试——这三件事又散回各个模块。改成「要一份带年龄的数据」后，调用方只能表达两件事：**我要什么**（topic）、**我能忍多久**（`maxAgeMillis`）。发不发、发几条、什么时候发，全部留在查询器里。

**两种形态：**

| 形态 | 语义 | 典型场景 |
|---|---|---|
| 订阅式 | 「我在意 X，有新值时给我」 | 首页、通知页、横幅、诊断面板 |
| 一次性 | 「我现在就要，允许等待」 | 向导「计算」、确认前核对、取消前核对 |

```kotlin
// 示意：模块侧只表达「要什么 + 能忍多久」
val handle = queryService.subscribe(
    topic = PumpTopic.IOB,
    maxAgeMillis = 3 * 60_000,
    priority = QueryPriority.P1_STATE,
) { reading -> renderIob(reading.value, reading.lastRxAtMillis) }

// 一次性：允许等待；超时返回 last-known + age，而不是抛异常
val reading = queryService.await(
    topic = PumpTopic.BOLUS_CURRENT,
    maxAgeMillis = 10_000,
    priority = QueryPriority.P0_CONFIRM,
)
```

**唯一例外（直发）：**

- 适用范围：**必须立刻拿到单一结果**的动作，例如「一次确认」「一次取消前的状态核对」。这类调用不能被合并、不能被推迟。
- 但**必须登记**：直发走 `queryService.requestDirect(topic, reason)`，仍然计入同一个预算统计与诊断计数。
- 直发**不允许**成为绕过年龄判断的暗渠：直发也要返回 `PumpReading`（带 `lastRxAt`），也要写「本次直发原因」。

### 3.4 状态维度（决定策略的输入）

| 维度 | 取值 | 来源 | 影响 |
|---|---|---|---|
| 连接态 | `DISCONNECTED` / `CONNECTING` / `CONNECTED` / `LINK_SILENT` | `DiagMonitor.kt:491-492`（`connected && lastRxAgo ≤ 30 s` 为 `LINK_ALIVE`，否则 `LINK_SILENT`） | 断开全停；静默只留探活与 P0 |
| 刚连上 | `CONNECTED` 且距连接 < 60 s | 连接回调 | 只发初始化最小集，不叠加页面批次 |
| CGM 有无 | 有会话 / `SESSION_STOPPED` | `CGMStatusResponse.sessionState` | 无 CGM 时不排 CGM/EGV 查询，也不期望 CGM 事件 |
| CIQ 开关 | `closedLoopEnabled` true/false | `ControlIQInfoV1/V2Response` | 决定「是否要问 CIQ 专属状态」。**IOB 选源暂为待定**：不是「CIQ 开关」一项就能决定，见 §11 待验项 V1；在 V1 有结论前不据此改发送行为 |
| 机型能力 | `TSLIM_X2` / `MOBI`（判不出 = `null`） | `setupDeviceName` → `determinePumpModel`（`PumpDeviceNameUtil.kt:28`）；`canControlPump` / `supportsDevice`（`shared/.../SupportedDevicesUtil.kt:12-27`） | **决定「这一类请求能不能发」**。能力不支持时**不发**，也不"发出去等失败"。门控粒度是**请求类**（`Message` 子类），不是 topic——同一 topic 下可能「读支持、写不支持」（见 §3.5 #17 与"请求级约束"） |
| 大剂量会话 | 无 / 确认中 / 立即段进行中 / 延展进行中 | `45` / `47` / `-73` + 本地会话状态 | 决定 10 秒档还是 5 分钟档 |
| 页面可见性 | 前台可见 / 后台 | Activity 生命周期 | 只决定「渲染年龄」与「是否进后台低频档」，不直接决定发送 |
| 历史回补许可 | 允许 / 不允许（预算档） | 原 `auto-fetch-history-logs`，改造后为预算参数 | 只影响 P2；不允许时不得抢占 P0/P1 |

**机型能力必须按「请求类」判定，不能按 topic 一刀切**

- 同一 topic 可能「读可以、写不行」，所以门控的最小单位是 `Message` 子类，不是 `PumpTopic`。
  - `QUICK_BOLUS`：`PumpGlobalsRequest`（86）在 X2 上**可读**；`SetQuickBolusSettingsRequest`（-46）在 X2 上**不可写**——这是用户明确给出的事实（X2 不支持、Mobi 支持），代码注释与之相符（`QuickBolusSettingsActions.kt:86`）。
  - `CGM`：`HomeScreenMirrorRequest`（56）/ `CGMStatusRequest`（80）在 X2 上可读；Dexcom 起停与配对码写入在 X2 上不可写（`CGMActions.kt:108`、`:190`）。
- **能力来源只允许一处**：`determinePumpModel(deviceName)` + `canControlPump(model, messageClass)`（= App 规则 `model == MOBI` **且** 库注解 `@MessageProps(supportedDevices)` 放行，`SupportedDevicesUtil.kt:24-27`）。查询器**不得**另建 `supportsQuickBolus` / `supportsG7` 这类本地布尔开关，否则会出现"页面说支持、查询器说不支持"的第二真相。
- **判不出机型（`null`）时按不支持处理**（`supportsDevice` 对 `null` 返回 `false`，注释明确"宁可少显示可控项，也不要让人点了才发现不行"）。
- **不支持时调用方拿到的是 `Unavailable(MODEL_UNSUPPORTED)`**，不是空值、空集合或异常；与 §4.1.3 三态语义对齐，详见 §4.1.4。
- **已知上游缺口**（库注解不可信、配置文件自称与实际不符）见 §10.1「上游债务」；本轮只登记，不主动补。

#### 3.10.2 为什么控制页适合作为第一批

8 个页面形态完全一致：`LifecycleStateObserver(onStart)` 发一次、`LaunchedEffect(intervalOf(60))` 每 60 秒发一次、一张命令表 + 一张字段表、`waitForLoaded` 轮询本地字段到齐。替换面最小，共用度却最高：

| 共用请求 | 被谁使用 | 统一后的效果 |
|---|---|---|
| `HomeScreenMirrorRequest`（56） | Actions / Cartridge / CGM / Sound / QuickBolus | 同一 tick 只需 1 条 |
| `LoadStatusRequest`（20） | Dashboard / Cartridge | 同一 tick 只需 1 条 |
| `PumpGlobalsRequest`（86） | Sound / QuickBolus（**命令表与字段表完全相同**） | 纯重复源，合并为一条 `PUMP_GLOBALS` 订阅 |

#### 3.10.3 收编边界：只收「读」，不收「写」

- 进查询器的是各页的**查询**（`SendType.STANDARD` 那批读请求）。
- 页面上的**写动作**（`SetPumpSoundsRequest`、`SetQuickBolusSettingsRequest`、Dexcom 起停与配对码、耗材进退模式）仍留在页面，按 §3.4 的**请求级**机型门控判定；X2 上这些写本来就不该发。
- 因此「控制页全部查询进查询器」成立；「控制页全部功能进查询器」不成立，也不应成立——写动作是用户触发的直发，语义上属于 §3.3 的例外。

#### 3.10.4 施工顺序（三步，每步独立可回滚）

| 步 | 内容 | 改发送行为? | 验收判据 |
|---|---|---|---|
| **0′** | **页内去重**：去掉「onStart + `intervalOf` 首帧」双发与进页二次 `BUST_CACHE`（见 §3.10.5） | 是（少发一次） | 真机停留 5 分钟无字段缺失；`/api/query/stats` 每页计数减半 |
| **1** | B 步三件：`PumpTopic` 已有，补 `PumpCommandPort`、`PumppanQueryRouter`、调度器；`pumppan-query-engine` 默认 `LEGACY` | 否（LEGACY 不动） | 开关为 `LEGACY` 时 `stats` 与现状逐条一致 |
| **2** | 逐页切 B5–B12：`PumppanQueryRouter.tick(PumpTopic.X)` 一行，原发送整体移入 `LEGACY` 私有分支 | 是（走 V2 才变） | 同 topic 一分钟内只发一次；共用请求合并生效 |

#### 3.10.6 opCode 级观测（第 1 步）的落盘记录

第 0 步的 `requestCounts` 按 topic 聚合，一次首页批量 16 条命令只落进 4 个桶，看不出「哪条命令被重复发」。第 1 步把粒度下沉到 **opCode + 请求类名**，并用 250 ms 窗口识别「同一 tick 重复」，仍然只观测、不改发送行为。

| 新增字段（`/api/query/stats` → `counters`） | 含义 | 怎么读 |
|---|---|---|
| `opCodeCounts` | key = `"178\|ControlIQInfoV2Request"`，**真实下发**总量 | 分母；为空说明登记点没接上 |
| `opCodeDuplicateCounts` | 同一 250 ms 窗口内第 2 次及以后的次数（key 同上） | 分子；等于「合并同 tick 后可省下的写入次数」 |

- **窗口为什么是 250 ms**：一次 bulk 的 10 条命令实测在 30–50 ms 内写完（两批间隔 60 ms 的日志见 §3.10.5），250 ms 足以容纳整批；又远小于 60 s 页面 tick，不会把两次独立轮询误判成重复。
- **只计真实下发**：登记点在 `PumpCommHandler.command()` 的三个守卫（无 peripheral / 未连接 / 无 session）**之后**；`noteLegacyRequest` 仍在守卫之前计「尝试」，两者语义分开。
- **opCode 取无符号值**：`message.opCode()` 是 signed Byte，需 `and 0xFF` 才能与协议对照表一致（`178` 而非 `-78`）。
- **零值语义**：两个 map 由同一次调用写入，`opCodeCounts` 有值而 `opCodeDuplicateCounts` 为空，表示「确实没有同 tick 重复」，不是「登记没接上」。

首轮真机基线（2026-11-10，冷启动 20 s 内）：

```
opCodeCounts: 20 个键 / 合计 20 次；唯一 >1 的是 164|LastBolusStatusV2Request = 2
opCodeDuplicateCounts: {}      // 启动阶段没有同 tick 重复
requestCounts 合计 20 = opCodeCounts 合计 20   // 两套计数对得上
```

> 已知盲点：opCode 级只能回答「哪条命令重复了几次」，回答不了「谁发的」。页面归因仍靠 `pageSourceCounts`，目前只接了 Dashboard 与 CartridgeActions 两页；其余 6 页接入前，重复清单只能配合 `requestCounts` 的 topic 分布推断。

#### 3.10.7 与「先收集数据」的关系

第 0 步计数桩的目的，就是**先用真实数据回答「删掉某页的 60 秒会不会影响别人」**。因此：

- 第 0′ 步（页内去重）与第 0 步（计数）**并行且互不阻塞**：前者少发重复，后者继续积累画像。
- 只有在 `/api/query/stats` 上看到「每 topic 的调用来源分布、请求→应答匹配率」之后，才允许讨论第 2 步删掉哪条页面定时器。
- **没有基线就不删**（§3.8 原文）。第 0′ 步不删定时器，所以不受这条限制。

#### 3.10.8 明确不做

- 不改 `waitForLoaded` 的「到齐即停」逻辑——它属于第 2 步，单独改会形成双轨。
- 不把写动作搬进查询器。
- 不在第 0′ 步动其余 6 处（等本页实测结论）。
- 不改 `canControlPump = model == MOBI` 的判定规则（§3.4 唯一真相）。

## 4. 查询器的落地形态与自监控

> §3 定了「管什么、按什么状态、谁归它管」；本节回答「长什么样、放哪里、谁持有、怎么观测」。
> **只做设计，不改代码。** 大剂量那条线本轮不推进，查询器先行——它本身就是答案的度量工具。

### 4.1 落地形态

#### 4.1.1 它是什么：一个实例 + 构造注入，不是 Android Service

- 形态：`PumpQueryService` 是**单实例的纯 Kotlin 协调器**（普通 `class`），不是 `object` 单例、也不是 `Service` / `ViewModel`。
- 它只持有一个可替换的执行端口 `PumpCommandPort`（接口），真正「把一条指令写到泵」的实现由上层注入。
- 为什么不用 `object`：`object` 无法在测试里替换端口，也无法在「只收不发」实验里做双实例回放。用「进程内唯一实例 + 构造注入」既保证全局只有一处调度，又可在实验/单测里替换实现。
- 为什么不做成 `Service`：`CommService` 已经是前台服务，再起一个 Service 会带来第二套生命周期、通知与唤醒；查询器只需要**进程内一个对象**，跟着 `CommService` 活即可。

#### 4.1.2 放哪个模块

| 模块 | 归属内容 | 理由 |
|---|---|---|
| `shared` | **调度核心**：`PumpTopic`、`PumpReading`、优先级/预算状态机、去重与单飞、统计计数 | 全是纯逻辑（时间、年龄、优先级、计数），不依赖 Android，可单测、可复用；不会把 UI 类型带进来 |
| `pumpcomm` | **端口实现**：`PumpCommandPort` 的 `PumpSession` 版本；事件接入（`onReceiveQualifyingEvent`）；连接态/静默上报 | 只有这一层握有 `PumpSession` 与 BLE 回调，无法也不该上移 |
| `mobile` | **消费者适配**：把 `DataStore` 接成一个订阅者；诊断端点与面板 | 页面只应「订阅 + 渲染」，适配层越薄越好 |

依赖方向（单向，禁止反向）：

```
mobile(页面 / DataStore 适配) ──→ shared(PumpQueryService · PumpTopic · PumpReading)
pumpcomm(端口实现 · 事件 · 连接态) ──→ shared
shared ──✗→ 不得依赖 mobile / pumpcomm，也不得 import pumpx2 的 Android 侧类型
```

- 如果 `shared` 现状不便承载（例如它的 Android 依赖已经偏重），退路是放 `pumpcomm` 的纯 Kotlin 子包；但**必须保证调度状态机里不出现 `Message` 类型**，否则又会把「传输」和「调度」绑死。

#### 4.1.3 接口长什么样

```kotlin
// --- 对外只有：订阅 / 一次性 / 直发登记 / 快照 / 诊断 ---
interface PumpQueryService {
    fun subscribe(
        topic: PumpTopic,
        maxAgeMillis: Long,                 // 我能忍多久
        priority: QueryPriority,
        onReading: (PumpReading<*>) -> Unit,
    ): Subscription                        // cancel() 即退订，引用计数归零即停

    suspend fun await(
        topic: PumpTopic,
        maxAgeMillis: Long,
        priority: QueryPriority,
        timeoutMillis: Long = 15_000,
    ): PumpReading<*>                       // 超时不抛异常，返回 Stale / Unavailable

    fun requestDirect(                     // 唯一例外：必须立刻拿到单条结果
        topic: PumpTopic,
        reason: String,                    // 必填，写进诊断
        priority: QueryPriority = QueryPriority.P0_CONFIRM,
    ): PumpReading<*>

    fun snapshot(topic: PumpTopic): PumpReading<*>
    fun diagnostics(): QueryDiagnostics
}

// --- 数据形态：永远不是 null ---
sealed interface PumpReading<out T> {
    data class Fresh<T>(
        val value: T,
        val atMillis: Long,                // 本地收到时刻
        val source: ReadingSource,         // PUMP / CACHE
    ) : PumpReading<T>

    data class Stale<T>(
        val value: T?,                     // 可能是「从未有过」= null，但外层不是 null
        val atMillis: Long?,
        val ageMillis: Long,
        val source: ReadingSource,
        val reason: StaleReason,           // 超容忍 / 断连 / 静默 / 超时 / 预算
    ) : PumpReading<T>

    data class Unavailable(
        val topic: PumpTopic,
        val reason: UnavailableReason,     // NEVER_RECEIVED / DISCONNECTED / SILENT / BUDGET / MODEL_UNSUPPORTED
    ) : PumpReading<Nothing>
}
```

- **为什么是三态而不是 `T?`**：`Fresh` 表示「本次/容忍期内真实收到」；`Stale` 表示「有旧值但已超期」，强制携带 `ageMillis`，UI 不能假装实时；`Unavailable` 表示「确实没有」，调用方必须显式处理，而不是靠 `null` 猜。
- **为什么 `await` 不抛异常**：数据要不到是常态（断连、静默、首次启动），不是异常路径。抛异常会逼每个调用方写 `try/catch`，最终又变成「各自处理」。
- **`source` 只允许 `PUMP` / `CACHE`**：不设 `DERIVED`，因为 §10 已明确「不为省请求而推算泵状态」。推算值一旦进来，年龄口径会立刻失真。

#### 4.1.4 没有数据时返回什么

- **不返回 `null`**，返回 `Unavailable(topic, reason)`。
- **机型不支持也走三态**：返回 `Unavailable(topic, MODEL_UNSUPPORTED)`，而不是 `null`、空列表、空对象或 `UnsupportedOperationException`。调用方据此显示"该型号不支持"，并能与"没查到 / 断连"区分开（§3.4 请求级约束）。
- 订阅回调**首帧就要给结果**：要么 `Unavailable`，要么 `Fresh`/`Stale`；不允许「先静默、等有值再回调」，否则 UI 无法区分「还没查」和「查了没有」。
- 统一渲染约定：

| 返回 | 界面表达 |
|---|---|
| `Fresh` | 正常值，可选显示「刚刚」 |
| `Stale` | 值 + 「N 分钟前」；超过硬上限时置灰 |
| `Unavailable` | 按 `reason` 分开表达：「未连接」/「本次不可用」/「等待泵响应」/「该型号不支持」 |

#### 4.1.5 谁持有它、生命周期与重启

- **持有点**：`CommService` 创建并持有；`PumpCommHandler` 注册端口与事件回调。这样查询器与「正在连泵的那个服务」同生共死，不会出现「服务停了但调度器还在发」。
- **生命周期**：跟随 `CommService`；服务销毁 → 查询器销毁，所有订阅者收到 `Unavailable(DISCONNECTED)`。
- **App 重启**：查询器重建，**内存缓存清空**；首帧全部 `Unavailable`，直到第一个真实回包。
- **不落盘**：查询器只做「内存 last-known + 年龄」。跨重启的持久数据仍由 `HistoryLogDatabase`（历史）与 `StatePrefs`（并发症用的小状态）提供。
  - 理由：查询器一旦自己落盘，就会出现「查询器缓存 / DataStore / DB」三份真相，年龄口径必然分叉；而且重启后的旧值到底算不算「fresh」会变成新的争议点。

#### 4.1.6 与现有层的边界

| 层 | 保留 | 搬走 |
|---|---|---|
| `PumpCommHandler`（传输） | 连接/认证、发送、收包、事件原始解包、`CacheSeconds` 命中判断（改为「上报收到 X」） | 不再决定「何时发、发几条」；`suggestedHandlers` 的**执行**移交查询器，自己只上交事件 |
| `DataStore`（镜像） | 作为**订阅者之一**，把 `PumpReading` 镜像成 `MutableLiveData`；保留 Compose 的同步读 | 不再持有页面定时器；不再是「发送触发点」 |
| `HistoryLogFetcher`（回补） | 缺口计算、按批请求、写库 | 「何时开始/暂停/让路」交给查询器 P2；不再每 500ms 硬等 |
| 各页面（消费者） | 订阅 topic、渲染值与年龄、布局 | 删除全部 `LaunchedEffect` 定时发送、`postDelayed` 重试、固定次数轮询 |
| `MainActivity` | 生命周期上报（可见/不可见） | 仍可转发消息，但不再决定查询 |

关键取舍：**`DataStore` 从「全局变量袋」变成「查询器的镜像订阅者」**。它是唯一保留 `LiveData` 的地方，因为 Compose 需要同步读；但写入权只来自查询器。

#### 4.1.7 事件怎么进

- 链路：`TandemBluetoothHandler`（解出位掩码）→ `PumpCommHandler.onReceiveQualifyingEvent` → **`queryService.onPumpEvent(events, rawBitmask, atMillis)`**。
- 查询器把事件当**输入信号**，而不是旁路：
  1. 记录事件（进入 §4.3 的统计与「该来没来」基线）；
  2. 把 `event.suggestedHandlers` 映射成一组 `PumpTopic`；
  3. **只有「有订阅者 + 当前 age > 容忍度」才发**；否则只更新期望时间，不发。
- 事件可以**跳过年龄门槛**（泵刚说变了，容忍度视为 0），但仍必须经过：合并、单飞、预算、连接态检查。
- 保留的特例：`PUMP_COMMUNICATIONS_SUSPENDED` 仍即时 `pauseSends`——它是安全动作，不是查询，不纳入预算。

#### 4.1.8 硬闸在哪、拒绝时给什么

发送前检查只有一处（查询器出口），顺序固定：

1. **连接态**：`DISCONNECTED` → 全部拒绝，回 `Unavailable(DISCONNECTED)`。
2. **静默**：`LINK_SILENT`（>30 s 无回包，`DiagMonitor.kt:491-492`）→ 只放行 P0 与一条轻量探活，拒绝 P1/P2。
3. **预算**：超限 → P2 丢弃、P1 延后一轮、P0 放行并标记「预算超限下的 P0」。
4. **合并/单飞**：同 `opCode` 在飞 → 不重发；超时后才允许重试。

拒绝的反馈**不是异常**，而是带原因的 `PumpReading`：

- 从未有过值 → `Unavailable(reason)`；
- 有旧值 → `Stale(lastKnown, age, reason)`。

每一次拒绝都必须计数（见 §4.3），否则「为什么没数据」永远查不清。

### 4.2 第 0 步「登记与旁路」具体是什么

#### 4.2.1 改哪些文件、加什么

| 文件 | 加什么 | 影响发送? |
|---|---|---|
| `shared/.../query/PumpQueryService.kt`（新增，可先空壳） | `noteLegacyRequest(topic, source, atMillis)` / `noteLegacyReply(topic)`：**只做内存计数 + 可选日志** | **否** |
| `shared/.../query/PumpTopic.kt`（新增） | topic 枚举 + 到 pumpx2 请求类型的映射表（本步不执行） | 否 |
| `pumpcomm/.../PumpCommHandler.kt` | 在每个真实发送点旁边加一行登记；收到应答处加一行回执登记 | **否**（原发送逻辑一行不动） |
| `mobile/.../CommService.kt` | 周期任务、历史入口各加一行登记 | 否 |
| `mobile/.../HttpDebugApiService.kt` | 新增只读端点 `GET /api/query/stats`，把计数吐出来 | 否 |
| 各页面 | **本步不改** | 否 |

- 为什么登记点放在**发送处**而不是页面：页面多、改页面等于提前动行为；从唯一的发送出口登记，能以最小改动拿到全量基线。

#### 4.2.2 为什么这一步不改行为

- `noteLegacyRequest` 是**纯 no-op 计数桩**：不改调用顺序、不改返回值、不改重试、不改超时、不改线程。
- 所有登记都是「原语句旁多一行」，不包裹、不替换。
- 不需要 feature flag 也能回滚：删掉那几行即可。
- 本步**禁止**任何「顺手」的合并、去重、年龄判断、预算判断。

#### 4.2.3 怎么证明「没改行为」

三条同时成立才算：

1. **发送序列不变**：同一场景（例如进首页并停留 3 分钟）对比改前/改后的报文序列（opCode + 顺序 + 间隔），逐条一致。
2. **计数可对账**：`/api/query/stats` 的发送计数 ≈ 报文流里实际出现的请求数（差值只能来自丢包/日志缺失）。
3. **异常不上升**：超时率、失败率、断连次数与基线同量级。

第 1 条不成立 → 说明动到行为了，立刻回滚那一处。

### 4.3 查询器自监控

#### 4.3.1 一句话健康判断

> **「近 1 分钟：P0 全部成功；每个 topic 的 age 都在容忍度内；没有任何 opCode 同时在飞 >1；拒绝次数 = 0（或拒绝理由全部是预期内的断连）。」**

任意一项不满足即为不健康；具体原因看拒绝/超时计数。

#### 4.3.2 指标清单

| # | 指标 | 怎么算 | 粒度 | 保留 |
|---|---|---|---|---|
| 1 | 谁在问 | `topic × source`（source = 页面/定时器/事件）计数 | 每分钟 | 24 h 滚动 + 每小时落盘 |
| 2 | 问了几次 | `requestsSent[topic]`（真实写出次数；Bulk 记 1） | 每分钟 | 同上 |
| 3 | 省了几次 | `merged[topic]` / `deduped[topic]` | 每分钟 | 24 h |
| 4 | 回了没 | `replies[topic]` / `timeouts[topic]` / `failureRate` | 每分钟 | 24 h |
| 5 | 数据多老 | `ageMs[topic]` 当前值 + `ageP95[topic]` 窗口 | 实时 + 每分钟 | 24 h |
| 6 | 被拒几次 | `rejected[topic][reason]`（DISCONNECTED / SILENT / BUDGET / IN_FLIGHT） | 每分钟 | 24 h |
| 7 | 为什么被拒 | 同 #6 的 reason 维度 + 拒绝瞬间的连接态快照 | 每次拒绝 | 24 h |
| 8 | 事件侧 | `eventsReceived[name]`、`eventToRequestLatencyP50`、`eventWithoutRequest[name]` | 每分钟 | 24 h |
| 9 | 单飞违规 | `concurrentInFlight[opCode] > 1` 的累计次数 | 每次 | 24 h |
| 10 | 预算水位 | `sentLastMinute / limit`、被丢弃的 P2 数 | 每分钟 | 24 h |

#### 4.3.3 落在哪

三层，全部只读：

1. **内存计数（主）**：查询器内部原子自增 + 每分钟滚动窗口；读它不阻塞发送。
2. **只读 HTTP 端点（对外）**：在现有 `HttpDebugApiService` 加 `GET /api/query/stats`，返回 #1–#10 的 JSON。**复用现有端口与鉴权，不新增服务器。**
3. **小时归档（留证）**：把 `/api/query/stats` 快照追加到 `archive/query-hourly-YYYYMMDD.jsonl`。**挂到已有每小时归档任务里，不新增定时器。**

可选（非必须）：`DiagScreen` 加一块只读面板，渲染同一份 stats。

#### 4.3.4 明确不做

- **不为监控新增泵查询**：所有指标都来自「已发生的发送/接收/拒绝」。
- **不新增常驻线程**：统计在发送路径上 O(1) 累加；聚合惰性计算或复用它已有的秒级节奏。
- **不写 BLE 热路径日志**：只在拒绝/超时/单飞违规时打日志。
- **不落全量明细**：只存每小时聚合，原始明细继续由报文流/日志提供，避免双份存储。
- **不让监控影响预算**：统计不参与调度决策，防止形成反馈环。

#### 4.3.5 与复查机制（§9.2）的接口

- 复查时直接看 `/api/query/stats`：删除/合并/降级的依据就是 #1、#3、#4。
- 「该来没来」在 #8 体现：`eventWithoutRequest` + `IOB_CHANGE` 的 age。

为什么 Kotlin 没有「同名覆盖」这条路：同 module 同 sourceSet 里同包同名类直接重定义编译失败；不同包则是两个可调用实现，只能靠调用点二选一——**所以分叉点必然落在调用点，也就是「入口一行」**。

1. **上游更新时怎么做**：只对「上游文件」列跑 `git log <复制时基线 sha>..<上游HEAD> -- <path>`；有提交才看 diff，无提交直接跳过，其余文件一律不看。
2. **什么算漂移**（只认三类）：上游改了**同一个函数**；改了**入口行或紧邻行**（±5 行）；**删除了入口所在的调用**（函数被删/重命名/移走）。同一文件别处的改动、注释、格式化**不算**。不确定是否触及入口时，按漂移处理，人工看 diff。
3. **发现漂移怎么处理**：先判断是否影响入口语义——不影响只更新「上次核对日期」；影响则按归属执行：**入口行以上游为准**（接受上游新逻辑，再把我们那一行重新插回去）；**副本以副本为准**（人工把上游改动搬进副本，绝不反向合回上游）。
4. **核对节奏**：双周一次 + 上游发版/合并 `main` 前一次（与 §9.2 同频）。
5. **一句话原则**：表外的改动视为违规，必须补登记。
6. **基线 sha 口径**：入口行 = 开始分叉时的上游 HEAD；复制件 = 复制时的上游 HEAD。**未分叉/未复制一律记 `待补`，不得编造。**
7. **列设计（生成时沿用）**：编号 / 上游文件 / 位置·函数 / 我们的改动（一句话）/ 开关如何生效 / 回退方式 / 复制时基线 sha / 上次核对日期 / 漂移标记；按 B（入口）、P（pumppan 自有）、C（复制件）、N（不动）分组。

#### 4.4.4 开关设计

- **粒度：一个总闸**（不是按域）。键名沿用既有约定（`PumppanPrefs.kt:12-14` 的 `pumppan-*` 前缀）：

| 键 | 默认 | 语义 |
|---|---|---|
| `pumppan-query-engine` | **`false`**（= `LEGACY`，与 `pumppan-bolus-ui` 默认一致） | `false` 走上游原路；`true` 走 pumppan 查询器 |

- **为什么不分域**：分域会产生"UI 走新路、后台走旧路"的组合，而两条路可能对同一 topic 各发一次——直接违反「不允许两份实现同时活着」。真要分域，前提是**证明域之间 topic 不相交**，且写进 §4.3 自监控。
- **切换后果**：切换瞬间**已排队的旧定时器不会自动停**，必须在开关读到 `V2` 时先 `cancel` 旧任务再启动订阅；否则首分钟会看到双份请求。这是 B/C 步验收的第一条。
- **不许有中间态**：`PumppanQueryRouter` 只有 `LEGACY` / `V2` 两个 mode（对齐 `BolusRouter.kt:24-32` 的写法），不允许第三个"混合"分支。
- **怎么在日志/自监控里看出当前走哪条路**：
  - `/api/query/stats` 增加 `engine: "LEGACY" | "V2"`（**observed**，来自 router 实际调用计数）与 `switch: { configured: "V2", observed: "LEGACY" }`。
  - 启动时打一行 `PumppanQueryRouter: mode=<LEGACY|V2>`。
  - 自监控面板显示 **observed**，不是配置值——只有 observed 才能证明"真的切了"。
- **防「以为切了其实没切」**：开关为 `V2` 时，若 `noteLegacyRequest` 计数仍在增长 → 记 `SWITCH_MISMATCH` 并告警。这条就是 §4.2 第 0 步计数桩的最终用途。

#### 4.4.5 上游同步流程

- **节奏**：每两周一次；上游发版/合并 `main` 前必须做一次（`§9.2` 复查同频）。
- **看哪些文件**：只看 §4.4.3 A 组的「上游文件」列，加上 §4.4.2 每个 `Copy.kt` 的 `upstream` 路径。
- **怎么算落后**：对每个副本/入口行执行 `git log <fork-of>..<上游HEAD> -- <upstream路径>`；有提交 = 落后，逐条判断是否触及我们复制/分叉的区间。
- **副本怎么合并**：单向跟随——把上游改动**手工搬进副本**，更新 `fork-of` sha；**绝不把副本反向合回上游**（那是 §10.1 的上游债务，不主动补）。不触及被复制区间的提交，只更新 `fork-of` 注释。
- **冲突以谁为准**：

| 冲突类型 | 以谁为准 | 理由 |
|---|---|---|
| 入口一行（B 组） | **上游**——把上游新逻辑整段接受，再把我们的那一行重新插回去 | 那段逻辑的 owner 是上游 |
| 副本（`Copy.kt`） | **副本**——上游改动经人工判断后吸收，绝不自动合并 | 那段逻辑的 owner 已经是我们 |
| 注释/来源块 | 副本 | 不影响行为 |

- **同步后必做**：跑一次 §4.3.2 的 #1/#4 对账 + `SWITCH_MISMATCH` 检查，确认行数没变（新增上游分叉要补进 §4.4.3）。

#### 4.4.6 风险清单

| # | 风险 | 表现 | 检测手段 | 对策 |
|---|---|---|---|---|
| R1 | **两份实现并存** | 同一 topic 双发请求，预算爆掉 | `noteLegacyRequest` 在 `V2` 下非零 → `SWITCH_MISMATCH` | 单一总闸；切换时先 `cancel` 旧定时器 |
| R2 | **上游改了副本没跟** | 副本行为落后于协议/UI 修复 | `fork-of` 与上游 HEAD 的 diff 触及副本行 | 双周审计（§4.4.5）+ 头部来源块 |
| R3 | **开关忘开，以为切了其实没切** | 以为省了请求，其实全在旧路径 | `stats.switch.observed != configured` | 面板显示 **observed**；`SWITCH_MISMATCH` 告警 |
| R4 | **包名迁移的可见性/内部引用** | 编译错误或运行时 NoSuchMethod | 编译 + 单测 | 见下方细则 |
| R5 | **副本吃掉上游修复** | 长期分叉，越走越远 | 副本行数与 A 组行数增长 | 只有"能整体替换的组件"才复制（§4.4.3 判定标准） |
| R6 | **顺手改了几处没登记** | 上游同步时漏看、冲突突发 | 代码评审对比 §4.4.3 表 | 表是唯一清单（§4.4.3 规则） |

**R4 细则（包名迁移实际会碰到的坑）**

- `private` **顶层**函数/扩展属性只在**文件内**可见——复制到新包后原文件里的调用会断。处置：复制时提升为 `internal`（同 module 可见），或把调用方一起搬。
- `internal` 在 **同 module** 内跨包可见，**跨 module 不可见**——所以 `shared`/`pumpcomm` 的 `com.pumppan` 包不能 import `mobile` 的 `internal`；反之亦然。依赖方向见 §4.1.2，本来就单向，别为图省事反向引用。
- `androidTest` / `test` 与主 sourceSet 的 `internal` 可见性按 Gradle friend-path 处理，通常可用；若报错，改用 `@VisibleForTesting` 而不是放宽到 `public`。
- **`R` 与 `BuildConfig` 不随包名变**：module 的 `namespace` 未改，资源引用仍是 `com.jwoglom.controlx2.R`，`BuildConfig` 同理。**不要**在新包里自建 `R`。
- **反射/字符串类名**：`Prefs`、序列化、`DataStore` 里若有以字符串保存类名的逻辑，副本类**不要改这些成员的包路径**；改名会让旧数据读不回。
- **Compose**：`@Composable` 默认 `public`，无可见性问题；但 preview 的 `setUpPreviewState` 仍在 `com.jwoglom` 包，副本 preview 需要 `import` 它（同 module，`public` 可访问）。

#### 4.4.7 构建配置：无需改

**结论：不需要改任何 `build.gradle`。**

依据：

1. 新文件都在**同一 module 的 `src/main/java`** 下，`android`/`kotlin` 插件的默认 source set 已包含该目录，不需要 `sourceSets { main { java.srcDirs += ... } }`。
2. 包名与目录一致即可，**不改 `namespace`**（`namespace` 只决定 `R` / `BuildConfig` 的包名），所以资源与 BuildConfig 全部零改动。
3. 跨模块的依赖现状已满足：`pumpcomm/build.gradle:37` 已有 `implementation project(path: ':shared')`，`mobile` 也已依赖 `shared` 与 `pumpcomm`。把调度核心放 `shared`、端口放 `pumpcomm` **不需要新增依赖行**。
4. 查询器只用 Kotlin 标准库 + 已有的 `pumpx2-*` 依赖，**不引入新库**。

唯一需要改构建的情形（本轮都不做）：把调度核心挪到新 module、或需要 `api` 导出 `com.pumppan` 类型给别的 module 继承/扩展。

### 4.5 策略外置：配置文件

> 目标：**频率、阈值、门控、预算、冷却**将来不改代码就能调；**发什么、能不能发**永远留在代码里（界线见 §4.5.7）。
> **2026-11-10 修订**：界线已由 §4.6.6 改写——「在什么条件下发、发哪些」移入配置，「发什么内容 / 安全闸」仍留在代码。本节其余内容继续有效。

#### 4.5.1 对齐既有约定（不造第二套体系）

先看现状：`mobile/src/main/assets/pump-capabilities.json` + `PumpCapabilities` 是项目里唯一成熟的配置先例；其口径正本是 [阈值配置外置-设计.md](阈值配置外置-设计.md)（2026-11-07 改写版）。

**沿用（这五条照抄）**

| 约定 | 既有做法 | 新配置照做 |
|---|---|---|
| 文件形态 | `assets/<dot-name>.json`，`ASSET_NAME` 常量 | `mobile/src/main/assets/pump-query-policy.json` |
| 版本号 | 顶层 `schemaVersion: 1` | 同 |
| 分组 | `default` 兜底 + `models[型号]`（`TSLIM_X2` / `MOBI`） | 同结构；本文件暂不设 `models` 键（见 §4.5.2） |
| 加载时机 | `initialize(context)` 于 `PumppanApplication.onCreate` 调一次，解析后常驻内存 | 同点位、同一次性缓存 |
| 兜底 | 文件缺失/解析异常 → 代码内 `FALLBACK_*` 常量，不崩、不阻断启动 | `FALLBACK_QUERY_POLICY`，同语义 |
| JSON 写法 | **内部不写注释**，值只放数字/布尔/短字符串；语义与出处进 [协议差异清单-出处表.md](协议差异清单-出处表.md) | 同（所以 §4.5.3 的示例 JSON 不带注释，字段解释放在紧邻的字段表里） |

**不沿用（既有做法本身的三个缺陷，新配置必须避开）**

| # | 既有缺陷 | 新配置的处置 |
|---|---|---|
| E1 | `note` 里写「UI 显隐、校验、发送前检查**只读此文件**」，实际有大量 `if (model == TSLIM_X2)` 硬编码（已在 §10.1 D3 登记） | **禁止写"只读此文件"这类无法自证的承诺**。改为**启动自检**：加载后枚举"仍硬编码的策略值"，发现即记 `HARDCODED_POLICY_FOUND` 并在 `/api/query/stats` 暴露；承诺由检查证明，而不是由注释声称 |
| E2 | 校验只有类型兜底（`optInt` 默认值），**没有范围钳制**：`intervalMs: 0` 能直接生效 → 忙等发请求 | 新配置必须**范围钳制 + 单调性校验 + 结构性拒绝**（§4.5.5）。宁可整份拒绝回退，也不让越界值上线 |
| E3 | 改完配置无法知道"哪份生效、改了哪几条" | 新配置必须给 `source / hash / loadedAt / 与默认值的差异列表`（§4.5.6），且暴露 **effective** 而不是 configured |

#### 4.5.2 放哪、叫什么

| 层 | 路径 | 可写 | 作用 |
|---|---|---|---|
| 出厂策略 | `mobile/src/main/assets/pump-query-policy.json` | 否（随包） | 权威默认值，可审计、不会被用户误删 |
| 现场覆盖 | `filesDir/query-policy-override.json` | 是 | 调参/诊断用；不存在则不启用 |
| 内建兜底 | `FALLBACK_QUERY_POLICY`（Kotlin 常量） | — | asset 与 override 都不可用时的最后一份 |

- **叠加方式**：asset 为底，override 做**深合并**（只覆盖同路径标量/数组，不整块替换分组）。
- **覆盖白名单**：override **只允许改 §4.5.7「必须外置」里的键**；白名单外的键一律忽略并记 `IGNORED_KEY`。这样即使有人往 override 里塞 `priority`/`freshness` 语义，也不会把状态机改坏。
- **为什么不只放 `filesDir`**：只放可写目录意味着"首次安装没有策略"，任何解析失败都会变成空策略上生产；asset + 兜底常量保证**永远有一份完整策略**。
- **是否按机型分文件**：**不分**。沿用 `default` + `models[型号]` 的单文件结构（与 `pump-capabilities.json` 一致）。**理由**：机型差异的唯一合法来源是**能力**（§3.4 的 `PumpCapabilities`），策略文件不重复定义能力；只有实测证明"同一条策略在 Mobi 上必须不同"时才加 `models.MOBI`，且要先补出处（§4.5.1 的"一值一出处"）。
- **两个文件职责分离，不合并**：`pump-capabilities.json` = **能不能做**；`pump-query-policy.json` = **多久做一次、等多久、超了怎么办**。合并会把"能力"和"策略"绑死，改频率就得碰能力表。

| `events.<事件名>.topics` | 数组 | 该事件触发去刷新的 topic 列表 | 见示例 | topic 必须存在于 `topics` |

| `reconnect.probeTopics` | 数组 | 连上后先发的探针 | `["STATUS_BATCH"]` | 非空 |
| `reconnect.probeDelayMs` | ms | 连上到发探针的等待 | `3000` | `0..15000` |
| `reconnect.probeTimeoutMs` | ms | 探针应答超时 | `15000` | `5000..60000` |
| `reconnect.batchAfterProbeMs` | ms | 探针成功后到放批的间隔 | `5000` | `0..30000` |
| `reconnect.maxBatchAtOnce` | 个 | 一次最多放几个 topic（防连上瞬间突发） | `2` | `1..5` |
| `switches.periodicEnabled` | bool | 总闸下的分项：是否启用周期刷新（`STATUS_BATCH` 等） | `true` | — |
| `switches.pageRefreshEnabled` | bool | 是否启用各页面 60 s 刷新 | `true` | — |
| `switches.backfillEnabled` | bool | 是否启用历史回补 | `true` | — |
| `switches.eventDrivenEnabled` | bool | 是否启用"事件→topic"触发 | `true` | — |

**注意**：`pumppan-query-engine`（§4.4.4 的总闸）**不进本文件**。它是**运行时用户开关**（`Prefs`），决定走旧路还是新路；本文件只描述"新路怎么跑"。两者职责不同，不要混。

#### 4.5.4 加载与生效

- **启动一次加载**：`PumppanApplication.onCreate` → `QueryPolicyLoader.initialize(context)`，与 `PumpCapabilities.initialize` 同一处。解析结果是一个**不可变** `QueryPolicy`，注入 `PumpQueryService`（§4.1.3）。
- **热更新**：不自动监听文件。Debug 页提供「重载策略」按钮 → 重新读 asset + override → 生成新 `QueryPolicy` → 原子替换引用。
- **什么时候生效**：
  - 立即生效：`intervalMs` / `cooldownMs` / `budget` / `freshness` → 下一个 tick 开始用新值。
  - 下一 tick 生效但**不清零计数**：预算计数器跨重载保留，避免"重载即获得新突发额度"。
  - **下次连接才生效**：`reconnect.*` 与 `states.connectedSettleMs`（明确标注 `applyOn: next-connect`），因为中途换重连序列会打断当前会话。
- **在飞请求**：不打断。旧策略排队的请求按旧参数跑完，新策略从下一个调度点接管。
- **失败兜底**：整份解析失败 → `FALLBACK_QUERY_POLICY`（与 asset 同值的内建常量）+ 标记 `POLICY_FALLBACK`；**不做部分降级**（半解析的 policy 比默认值更危险）。

#### 4.5.5 校验

| 情况 | 处置 | 记录 |
|---|---|---|
| 字段缺失 | 用该字段的**内建缺省**继续（不整份丢） | `MISSING_KEY` |
| 数值越界 | **钳制到范围**（如 `intervalMs: 0` → `1000`） | `CLAMPED` |
| 类型错（字符串当数字等） | 该字段回落缺省 | `TYPE_MISMATCH` |
| 未知字段 | **忽略**（前向兼容，允许先加字段后升级 App） | `UNKNOWN_KEY` |
| 覆盖白名单外的键 | 忽略 | `IGNORED_KEY` |
| **结构性错误**（`topics.*` 全缺、`budget.perMinute <= 0`、`freshness` 三档不单调、`degradeOrder` 缺 `P0_CONFIRM` 或把 `P0` 排在最前） | **整份拒绝**，用 `FALLBACK_QUERY_POLICY` | `POLICY_REJECTED` + 具体原因 |

**一句话规则**：**单字段错 → 缺省 + 标记；策略结构性错 → 整份拒绝回退。**（对应 E2：绝不让越界值静默生效。）

#### 4.5.6 可观测（接 `/api/query/stats`）

在既有 stats 响应里加 `policy` 段：

```json
{
  "policy": {
    "source": "ASSET+OVERRIDE",
    "schemaVersion": 1,
    "hash": "sha256:ab12…",
    "loadedAt": "2026-11-09T20:14:03+08:00",
    "applyPendingOn": ["reconnect"],
    "effective": { "DASHBOARD_BATCH.intervalMs": 60000, "budget.perMinute": 10 },
    "diffFromDefault": ["DASHBOARD_BATCH.intervalMs: 60000 → 30000"],
    "diagnostics": { "clamped": [], "rejected": [], "unknownKeys": [], "ignoredKeys": [] },
    "hardcodedPolicyFound": []
  }
}
```

- `source` 三选一：`ASSET` / `ASSET+OVERRIDE` / `FALLBACK`。
- **`effective` 是实际生效值，不是配置值**（与 §4.4.4 开关同一个教训：observed 才能证明"真的生效了"）。
- `diffFromDefault` 只列与内建默认不同的键——**一句话就能看出"被配置改掉的是哪几条"**。
- `hardcodedPolicyFound` 就是 E1 的自检输出：仍硬编码的策略常量清单；为空才说明"策略真的外置了"。

#### 4.5.7 界线：哪些绝不外置，哪些必须外置

**绝不外置（写死在代码里，配置文件改不动）**

| 项 | 为什么 |
|---|---|
| **请求类本身**（发哪个 opcode、字段编码、单位转换） | 协议事实，改错就是发错包 |
| **三态语义与 `UnavailableReason` 判定** | 状态机语义；配置只能调"多久算旧"，不能调"什么叫没有" |
| **安全边界**：大剂量确认/签名、`insulinDeliveryActions` 前置、`canControlPump` 的**判定规则** | 安全闸不允许被一份 JSON 打开 |
| **硬闸本身的存在性** | 可以调 `perMinute` 数值，不能把硬闸关成 0 条上限之外的无上限 |
| **P0 语义**（确认/取消永远先于装饰类） | 排在 `degradeOrder` 里可调顺序**上限**，但不能把 `P0` 降到"可丢弃" |
| **能力值来源**（`PumpCapabilities`） | 能力只有一处真相；策略文件不复制 |

**必须外置（配置文件说了算）**

- 某 topic 是否发送（`topics.*.enabled`，新增于 §4.6）
- 频率与最小间隔（`topics.*.intervalMs` / `minIntervalMs`）
- 状态门控的**阈值**（`connectedSettleMs` / `linkSilentAfterMs` / `visibilityDebounceMs` / 会话期轮询）
- 三态时间阈值（`freshness.*`）
- 预算数值与降级顺序（`budget.*`）
- 事件 → topic 映射与冷却（`events.*`）
- 重连序列的时间参数（`reconnect.*`）
- 分项开关（`switches.*`）

> **界线一句话（可直接转述）**：
> **「发什么、能不能发」写在代码；「多久发一次、等多久、超了怎么办」写进配置。**
>
> **2026-11-10 已被 §4.6.6 修订**，转述口径改为：「发什么内容、怎么编码、安全闸」写代码；「在什么条件下发、发哪些、多久发、超时怎么办」写配置。

#### 4.5.8 迁移（保证行为不变）

1. **抄值不抄逻辑**：把 §3.5 策略表的间隔、§7 的预算数字、§5.4 的数据年龄容忍度，逐项抄成 `default` 块；逻辑（何时触发、怎么降级）仍留在代码。
2. **等价性证明**：加载后把 `effective` 与旧硬编码常量逐项比对；单测/脚本断言**全等**，任一不等即阻断启用（这是"第 0 步不改行为"的前提）。
3. **第 0 步只加文件与读链**：asset + fallback + 校验 + stats 一起进，但**不接 override**、不接热更新；`pumppan-query-engine` 仍为 `false`，所以线上行为零变化。
4. **分项开关先全 `true`**：避免"迁移当天就关掉某一路"制造行为差异；关分项留给 B/C 步排查用。
5. **硬编码清单化**：迁移时把现存硬编码值列成"待删除清单"，并入 §4.2 的登记表；`hardcodedPolicyFound` 归零才算迁移完成。

### 4.6 策略配置化约定（2026-11-10 用户拍板）

> 本节是对 §4.5 的**加严与放宽同时发生**：加严在于「策略必须可配置、不许写死」；放宽在于把「能不能发某类查询」从代码移进配置。
> 一句话：**代码只保留协议与安全，其余查询行为都由配置决定。**

#### 4.6.1 三条硬约定

| # | 约定 | 落地要求 |
|---|---|---|
| 1 | **策略不写死**：频率、门控、预算、开关、抑制，全部来自 `pump-query-policy.json` | 加载后若仍发现硬编码策略值，记 `HARDCODED_POLICY_FOUND` 并在 `/api/query/stats` 暴露（沿用 §4.5.1 E1 的自检思路，不写"只读此文件"这种空承诺） |
| 2 | **按「泵类型 × 固件版本 × 工作态」分策略** | 三类条件都是 `overlay.when` 的固定键，命中即覆盖；条件之间是 AND |
| 3 | **泵主动推送是策略的输入条件，不是动作** | 推送只改变「要不要发 / 发多快 / 临时算哪种工作态」，绝不因配置产生新的发送内容 |

#### 4.6.2 两层结构：`default` + `overlays`

不再用「`models.TSLIM_X2` 单独一份」的写法——机型只是 `when` 的一个维度，固件与工作态同理。这样只有一个匹配算法，排查时只需回答「哪几条 overlay 命中了」。

```json
"default": { "topics": { "...": {} }, "heartbeat": {}, "push": {} },
"overlays": [
  {
    "id": "cgm_session_stopped",
    "priority": 10,
    "when": { "state": { "cgmSession": ["STOPPED"] } },
    "set": { "topics": { "CGM": { "enabled": false } } }
  },
  {
    "id": "ciq_off",
    "priority": 10,
    "when": { "state": { "controlIQ": [false] } },
    "set": { "topics": { "CONTROL_IQ": { "enabled": false }, "STATUS_BATCH": { "intervalMs": 300000 } } }
  },
  {
    "id": "x2_legacy_firmware",
    "priority": 20,
    "when": { "model": ["TSLIM_X2"], "firmware": { "flavor": ["LEGACY"] } },
    "set": { "topics": { "PROFILE": { "intervalMs": 120000 } } }
  }
]
```

**`when` 的键是白名单，不是表达式**（刻意不支持布尔表达式/脚本，否则会退化成无法自检的规则引擎）：

| 键 | 取值 | 来源 |
|---|---|---|
| `model` | `TSLIM_X2` / `MOBI` | `PumpCapabilities` |
| `firmware.flavor` | `LEGACY` / `V2_5` … | 现有 `observedEngine` 与 API version |
| `firmware.min` / `firmware.max` | 版本字符串 | 泵 API 版本；按数字段逐段比较 |
| `state.cgmSession` | `STOPPED` / `RUNNING` / `UNKNOWN` | `DataStore.cgmSessionState` |
| `state.controlIQ` | `true` / `false` | `DataStore.controlIQEnabled` |
| `state.bolus` | `IDLE` / `IN_PROGRESS` / `EXTENDED` | 大剂量会话容器 |
| `state.screen` | `ON` / `OFF` | 现有可见性判定 |
| `state.link` | `CONNECTED` / `LINK_SILENT` / `DISCONNECTED` | `DiagMonitor` |

**匹配与合并规则（必须确定性）**：

1. `when` 内所有出现的键都命中才算命中（AND）；未出现的键不参与。
2. 命中的 overlay 按 `priority` 升序应用，**后者覆盖前者**；同 `priority` 按数组顺序。
3. `set` 只做**键级覆盖**，不整块替换分组（沿用 §4.5.2 深合并口径）。
4. 每个最终生效值要记住「被哪条 overlay 最后写入」，输出到 `effectiveFrom`（见 4.6.5），便于回答「这个 300000 是哪来的」。

#### 4.6.3 60 秒心跳：不可关闭的兜底节奏

用户口径「60 秒固定查询」落成 `heartbeat` 段，它的作用是**证明链路还活着**，而不是给页面供数：

```json
"heartbeat": {
  "enabled": true,
  "intervalMs": 60000,
  "topics": ["STATUS_BATCH"],
  "neverDrop": true
}
```

- **任何 overlay 都不能把 `heartbeat` 关掉或清空 `topics`**；校验阶段发现即整条 overlay 拒绝（`POLICY_REJECTED`），并在 `diagnostics` 说明。
- `intervalMs` 钳制 `30000..300000`；`enabled` 只允许在**调试开关**里关，不允许由策略文件关。
- 心跳在预算降级里**最后才降**（`neverDrop: true` 等价于优先级高于 `P0_CONFIRM` 的保留项）。
- 心跳与页面轮询是两件事：某 topic 被 overlay 设成 `enabled: false` 后，心跳仍按自己的 `topics` 发。这样「页面全关」不会把链路变成盲区。

#### 4.6.4 推送作为条件：两种用法，都不产生新发送

| 用法 | 语义 | 配置 |
|---|---|---|
| **抑制（suppress）** | 收到该类推送后，认为对应 topic 已新鲜，在窗口内不再轮询 | `push.suppress[]`：`{ pushType, topics, suppressForMs }` |
| **升格（promote）** | 收到该类推送后，临时把某个状态维度置为指定值，从而命中相应 overlay | `push.promote[]`：`{ pushType, state, holdMs }` |

- `pushType` 是**代码维护的枚举**（`Message.simpleName` 或通知 ID 的分类结果），属于「发什么」的一部分，不进配置；配置只引用它。
- `suppressForMs` 必须 `≤ 5 × topics[].intervalMs`，避免「一条推送把某 topic 永久静音」。
- 抑制到期后**必须补发一次**（不依赖下一次自然 tick），否则推送停摆时该 topic 会无限变旧。
- `promote` 的 `holdMs` 到期后自动回落，不需要额外的清除事件；重复推送只延长 `holdMs`，不叠加状态。

> 为什么强调「不产生新发送」：推送驱动的查询很容易退化成「收到什么就立刻回问什么」，那等于把泵的推送变成 App 的请求放大器——正是本轮要收敛的对象。

#### 4.6.5 兜底矩阵（每一层都要有下家）

| 失效情形 | 兜底 | 可观测 |
|---|---|---|
| 配置文件缺失 / 解析失败 | `FALLBACK_QUERY_POLICY`（§4.5.1 已有） | `policy.source=FALLBACK` |
| 一条 overlay 都没命中 | `default` 原样生效 | `effectiveFrom` 全为 `default` |
| overlay 条件互相矛盾 | 按优先级最后写入者胜出，不报错 | `effectiveFrom` 可回溯 |
| 配置把某 topic 长期关掉 | 心跳仍发；`enabled:false` 的 topic 在 stats 里标 `DISABLED_BY_POLICY` | `opCodeCounts` 中对应该 topic 的键停止增长 |
| 推送抑制导致某 topic 长时间不发 | `suppressForMs` 封顶 + 到期强制补一次 | `lastRequestAtMillis` 不再增长即异常 |
| 策略算出间隔大于心跳间隔 | 取 `min(topicInterval, heartbeat.intervalMs)` 作为实际节奏 | `effective` 与 `observed` 对比 |
| 泵静默（`LINK_SILENT`） | 心跳 + 重连序列（§4.5.3 `reconnect`） | `diag/state.lastRxAgoMs` |
| 配置生效但行为没变 | `effective` 与 `observed` 告警（配置说 300000，统计里仍是 60000 就说明没接上） | stats 的 `policy.effective` vs `opCodeCounts` 时间分布 |

**「observed 才能证明生效」**：与 §4.5.6 同一条原则。配置写得再对，只要 `/api/query/stats` 里的实际发送间隔没跟着变，就按未生效处理。

### 4.7 第一个迁移对象：大剂量 V2 的查询（2026-11-10 落盘）

#### 4.7.1 事实：V2 曾自建了一套微型查询器

`BolusPollScheduler` 在本该只做「何时该问」的位置，把查询器出口的三件事自己实现了一遍：

| 它做了什么 | 应归属 | 现状 |
|---|---|---|
| `currentInFlightAt` / `extendedInFlightAt` 单飞 | 查询器出口 | 与页面直发并存，两套在飞互不知情 |
| `lastCurrentAt` / `lastExtendedAt` 节流（10 s / 5 min） | 查询器出口 | 每新增一个查询点就要再抄一遍 |
| 直接 `sendPumpCommands(SendType.STANDARD, listOf(44 / 46))` | 唯一出口 | 绕开查询器 |

## 4.8 全量只读查询收口（2026-11-10 第 2 轮）

### 4.8.1 为什么不在页面逐个加门控

首帧双发的根因是 `LifecycleStateObserver(onStart)` 与 `LaunchedEffect(intervalOf(60))` 的 `tick = 0` 各发一批。按页面加 `if (tick > 0)` 能治，但要改 9 个页面 + 1 个子页，且以后新页面还会复发。改为在**物理出口**统一判一次。

### 4.8.2 分流点

`PumpCommHandler.command()` 是四个守卫之后的唯一真实下发点：手机 UI、手表转发、通知接收器、HTTP 调试口全部汇到这里。

| 类别 | 走向 |
|---|---|
| 只读查询（白名单） | `queryPort.request(...)`，同 opCode 单飞 |
| 控制 / 签名 / 确认 / 取消 | `dispatchDirect(...)`，原样直发 |

`queryPort` 由 `PumpCommHandler` 持有，进程内唯一；响应到达时在 `onReceiveMessage` 调 `queryPort.onMessage(it)` 清除在飞。响应对象自身的 opCode 未必等于请求 opCode，端口优先按 `getRequestProps()` 取请求侧。

### 4.8.3 白名单与判据

见 `shared/src/main/java/com/pumppan/controlx2/query/PumpReadOnlyQueries.kt`。pumpx2 的 `Message` 没有只读基类，控制与查询同在 `request` 包，只能按 simpleName 显式列举；名单来源是 `PumpTopic.fromRequestSimpleName` 覆盖的全部请求。

**白名单优先**：不在名单里的一律直发。漏判只退化成「少一层单飞」，不会误挡控制。

```kotlin
    val onReading: (PumpReading<*>) -> Unit,
)

interface PumpStateBus {
    /** 订阅；返回取消句柄。重复订阅同一 topic 由调度器合并。 */
    fun subscribe(sub: PumpSubscription): Cancellable

    /** 只读快照：值 + lastRxAt + 来源。UI 用它渲染年龄/降级。 */
    fun reading(topic: PumpTopic): PumpReading<*>?

    /** 断连/恢复由 BLE 层回调；不在这里发请求。 */
    fun onConnectionChanged(connected: Boolean)

    /** 诊断：最近 N 秒真实发出的请求数与合并/丢弃数。 */
    fun stats(): QueryStats
}
```

调度规则：

1. **合并**：同一 `topic` 的多个订阅取**最严格的 `maxAgeMillis`**，只发一次。
2. **去重**：`now - lastRxAt < min(maxAge)` 时**不发**，直接把现有 `reading` 回调给订阅者（带 age）。
3. **单飞**：同一 `opCode` 同时只允许一个请求在飞；超时才允许重发（沿用 `BolusPollScheduler` 的做法）。
4. **优先级**：发送队列按 `QueryPriority` 排序；P0 可以抢占，P2 在预算不足时直接推迟。
5. **降级**：请求失败 / 超时 / 断连 → 回调「最后已知 + age + 不可信原因」，由订阅者决定文案；**不在调度器里重试轰炸**。

### 6.2 需求表

| 需求 | 要哪类状态 | 最严格新鲜度 | 可用来源 | 能否降级 |
|---|---|---|---|---|
| 首页 IOB | `IOB`（`ControlIQIOBResponse`） | 视图刷新 ≤ **3 分钟**（超过不采信） | 本次查询 / 缓存（带 age） | 可：标「缓存 · N 分钟前」或「本次不可用」 |
| 横幅「正在输注什么」(#64) | `BOLUS_CURRENT` + `BOLUS_EXTENDED` + `LAST_BOLUS` | 输注中 ≤ **10 秒**；空闲 ≤ **5 分钟** | 泵真相层 `45` / `47` / `-73` / `-91` | 可：最后已知 + age；不确定时写「状态未知」 |
| 立即确认（发起/取消大剂量） | `BOLUS_CURRENT` | ≤ **10 秒**，发出后 10 秒无应答即失败 | `45` | **不可降级**：拿不到证据就不许报「成功/已取消」 |
| 延展输注 | `BOLUS_EXTENDED` | 运行中 ≤ **5 分钟**；结束窗口 ≤ **10 秒** | `47` / `-73` | 可：最后已知 + age；不得显示「未在输注」冒充 |
| 向导（一次性） | `IOB` + 泵参数 + CGM + `BOLUS_*` | 按下「计算」时必须**本次查询** | `ControlIQIOBRequest` + `BolusCalcDataSnapshotRequest` + `CurrentEGVGuiDataRequest` + `45` + `47` | 可：IOB 缓存 ≤3 分钟；输注证据不新鲜则本次不扣 |
| 历史回补 | `HISTORY_STATUS` | ≤ **10 秒**（仅回补期） | `59` / `-127` | 可：随时暂停，恢复后继续；绝不与 P0/P1 抢预算 |

## 7. 预算与优先级

### 7.1 降级顺序（用户确认口径）

**确认 / 取消（P0） > 状态类（P1） > 装饰类（P2）**

- P0：立即确认、取消、权限应答。**永不排队等待**，预算不足时抢占 P1/P2。
- P1：`45` / `47` / `-91` / IOB / 告警状态 / 基础率。允许 1 个轮次的延迟。
- P2：电池、CGM 图表刷新、历史回补、诊断面板、装饰性倒计时。可无限期推迟，断连时直接显示「暂停」。

### 7.2 硬闸（建议：先观测，再启用）

- 建议设**每分钟报文上限**：持续 **10 条/分钟**、突发 **20 条/分钟**（Bulk 请求按「1 次发送、N 条应答」计为 1 次发送）。
  - 依据：当前最坏组合（Dashboard 18 条 × 60 秒 + 旧通知 1 条/秒×60 + 周期 4 条/5 分钟 + 延展 1 条/5 分钟）在确认窗口内可轻易超过 60 条/分钟；而 BLE 往返在弱信号下会到秒级，10 条/分钟是保守上限。**该数值是工程推测，需用 `DiagScreen` 的「近 10 秒查询次数」观测校准后再定。**
- 硬闸的落点：**调度器发送前**统一计数；超限时 P2 直接丢弃（记诊断），P1 延后一个轮次，P0 仍然放行并记录「预算超限下的 P0」。
- 硬闸必须带**诊断计数**（合并次数 / 去重命中 / 丢弃次数），否则无法复查是否真的省下了请求。

### 8.3 迁移可分步

- **0 步（只登记与旁路）**：见 §3.8。不改行为，只产出基线；是后续所有删除的依据。
- **A 步（只加观测，不改行为）**：`DataStore` 关键字段补 `lastRxAt`；`DiagScreen` 展示每 topic 的年龄与近 1 分钟请求数；页面先把年龄显示出来。
- **B 步（只改「何时发」）**：引入 `PumpStateBus`，先接管旧通知 1 秒×60 与 7 处 60 秒刷新；周期任务保持原样做兜底。
- **C 步（收编周期任务与历史）**：周期任务改为订阅；历史回补进 P2 预算；启用硬闸（先告警模式，再拦截）。

每一步都可独立回滚；0/A 步不改变任何发送行为，风险最低。

### 8.4 轮次收尾定义（先写死，避免「差不多完成了」）

- **B 轮（发送态）收尾 = 四段全通**：向导能算 → 用户可改写 → 确认页 → 真的把 `-98` 发到泵；并由真机实际打一笔、核对泵侧记录与回执，才算 B 轮收尾。缺任何一段（尤其「真机打一笔」）都只能算「能算不能发」。
- **C 轮开工第一件事 = 「只收不发」实验**：先关掉全部主动查询（向导查询、页面刷新、周期任务、历史回补一并停），只记录收到的报文与时间戳，验证输注状态类报文（`45` / `47` / `-91` 等）在没有主动请求时是否会自己到来。
  - 结论直接决定横幅 / 输注状态观测层能否按「推送优先」设计：若确认自发推送，按 §5.4「该来没来才补」；若确认为纯请求-响应，则该层必须保留主动查询，只做去重与年龄调度。
  - 实验期间不启用硬闸、不改 BLE 库；只观测并留证，把 §11 的对应项从推断升级为实测。

## 9. 复查机制（必须随推进定期复查）

这套整理不是一次做完就完事。用户明确要求：**随着功能推进定期复查**。

### 9.1 触发点（准入规则）

- **任何新功能若需要泵状态，必须先在 §6.2 需求表里占一行**：要哪类状态、最严格新鲜度、能否靠推送满足、可否降级。
- **没有这一行，不许新增定时器、不许新增 `postDelayed` / `LaunchedEffect(intervalOf(...))` / 固定次数重试**。
- 新增订阅必须声明 `PumpTopic` + `maxAgeMillis` + `QueryPriority`；能复用已有 topic 的，禁止另开。

### 9.2 节奏

- 按迁移 **0 / A / B / C / D 每轮收尾时复查一次查询清单**（§2.1 表）。
- 复查问法是「**这条现在还必要吗**」，不是「这条有没有坏」。
- 复查产出：删除 / 合并 / 降级 / 保留 四选一，并更新 §2.1 与 §6.2；没有结论的条目要写明「暂留原因」。

### 9.3 判定口径

- **以推送为准**：只有实测证实的主动推送才允许「该来没来才补」；未证实的，一律按必须主动问处理。
- **只在「该来没来」时补查询**：先看 `lastRxAt`，再看容忍度；不满足就不发。
- **弱信号下降级顺序**：确认/取消 > 状态类 > 装饰类；P2 可静默暂停，P1 可延后一轮，P0 不降级。
- **复查时同时看预算诊断**：合并率、去重命中率、丢弃次数。如果某项功能让 P0 开始排队，直接判为设计错误。
- **任何「直发」都必须出现在诊断里**：没有 `requestDirect` 记录的直发，一律视为暗渠。

## 11. 证据等级与待验证

### 有实测支撑

- `45` / `47` / `-91` 在 3h12m、1685 条被动报文里**没有独立周期出现的证据**，总是成簇（同一秒级窗口 4 条依次到达，例：`13:05:02–13:05:06`、`14:14:01–14:14:05`）。
- 延展运行期间存在 **5 分钟空窗**（14:19:32 → 14:24:31），期间其他报文 116 条正常应答，`45` / `47` / `-91` 为 0。
- `-127 HistoryLogStreamResponse` 是请求触发的流式返回（203 条）。
- 泵上发起的大剂量，`45` 的 `bolusId = 0`，延展只在 `47` / `-73` 可见。
- IOB 字段断连冻结 23.9 分钟、恢复后新值低 1.80 U；用 `iobUpdatedAtMillis` 才能表达年龄。
- 泵主动事件（`QualifyingEvent`）25.6 h 实测：675 簇、9 类；`IOB_CHANGE` 630 次、p50 间隔 60.06 s；`EXTENDED_BOLUS_CHANGE` 6 次全部被 `normalizeQualifyingEvents` 吞掉（`TandemBluetoothHandler.java:306-312`）。

### 属于推测 / 待验证

- 「`45` / `47` 会被主动推送」——**未证实**；需要一次「全程不查询、只记录」的采样（至少覆盖一笔立即段 + 一笔延展）。
- 每分钟 10 条持续 / 20 条突发的预算上限——工程推测，需用诊断计数校准。
- 各页面 60 秒是否真的都需要——需按 §9.2 逐条复查（尤其 Dashboard 18 条 Bulk 是否可拆成不同容忍度）。
- 「延展结束窗口 10 秒」是否够快——需实测结束时刻的 `47` 应答延迟。
- 「空闲期补一条 `44`」是否必要——取决于横幅/输注观测层是否要在无会话时也显示「最近一次输注」。
- 历史回补最终是「取消开关」还是「降级为预算参数」——**待用户拍板**。
- **`109 ControlIQIOB` 与 `38 NonControlIQIOB` 是否可以互相替代**——**待验，见下面 V1**。此前按「两者同值、38 可作备源」表述，已撤回为待定。

### 待验项 V1：`109`（`ControlIQIOB`）与 `38`（`NonControlIQIOB`）的关系

> **当前状态：待定。** 「38 与 109 同值、可作等价备源」**不是结论**，已撤回。
> 唯一已实测的样本只覆盖**一个格子**：**无 CGM + CIQ 关闭 + X2**。不能外推到 CIQ 开启、有 CGM、或 Mobi。

**为什么必须降级**

两者在协议里是**两条语义不同的请求**：`ControlIQIOB`（108 → 109）与 `NonControlIQIOB`（38 → 39）。连字段集都不同——109 有 `mudaliarIOB` / `swan6hrIOB` / `mudaliarTotalIOB` / `iobType` / `timeRemaining`，39 只有 `iob` / `totalIOB` / `timeRemaining`。字面上就是两种不同行为。

"在一台 **CIQ 关闭、无 CGM 的 X2** 上数值恰好相等"，只能说明**该格内两条路当时吐出同一个数**，不能说明它们是同一个东西，更不能说明可以互相替代。

当前设备恰好同时满足两个"不适配"条件：① CIQ 未开；② 不是 Mobi。因此现有数据**天然不能代表** CIQ 开启或 Mobi 的行为。

**已实测数据（保留，但适用范围仅限 M1 格）**

- 采样条件：CIQ **全关**（49/49 `closedLoopEnabled=false`）、CGM **全停**（46/46 `SESSION_STOPPED`）、设备 **X2**。
- 应答量：`109` 63 条、`39` 112 条。
- 同刻配对 **5 对**（到达时间差 ≤3 s）：4 对 `mudaliarIOB == 39.iob`；1 对（12:58:30，Δ2.764 s）差 **−60 mU**，同一对 `timeRemaining` 也差 **−60 s**。
- `totalIOB`：5/5 完全相等。
- `iobType`：63/63 = 0（`MUDALIAR`）——即 109 在本设备上**从未**走过 `swan6hr` 曲线。
- `mudaliarIOB − swan6hrIOB`：全部为正，范围 **798–5232 mU**（两条曲线差异不小，`iobType` 选哪条会明显影响显示值）。

**条件矩阵（待采）**

**每格比什么**

- `109`：`mudaliarIOB`、`swan6hrIOB`、`mudaliarTotalIOB`、`iobType`、`timeRemaining`。
- `39`：`iob`、`totalIOB`、`timeRemaining`。
- 成对关系（每条都要记差值，不能只记"相等"）：
  - `39.iob` ↔ `109.mudaliarIOB`（主对照）
  - `39.iob` ↔ `109.swan6hrIOB`（判断 38 对应哪条曲线）
  - `39.totalIOB` ↔ `109.mudaliarTotalIOB`
  - `39.timeRemaining` ↔ `109.timeRemaining`
  - 两包的**到达时刻差**（谁先谁后、偏移多少秒）

**判定规则（先写死，避免事后解释）**

1. **认定"38 是等价备源"**：某格内 ≥10 对样本，`39.iob` 与 `109.mudaliarIOB` 的差值 **100%** 落在 ±60 mU（一个最小分辨率）内，`totalIOB` 100% 相等，`timeRemaining` 差 ≤60 s，且 `iobType` 恒为 `MUDALIAR`。→ 该格内可用 38 顶替 109。
2. **认定"38 语义不同、不可替代"**：任一对出现 `39.iob` 与 `109.mudaliarIOB` **和** `109.swan6hrIOB` 都不相等；或 `iobType` 在该格出现非 0 值、而 `39.iob` 只能对上其中一条曲线 → 两者 IOB 定义不同，38 只在明确对应某条曲线时才可用。
3. **认定"某型号/状态根本不应答其中之一"**：某格内持续只收到一条，另一条在多次请求后仍 0 应答 → 该格不存在"选源"，只剩唯一可用源；策略表要写成"该格只有 109 / 只有 39"。
4. **禁止跨格复用结论**：任一格若 `iobType` 出现 `SWAN6HR` 且 38 值更接近 `swan6hrIOB`，说明 38 的语义随设备状态漂移——不得用 M1 的结论推断 M2–M8。

**采集方式（只读，不改行为）**

- **只读**：不新增任何泵查询、不改发送逻辑、不动现有两套路径。用现有报文流（`/api/pump/messages` 与 `/api/comm/messages`）被动记录。
- **成对窗口 ≤3 秒**：两包到达时间差超过 3 s 即丢弃该对，避免拿不同时刻的 IOB 硬比。
- **样本量**：每格 ≥**10 对**；M1 现只有 5 对，需补足。
- **时长下限**：每格至少覆盖一次完整 IOB 变化周期（实测 `IOB_CHANGE` p50 ≈60 s，故 ≥10 对 ≈ ≥10 分钟有效连接）；M2–M4（有 CGM 或 CIQ 开）建议 ≥30 分钟，覆盖曲线切换。
- **收尾条件**：M1–M4 每格满 10 对且能按上面三条规则明确归属；M5–M8 待设备后同法补。

**结论落点**

- 验证通过后要改的是**「选源策略表」里的那一行**——即 §3.5 表的 **#7（CIQ 关）**；若结果分化，则拆成 CIQ 开 / 有 CGM / Mobi 各自的行。§3.4 的「CIQ 开关」行同步从"待定"改为具体判据，§3.7 #14 同步从"两套并存"改为确定归属。
- **在 V1 有结论之前，§3.4 CIQ 行、§3.5 #7、§3.7 #14 一律保持"待定/待验"字样**，不得写成定论。

**在待验结论出来前不许动的事**

- 现在**事件端默认发 38（`NonControlIQIOBRequest`）、UI 端发 108（`ControlIQIOBRequest`）**，两套**并存**。这是**现状事实**，不是"可删的重复"。
- V1 有结论之前，**不要**：删掉事件端的 38、把事件端改成 108、或把 UI 端改成 38。任何一边的改动都属于"凭猜测改行为"。
- 清单文档里"38 无消费者"只是**当前代码事实**（没有 `NonControlIQIOBResponse` 的处理分支），**不等于**"38 可删"。
