## §0 设计前提：注意力是会耗尽的资源（2026-11-09 补）

用户原话（大意）：**常年胰岛素输注本身是一笔很大的压力，注意力焦点会降级；没事的时候被打扰还好，一旦有事，重复输注是不可避免的；这一点靠泵拦截完全没戏。**

这段不是感慨，是本设计的前提，推出四条可执行推论：

| # | 推论 | 对本设计的具体约束 |
|---|---|---|
| P-1 | **默认人会忘，系统负责记账**。剂量、时刻、结果必须由系统自动留存并可事后查，不能依赖用户记忆 | 不能只依赖 `-91`（只保留最后一笔，6886 就是这样被 6887 顶掉的，见 §9.3）；「最近一次大剂量」与「我方观察到的每一笔」都要落在本机（§9.3-A / §9.3-B）。判据是**事后能不能回答「我最近打过什么」**，不是当时界面好不好看 |
| P-2 | **异常时刻不加操作步骤**。断连、低血糖、正在进食这些时刻，人的余量最少；此时任何新增确认、二次弹窗、强制跳转都是**负资产** | 与既有约定「不做判断、不给建议、只提示错误」同向，但这里要单独写明**异常场景**这个前提（不只是「怕麻烦」）：**异常时只减少摩擦，不增加摩擦**。§9.3-A 因此只能是信息呈现，不做拦截、不做「你确定要打吗」 |
| P-3 | **不指望泵拦截**。泵只知道「又收到一笔」，不知道用户忘了 | 重复给药的防线只能在我们这一侧：**记账 + 输入前的信息呈现 + 预约固化决策**。§9.3 案例已证明泵侧不会替我们兜底（两笔各 7 U 都被正常执行） |
| P-4 | **把重复决策固化一次**。预约/定时的真正价值是减少「再一次手工输入」的机会，而不只是省事 | 这是 [定时大剂量-设计.md](定时大剂量-设计.md) §0 动机的直接来源：预定那一刻这笔就进入账本（§9.3-C），后面不必再手输一遍 |

**边界**：以上四条都是**信息与记账**层面的手段，**不引入拦截、不给医疗建议**；不改变 §4.9.2 确认阶梯与 §4.9.3 轮询，也不把任何提示写入发送前的判据。

## §1 与旧文档的关系

旧稿的三段式（输入态 → 全屏执行态 → 流式日志）在结构上被推翻，改为「**线性分步 + 单页外壳**」。逐条对照：

| 旧稿结论 | v2 处置 | 原因 |
|---|---|---|
| 全屏流程页（`BolusFlow` 覆盖层）vs 多页跳转之争 | **已定：线性分步、单页外壳**（不新增 `BottomScaffoldState`，复用已展开的 BottomSheet 内分派；全屏降级为待验证备选） | 单页分步才可能做到「只改 `Landing` 2 行」；全屏需要新增状态 + 修 reset 白名单 |
| 执行态窗口停留、轮询 `CurrentBolusStatus` 至结束 | **作废：发完命令即销毁窗口**，后续靠常驻通知 + Dashboard 横幅 | 延展段可达数小时，占屏就无法再发普通大剂量（旧稿 L143-148 的诉求保留，承载方式改变） |
| 「CIQ 自动模式禁止扩展」 | **作废**：允许扩展，只把时长上限压到 2h（Mobi 为 8h） | 用户更正：原记忆来源是美敦力；Tandem 固件（Moonlight 7.4 起）即支持 |
| 三结局显示已输注剂量 | **作废**：结局三态（成功 / 取消 / 失败）**一律不显示剂量** | 2026-09-29 已决策，v2 沿用并写死 |
| 预设带 `successCount` / `lastUsedAt` / 「另存提示」 | **作废**：预设 = 纯预填器，不计数、不排序最近使用 | 预设目的是「少输几个字」，计数无产品意义 |
| 「官方 App / 第三方并发发起我们完全不知道」 | **作废**：泵连接需蓝牙 code，同一时刻只有一个 App 连着；泵本体发起的可读，失去的只是「发起前的输入过程」 | 见 §4 与缺口修正 |
| 5 个 `mutableStateOf<Boolean>` + 5 个 `AlertDialog` 并发可弹 | **作废**：改为单一 `BolusSessionController` 单一状态源 | 旧实现的结构性缺陷 |
| Dialog 承载执行态（`BolusDialogs`） | **legacy 分支保留原样，v2 完全不用** | 平行实现，不改上游 |
| `BolusDraft` 唯一契约 | **保留**（字段为 `nowMilliunits` / `laterMilliunits` / `extendedSeconds` + `BolusShape` + `BolusSource`；now/later 是「总量 + 百分比」拆分后的等价表示，全部为千分之一单位整型） | 输入与执行解耦的思路仍然正确 |
| 单位/缩放铁律（profile 原始值、协议 mg/dL） | **保留**：批次 A 只做直接输入，不涉及向导；批次 B 做向导时启用 | 见 §5 批次划分 |

## §4 状态机与实时性

### 4.1 三态判定

```kotlin
// 输入只有两个：pumpConnected、holder.session
fun isAnyBolusActive(now: Long): BolusActivity = when {
    !pumpConnected                                    -> Unknown
    holder.session == null                            -> Idle
    holder.session.isExpired(now)                     -> Idle
    now - holder.session.lastEvidenceAt > staleWindow -> Unknown
    else                                              -> Active
}
```

- `Unknown` **只由断连产生**（以及「已连接但会话证据断流」这一短暂窗口）；**不再**表示「可能有第三方 App 发起」。
- 会话痕迹过期 → 归 `Idle`（已知已结束，不该长期占屏显示 Unknown）。
- **`ACTIVE` 不区分立即 / 延展（2026-11-07 定案）**：统一一个 `ACTIVE`，形态只由 `expectedEndAt` 是否存在区分——存在即延展，不存在即立即。文案、相位与门控复用同一套，不新增枚举。
- `staleWindow`（2026-11-07 修订，数值待 #52 复核）：**无输注**维持 10 分钟（2× 5 分钟兜底）；**输注期**立即段 30 s（3× 10 s 轮询）；**延展段**到 `expectedEndAt` 后再给 5 分钟（覆盖 1 次兜底轮询 + `-91` 延迟），超时且无 `47` / `-91` 才落 `Unknown`。

### 4.2 消息驱动

- 单点入口：`MainActivity :: handleMessage` 开头一行 `BolusSessionController.applyMessage(message)`；controller 内部按报文类型更新 holder（`BolusPermissionResponse` / `InitiateBolusResponse` / `CurrentBolusStatusResponse` / `CancelBolusResponse` / `LastBolusStatusAbstractResponse`）。
- **兜底轮询（2026-11-07 修订）**：**无输注相位**沿用 5 分钟一次 `CurrentBolusStatusRequest`，防止会话长期停留在过期前的假 Active；**输注期**立即段每 10 s 查 `44`，延展段改为「连接时对账一次 + 每 5 分钟兜底」（结束有泵侧主动 `47`，见 §4.9.3）。
- 重连/冷启动**对账顺序四步**：`CurrentBolusStatus` → `ExtendedBolusStatus` → `LastBolusStatus` → 历史日志；对账完成前取消行保持只读。

### 4.3 断连期间 UI 契约

| 情形 | 取消行 | 形态 | 点击 |
|---|---|---|---|
| 已连接 + Active | 显示 | 可点（danger 色） | 发 `CancelBolusRequest(bolusId)` |
| 已连接 + 有痕迹但 id 未知 | 显示 | 可点 | 先查 `CurrentBolusStatus` 取 id；取不到则不发 |
| 断连 + 有痕迹 | 显示 | **只读** | 无动作，提示「未连接，无法发送取消」 |
| 断连 + 无痕迹 | 不显示 | — | — |
| 已连接 + 对账中 | 显示 | 只读，数秒 | 无动作 |

fail-fast：`pumpConnected == false` 时**不发送、不进入「取消中」UI**，且不得落到「取消失败」文案（那是「已发送但结果未知」的语义）。

副标题文案：Active → 「大剂量输注中」（**不给实时量**，§4.9.1）；延展段可附「预计 hh:mm 结束」（由 `expectedEndAt` 计算）；断连 → 「未连接，状态未知」；对账中 → 复用 `bolus_fetching_bolus_stat`。

上述五行统一由 `cancelRowState(connected, now)` 返回，取值为 `HIDDEN` / `READY` / `NEEDS_ID` / `READ_ONLY` / `RECONCILING`（S0 已实现）。它是 `isAnyBolusActive`（3 态）的细化：后者用于「是否允许发起新的大剂量」等门控，前者只决定取消行；两表对应关系为——`Idle` ↔ `HIDDEN`（断连无痕迹也归 `HIDDEN`），`Active` ↔ `READY` / `NEEDS_ID`，`Unknown` ↔ `READ_ONLY`（断连有痕迹）或 `HIDDEN`（断连无痕迹）。

### 4.4 取消行五态（`cancelRowState`）

| `cancelRowState` | 对应 §4.3 情形 | 与 `isAnyBolusActive` 的关系 |
|---|---|---|
| `HIDDEN` | 无会话 / 会话已结束 / 断连且无痕迹 | `Idle` 或 `Unknown`（无痕迹） |
| `READY` | 已连接、有 `bolusId` | `Active` |
| `NEEDS_ID` | 已连接、有痕迹但 `bolusId` 未知（先查 `44`） | `Active` |
| `READ_ONLY` | 断连但有痕迹 | `Unknown` |
| `RECONCILING` | 已连接且对账中 | 由 controller 置位，优先于其它状态 |

### 4.5 会话阶段与结局枚举（S0 已实现）

`SessionPhase`（10 态）：

| 阶段 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| `DRAFT` | 草稿在建，未发送 | 打开 v2 输入界面 | 用户点「输注」→ `PERMITTING`；或退出清空 |
| `PERMITTING` | 等待 `-94` 权限结果 | 已发权限请求 | 拿到 `bolusId` → `AWAITING_PHONE`；NACK → `FAILED` |
| `AWAITING_PHONE` | 已获权限，等待手机确认 / 发起 `-98` | 权限响应成功 | 发出 `-98` → `DELIVERING`；60 s 无证据 → `UNKNOWN`（§4.9.2，不重试）；明确 NACK → `FAILED` |
| `DELIVERING` | `-98` 已发，立即段在输注 | `-98` 发出或收到进行中状态 | 立即段结束且无延展 → `DONE`；有延展 → `EXTENDED_RUNNING` |
| `EXTENDED_RUNNING` | 延展段（方波/双波）进行中 | 立即段完成且 `extendedSeconds > 0` | 结束 → `DONE`；取消 → `CANCELLING` |
| `CANCELLING` | 已发 `-96`，等待结果 | 取消请求发出 | 响应返回 → `DONE` / `FAILED` |
| `DONE` | 本会话正常结束（含取消成功） | 收到完成/取消成功证据 | 15 s 自动收起 → `DRAFT`（计时只在页面可见时生效，2026-11-08 起无手动关闭按钮） |
| `ABORTED` | 用户主动放弃，未输注 | 确认页返回 / 权限前取消 | `clear` |
| `FAILED` | 明确失败 | NACK / Alarm / 发送前已断连 | `clear` |
| `UNKNOWN` | 状态未知（断连或证据断流） | 断连、`staleWindow` 超时、字段缺失 | 重连对账成功 → `Idle`/`Active` |

`BolusError`（5 值）与 `BolusOutcome`（sealed）：

```kotlin
enum class BolusError { NACK, ALARM, TIMEOUT, DISCONNECTED, UNKNOWN }

sealed interface BolusOutcome {
    data object Pending : BolusOutcome   // 尚未出结局
    data object Success : BolusOutcome   // 输注完成
    data object Cancelled : BolusOutcome // 用户取消（含部分输注）
    data class Failed(val error: BolusError) : BolusOutcome
}
```

- `NACK`：泵明确拒绝（`-97` `statusTypeId != 0`，含库枚举中不存在的 `1` / `nackReasonId != 0`）；**立即结束，不并入等待**（§4.9.2）。
- `ALARM`：阻塞、空储药器、低电量、复位、故障（说明书 13 章）。
- `TIMEOUT`（2026-11-07 收窄）：**不再**以「`-98` 后 30 s 无应答」判失败；60 s 仍无任何开始/结束证据一律归 `UNKNOWN`（§4.9.2），该枚举值仅留作统计标记，不得用于明确拒绝。
- `DISCONNECTED`：**发送前**已断连的 fail-fast；发送后断连只落 `Unknown`，不落失败。
- `UNKNOWN`：无法归类 / 字段缺失 / 60 s 无证据。

> **2026-11-09 位置定案（取代本节「App 内悬浮条」条目）**
>
> **通知页保持「报警」单一职责，不做任何改动，与上游对齐。实时输注状态不放通知页。**
> 若将来一定要放，只允许是「页面顶部一张独立卡片」，且**完全不进 `NotificationBundle`、不参与角标计数、不参与耗材流程拦截**；当前决定是「先不动」。
> 理由：该页语义是「现在有没有报警」，混入常驻输注状态会污染角标（永远亮红），报警与正常输注再也分不开；该页为上游原样，不动可避免将来同步上游时的合并债。
>
> **当初为什么判定不动（2026-11-09 补语境）**：原动机是想在这页加一个**大剂量入口**（理由「空着也是空着，加点东西不影响」）；核对该页职责后发现它是**报警播报 + 消除面板**，加常驻入口/卡片会**遮挡报警**，故判定不改。
> **这条约束的边界**：**不往里加常驻卡/入口、不把报警挤下去**；**不涵盖**「按机型切换整页」。
>
> **关联（已裁决，不构成冲突）**：X2 上按机型把通知页分派为「流水账」视图，见 [`通知页-流水账-设计.md`](通知页-流水账-设计.md)。该方案不往原页里塞常驻卡/入口，且报警条目在新页**置顶保留、不可被流水挤掉或折叠**，满足本段「不遮挡报警」的原意；裁决依据见该文档 §12.1。
>
> 输注状态的位置定案为三处，**通知页不在其列**：
>
> | 位置 | 职责 | 取消入口 |
> |---|---|---|
> | 首页卡片（电池行下、葡萄糖行上） | 展示状态 + 数据年龄 | **不提供**（避免同屏两个取消按钮） |
> | 底栏常驻细条（`BottomSheetScaffold` 的 `bottomBar` 内、导航栏上方；**非浮层**，仅活跃期占 40–48 dp 视口） | 任何页面可见 | **唯一常驻入口**，一键取消 |
> | 大剂量页「段二」 | 该页自带状态与取消 | 自带；**该页抑制细条**（位置排他，不判断窗口） |
>
> 关联记录（**只记录、不处理**，与横幅无关）：① 泵报警目前不镜像为系统通知；② 未读角标只在首页 / 通知页 / 耗材页活跃时刷新。

> **2026-11-09 实施原则：三位置行为一致，位置可逆**
>
> 首页卡片 / 底栏细条 / 大剂量页段二**行为完全一致，只是外壳不同**。实现上是**同一份派生 + 三个薄渲染**，不是三套逻辑：状态相位、文案、数据年龄、取消决策都在派生层（`bolus/state`），三处只负责摆放。
>
> 因此**选哪个位置是可逆的**，不构成「必须一次选对」的决策。真正的成本在派生层，那部分三处共用；先做哪一处都不算赌错，跑通后若觉得位置不合适，换位置改动很小。
>
> **第一步建议先做「底栏常驻细条」**：它同时满足「任何页面一键取消」这条硬约束，是唯一在任意页面都可见的入口；首页卡片与段二都是它的子集场景（卡片可只展示、段二自带取消），先做细条最不可能白做。

#### 4.6.5 全局常驻「上次大剂量」提示行（2026-11-06 追加）

| 项 | 定案 |
|---|---|
| 文案 | 「最后一次 X U 大剂量于 YY:ZZ」（`bolus_v2_last_bolus`）；有剂量无时间用 `bolus_v2_last_bolus_unknown_time` |
| 覆盖页面 | 三选项卡页、剂量与扩展页、确认页、取消输注页，以及完成/空闲共用的三段式页面（**每一步页面顶部；2026-11-08 起为「段一」，任何状态都在**） |
| 数据来源 | `DataStore.lastBolusStatusResponse`（**48/49** `LastBolusStatusResponse`：`bolusId`/`deliveredVolume`/`timestamp`），由 `MainActivity` 收到响应时写入；**不新造通路、不发请求** |
| 口径 | 取最近一次 `LastBolusStatusV2` 的 `deliveredVolume` + 时间戳，**包含被取消或部分输注的量**，与首页卡片同源。理由（用户原话）：① 取消也好、只打了部分也好，那都是实际发送到泵并被执行的命令，反映的才是真实发生的事；② 非要读「完全执行完毕」的历史记录反而麻烦，取消是出错后的特例，小概率且印象深刻；③ 提醒的作用是提醒，不是强制拦截；④ 与首页卡片同源，用户平时看的和提醒是同一个数，不会造成误判 |
| 强度 | ≤2 小时：警示色（`colorScheme.error`）+ 加粗；2–24 小时：`bodySmall` + `onSurfaceVariant`；>24 小时：整行不显示（**不设 ticker**，绝对时间不自行刷新） |
| 无数据 | **不显示**（`deliveredVolume <= 0` 时整行不渲染，不留占位） |
| 有剂量无时间 | 显示「最后一次 X U 大剂量，时间未知」（`bolus_v2_last_bolus_unknown_time`），不显示 1970；弱化样式 |
| 时间格式 | 绝对时间：`pumpTimeToLocalTz` + `shortTime`（如 `14:32`），复用血糖时间口径 |
| 交互 | **不可点击、不带箭头、不跳转、不参与任何校验**，纯提醒 |

不做入口的理由：入口等于「一键重复上次剂量」，容易被误当成快捷补药；提示的职责只是拦一下手，不是提供操作路径。

#### 4.6.6 验收点

1. **0:100 纯方波不计"已完成"**：`totalVolume == 0 && extendedVolume > 0` 时，`-98` 成功后直接进取消页，几秒后退横幅；不出现「已完成」文案。
2. **输注期间不给第二入口**：`CONFIRMING` / `UNCONFIRMED` / `DELIVERING` / `EXTENDED_RUNNING` / `CANCELLING` 时**段三整段不出现**（入口与返回都不渲染，不是置灰）；延后段在跑同样不允许发起第二笔（2026-11-08 起「二选一页」作废）。

| 10–60 s | 任一确认证据到达 | 立刻切回「已开始输注」 | `DELIVERING` |
| 60 s 仍无证据 | — | 「状态未知：无法确认是否已开始，请查看泵」；保留取消入口 | `UNKNOWN`；**不给重试按钮** |
| 任意时刻 | `-97` 返回 `statusTypeId ≠ 0`（含库枚举中不存在的 `1`） | 立即报错结束 | `FAILED(NACK)`；不得并入「继续等待」，也不得按未知处理 |

> **60 秒不重试**：命令可能已发出、只是回包丢失，重发等于加倍给药。取消入口照常保留，用户可先看泵再决定。
> **明确拒绝 ≠ 超时**：`-97` 的非 0 状态是泵的确定答复，必须立刻结束；`BolusError.TIMEOUT` 只作统计标记（见 §4.5），不得把拒绝归入其中。
> **本阶梯只适用于本 App 发起的立即 / 双波立即段**：纯延展（泵本体发起、`requestedNow=0`）的 `45` 从进入 `DELIVERING` 起就是 `bolusId=0`，**不能**用 `45 bolusId≠0` 判「已开始」；延展的开始 / 结束一律以 `47` 为准（§4.9.4、出处表 D14）。

#### 4.9.9 发起前的「已有进行中」提示（通用规则，本轮新增，**未实现**）

适用于**每一次**大剂量发起（普通、预设、C 轮链式），不是某一批次专属分支：

1. **发起前检查**：每次进入发送前（点击「输注」或确认预约），检查是否已有进行中的大剂量会话——包括本 App 发起的，以及通过 `47`/`45` 识别到的泵上发起。

#### 4.9.11 真机卡死 / 启动闪退缺陷（2026-11-08 定位并修复）

**修复口径**（均已在代码落地）：

1. **`-94` 不再建会话**：权限只表示「可以发」，会话由 `onInitiateSent`（`-98` 发出）建立；已有会话时迟到的 `-94` 只刷新证据，不回退状态。流程中途退出不会再留下无出口的 `CONFIRMING`。
2. **取消终态兜底**：新增 `timing.cancelConfirmMs = 10000`；`onTick` 的 `CANCELLING` 分支超过窗口仍无 `-95`/`-91` → `UNKNOWN + Failed(TIMEOUT, fromCancel=true)`。`cancelStatus` 的 FAILED 阈值与状态机**同源**，界面「最长 10 秒」不再是空话。
3. **迟到报文不回退**：`CANCELLING` 下收到 `-97` 成功只刷新证据，不写 `ACTIVE`。
4. **过渡态不还原**：恢复时 `CONFIRMING/UNCONFIRMED/CANCELLING` 一律作废并清掉落盘，交给冷启动只读对账（`44/46/48`）重新发现真实会话。任何无法识别/无法映射的落盘状态同样作废，不自动发、不自动取消。

#### 4.9.12 真机第三轮：旧确认弹窗抑制、三段式页面与「关闭」失效（2026-11-08）

**问题与根因**

| # | 现象 | 根因 |
|---|---|---|
| 1 | v2 确认输注后，前景仍压着上游老对话框（「大剂量请求 / 0.05 单位，来自 phone / 拒绝 / 确认 0.05U」） | `BolusManager.confirmBolusRequest` 在进入任何接收器之前就自己发「待确认」通知与 `TO_SERVER_BOLUS_CONFIRM_DIALOG`；阈值默认 0 → 必走该分支，与 v2 确认页重复确认 |
| 2 | 结局页点「关闭」无反应，1–2 分钟后才回空闲 | UI 直接调 `holder.clear()`：只清内存/落盘会话，**没有 `pushState()`**，`sessionState` 仍是旧快照 → `deliveryToPage` 继续返回 `DONE`；直到下一条泵报文（如 `44` 空态）才刷新。15 s 计时其实已到点，同样因为不推 UI 而看不到 |
| 3 | 完成态与空闲态整页换脸，只有一行不同却整块跳 | `DONE` 用独立的 `BolusDonePage`，`DRAFT` 用动作表，两套结构互相替换；顶部还有重复的进行中横幅 |

**修复口径**（均已在代码落地）

1. **旧确认弹窗只在 v2 的 phone 请求抑制**：`confirmBolusRequest(..., autoApprove = true)` 跳过旧通知与 `TO_SERVER_BOLUS_CONFIRM_DIALOG`，但**仍走同一条发送链路**：`PendingIntent` → `BolusNotificationBroadcastReceiver.INITIATE` → `InitiateConfirmedBolusSerializer` 签名 → `TO_SERVER_INITIATE_CONFIRMED_BOLUS` → `sendPumpCommBolusMessage`（真正发 `-98`）。该分支只由 `CommService` 在 `BolusRouter.controllerMode == V2` 时传入；**WEAR / legacy 路径完全不变**。接收器收到 `silent` 时不再画旧式「请求中」通知。
   - 安全边界：v2 确认页本身就是确认动作，抑制只作用于**确认 UI**，不影响发送。其他来源（wear、legacy）仍保留原有二次确认，避免「抑制」变成「没人能确认」。
2. **结局页关闭走协调器**：新增 `BolusSessionController.dismissFinished()`（只清 `isFinished` 的会话并复位 `outcome`，进行中的会话一律不动）与 `BolusEntryCoordinator.dismissFinish()`（多一步 `pushState()`）。15 s 自动收起改调该入口。
3. **三段式页面（最终形态）**：段一 `LastBolusReminder` 常驻；段二固定标题「大剂量」+ 一句状态（`StateDescription`，由 `delivery.state` + `outcome` 派生）；段三「新的大剂量 / 返回」。`DONE` 与 `DRAFT` **共用同一个组件调用**，只换段二文案 → 不换脸、不重排。进行中横幅组件删除。
4. **输注期间不给第二入口**：`CONFIRMING / UNCONFIRMED / ACTIVE / CANCELLING / UNKNOWN` 时段三**整段不渲染**；`EXTENDED_RUNNING` 也不再提供「追加普通大剂量」（`BolusEntryPage.EITHER_OR` 删除，`deliveryToPage(ACTIVE)` 恒为 `CANCEL`）。`startFlow` 只允许从 `DRAFT` / `DONE` 进入输入页。
5. **无手动关闭按钮**：完成态段三已含「新的大剂量」，可直接往下走；15 s 后段二换回空闲文案（计时只在 `RESUMED` 累计），不再需要点「关闭」。

#### 4.9.13 真机第四轮：v2 发送路径确认（2026-11-08）

**证据**：同一天在真机上连续发起两笔 0.05 U 普通大剂量——第一笔正常输完，第二笔在输注中取消；两次行为均符合预期，页面走的是 v2 三段式，**未再出现上游旧确认对话框**。

### 5.3 向导的定位

- 向导是**计算器**：用户填碳水、校正血糖（指尖 / 传感器）等参数，由它**算出胰岛素剂量**；直接输入入口则是用户**自己填胰岛素单位数**。
- 两者**输出同一个 `BolusDraft`（`nowMilliunits` / `laterMilliunits` / `extendedSeconds` + `BolusShape` + `BolusSource`）**，走**完全相同**的发送与状态机链路；差别只在 `BolusSource = CALC`（枚举取值 `MANUAL` / `CALC` / `PRESET`）。
- 因此向导**不改变主流程、不新增发送路径、不阻塞批次 A**。
- 展开设计（说明书事实、公式来源与差异、参数可得性、分步实施）见 [docs/old/大剂量向导-初稿.md](../old/大剂量向导-初稿.md)（**已归档**；实施口径见 §5.9）。

### 5.9 B 轮（大剂量向导）实施口径（2026-11-08 用户拍板，已实施）

> 本节取代 §5.2 / §5.4 的「只占位、不写代码」。向导已接入 WIZARD 标签并走通：输入 → 结果 → 确认 → 复用既有草稿与发送链路（`BolusSource.CALC`）。

**1）跨标签保留输入（留）**

理由：算出的胰岛素值需要人工判断；明显不对时用户必然要返回核对哪个输入填错了。「返回上一步仍能看到原输入」是流程成立的前提，不是便利性。

- 状态放在 `BolusWizardRuntime`（进程内唯一一份），不在页面组合里；切标签、离开标签页都保留。
- 只有三种情况清空：用户按「清空」（X）、流程完成、成功发送。

**2）`-98` 不上报碳水 / 血糖 / IOB（确认不报）**

理由（用户口径）：**不留下可追溯的医疗记录，开源软件不该承担这种责任**。

- 该理由提升为**可复用原则**：以后遇到「这个数值要不要存」，默认按此判。
- 配置键 `wizard.reportCarbsToPump` / `reportBgToPump` / `reportIobToPump`，默认全 `false`；需要变更只改配置，不改代码。

**3）血糖字段常驻，手动指血是主路径**

- 字段常驻，只是不用 CGM 强制预填：CGM 有实时值就预填且可改；没有就留空等用户输指血。
- 不做 LastBG 回落；「空」不等于 0（与 #61 三态一致）。
- 内部只存一个 canonical 值：mg/dL 整数；mmol 只是显示换算（1 mmol/L ≈ 18 mg/dL），回显保留一位小数。
- mg/dL 禁小数点、整数输入；mmol 强制一位小数（13 也显示 13.0）。
- 换单位从 canonical 值重排，不回读旧单位文本：100 mg/dL → 5.6 mmol/L → 100 mg/dL，不走样。
- 该血糖值只用于本机计算：不进 `-98`、不落盘、不进任何日志。

**4）范围按型号分表，全部进配置**

| 用途 | 配置位置 | 值 |
|---|---|---|
| 手动指血输入 | `wizard.fingerstick` | mg/dL 20–600；mmol/L 1.1–33.3 |
| CGM 预填（默认 / 未知型号） | `wizard.cgmPrefill.default` | 40–400（保守交集，宁可少预填） |
| CGM 预填（按传感器型号） | `wizard.cgmPrefill.bySensor` | DEXCOM_G6 40–400、DEXCOM_G7 40–400、LIBRE 40–500 |

越界的 CGM 值视作不可用，**不预填**；代码里不写死任何上下限。

**5）错误只陈述事实**

发现输入不对就判非法并保持非法，直到用户输入正确；程序**不做判断、只提示错误、不给建议**。文案只陈述事实（超出范围 / 格式不对 / 位数不对），不推测原因、不提示怎么改。

**6）计算器入口守卫（与输入框层分开）**

- 输入框层：给用户看的三态校验，挂在字段值上（#61）。
- 计算器入口层：给程序兜底，进计算器前统一规范化 —— 血糖必须是整数 mg/dL、碳水整数克、剂量 mU 整数。两层各管各的，不合并。
- 血糖带小数（上游换算漏了）：四舍五入后照常计算，**不抛异常、不中断**；只留一条本地诊断记录（`Timber`，不含任何医疗数值）。
- 舍入用 `roundToInt()`（half-up）；`kotlin.math.round` 是半值取偶，不符合「四舍五入」。

**7）输入快照层与过期判定（2026-11-08 修订：主动查询为主，缓存兜底）**

- `WizardSnapshots.build` 一次固定：CGM 值 + 本地收到时间、泵参数（ICR / ISF / 目标血糖 / Max Bolus）与 IOB；泵参数和 IOB **各自判过期**，参数过期不连带作废 IOB。
- **主动查询是主路径**：进入 WIZARD 标签、以及按下「计算」时，都要**真向泵发一次只读请求**（`BolusCalcDataSnapshotRequest` + `CurrentEGVGuiDataRequest` + `ControlIQIOBRequest` + `CurrentBolusStatusRequest` + `ExtendedBolusStatusRequest`，`SendType.BUST_CACHE`）。**读取脉冲之后到达的那份读数**才算「本次查询」；早于最近一次查询发起的读数一律标「缓存」。
- **IOB 取值顺序（严格按序）**：① 先发一次真实查询，成功 → 用 `ControlIQIOBResponse` 的新值，正常扣减；② 查询失败 / 超时才看缓存，缓存报文距现在 **≤ 3 分钟**（`wizard.iobStaleAfterMs = 180000`）可用；**> 3 分钟不予采信** → 「活性胰岛素本次不可用」。
- **输注否决（不扣减）**：近 **5 分钟**（`wizard.recentInfusionVetoMillis = 300000`）内存在新的输注记录 —— 本机发送的（`InitiateBolusResponse`），或泵历史里新增的（`LastBolusStatus` 的记录时刻）—— 或泵真相层显示正在输注 / **延展进行中**（`47` 进行中，`45` 的 REQUESTING / DELIVERING），一律视为 IOB 不可靠，本次不扣。
- **设计约束（不可用缓存冒充本次查询）**：App 的 `iobUnits`（含 HTTP `/api/pump/current` 里的那个字段）来自 `ControlIQIOBResponse`，由 `CommService` 的周期任务**每 5 分钟**才请求一次（`periodicUpdateIntervalMs = 5 min`），**且不标注报文时点、断连期间整块冻结**（实测最长冻结 23.9 分钟，恢复后首个新值低 1.80 U）。向导**不得**拿 `/api/pump/current` 或内存里的 `iobUnits` 当作「本次查询」。
- 泵参数超过 `wizard.snapshotStaleMillis`（默认 120 s，缓存）即不可参与计算：保留回显并明确说明本次无法计算（不会拿过期参数冒充）；CGM 超过 `wizard.cgmStaleMillis`（默认 300 s）视为读不到。
- 进入 WIZARD 标签的取数按 `wizard.fetchThrottleMillis`（默认 10 s）节流；「计算」前的查询**强制发起**，不受该节流限制。
- 查询失败 / 超时（`profile.requestTimeoutMs`）才退回缓存：界面标「缓存 · N 分钟前」，并按各自的阈值判过期。
- 结果页冻结当时的血糖、泵参数与 IOB 判定，返回输入页再前进不会因数据刷新悄悄换掉计算依据。

**9）结果页呈现（竖排公式，2026-11-08 追加口径）**

结果页不再是一行长式子，而是按段竖排，每段「标题 + 数值」一行、下方小字写算式与来源：

```
餐食                    3.00 U
30 g ÷ 10 g/U
校正                    1.40 U
(180 − 110) ÷ 50 mg/dL/U
已扣活性               − 0.80 U
泵 · 12 分钟前 · 原始 IOB 0.80 U
────────────────────────
建议                    3.60 U
```

- **硬约束**：界面上的数全部来自同一次快照、同一次计算，展示层只做排版与单位换算，**不再算第二遍**。用户拿计算器核对差 0.01 整页就失信。
- **缺项显式说明**：未填血糖 → 「未填血糖，本笔不做校正」；未填碳水 → 「未填碳水，本笔不计餐食」。空不是零，不能悄悄按 0 参与。
- 血糖落在目标与低血糖阈值之间时写「血糖未高于目标，本笔不校正」，而不是摆一个 0 的除法算式。
- 校正段为负时如实带负号显示；总量仍按既有截零规则，但负号不抹掉。
- 血糖段与中间量（目标、ISF、除法算式）随单位设置一起换算。
- 已知取舍：mmol 模式下显示值保留一位小数，而结果按 mg/dL 计算，二者可能有约 0.01 U 的显示差；这是换算取整带来的，不是两套计算。

**10）活性胰岛素（IOB）**

- 取**上游原始值，本机不加工**（不重算、不按时间外推、不扣基础率）。宁可显示略旧的值，也不显示本机自算的「更准」值 —— 用户会拿它跟泵首页那个数比。
- **采信判据以「是否本次查询」为主**：本次主动查询之后到达的读数视为新鲜，标「本次查询 · N 分钟前」；查询失败 / 超时退回缓存时标「缓存 · N 分钟前」。
- **缓存兜底窗口 3 分钟**：`wizard.iobStaleAfterMs = 180000`。只有缓存读数超过 3 分钟才不显示数值、不参与运算。
  - 按实测衰减 −0.09～−0.11 U/分钟折算，3 分钟窗口对应误差约 **0.3 U**；**若要求容差 ≤0.2 U，窗口需 ≤2 分钟**。
  - **不许把 5 分钟窗口说成 0.1 U 以下的误差**：那是把窗口误当成 1 分钟级算出来的，与实测不符；5 分钟窗口的真实量级是 **≈0.5 U**。这条写在这里，避免后续照着错误数字做决策。
- **输注否决窗口 5 分钟**：近 5 分钟内存在新的输注记录（本机发送的，或泵历史里新增的），或正在输注（含延展）→ IOB 视为不可靠，**不扣减**。
  - 理由是**方向性风险**：那段时间的缓存值偏**低**，扣得少 → 建议剂量偏高，方向危险。
  - 延展必须由**泵真相层**（`47` / `-73` 进行中；`-74` 只是请求 opcode）判定，不能只看本机会话状态，否则泵上起的延展会漏掉。
  - 依据：本次 3U / 900 s 方波实测，IOB 每 5 分钟整块 **+1.00 U**，段间只衰减；延展期间实时值最多滞后约 **1 U**，比单纯「时间戳过期」严重。
- **两条不可用文案必须分开**（都写明本次未扣除，不给结论、不劝退）：
  - A（查询失败且缓存超 3 分钟 / 从未收到）：「活性胰岛素本次不可用，本次未扣除」。
  - B（近 5 分钟有输注 / 正在输注，含延展）：「最近输注过大剂量，或有正在输注的大剂量，活性胰岛素可能不准确，本次未扣除」。
- **采样结论（2026-11-08 实测，可作为因果依据）**：
  - `/api/pump/current` 的 `iobUnits` 只跟 `ControlIQIOBResponse` 更新，**断连就整块冻结**（实测冻结 23.9 分钟；恢复后首个新值低 1.80 U，6 分钟后累计低 2.242 U）；泵本身每次被真查询都给随时间推进的新值（60 秒间隔中位数 −94 mU）。
  - 结论：**问题在 App 侧缓存不标注时点，不在泵**。
  - 3U 方波那笔：IOB 每 5 分钟整块 +1.00 U 跳变、段间只衰减 → 台阶是**泵自己的记账粒度**，不是采样粒度。
- **界面措辞只陈述可确认的事实**：可以写「本次查询 / 缓存 · N 分钟前」，**不能写「泵刚计算」**这类对泵内部行为的断言。
- **待验证假设（不是既成事实）**：用户猜想「每次向泵申请，泵都会现算一个 IOB 值」。验证方法：打一笔大剂量后，间隔 1 / 2 / 5 分钟各查一次快照，看 IOB 是否按泵里配置的胰岛素作用时长自然衰减；衰减且与配置吻合 → 支持现算，数值纹丝不动 → 更像泵侧缓存。验证前文档与界面都不得把该假设写成结论。
- **用户观察（非手册确认）**：IOB 与 CIQ 是否开启无关；只要在泵上输入大剂量，泵就按配置的胰岛素作用时长（X 小时）计算 IOB，衰减规则由泵配置固定，不随闭环开关变化。
- **专家意见（2026-11-08，作为「为什么扣 IOB」的依据）**：
  - IOB 永远不可信，最终决断应当看血糖趋势；
  - 但「扣了比不扣好」：扣掉 IOB 后总量下降 → 高血糖风险上升、低血糖风险下降，而**低血糖的危险远高于高血糖**，因此扣减在方向上属保守选择；
  - 专家给出的「分时段采信不同 IOB 取值」经验做法，本应用**无法实现，明确放弃**（不是遗漏，是有意不做）。
- **时间戳核实结果**：`BolusCalcDataSnapshotResponse`（PumpX2 1.9.0）报文**不带时间戳**，报文头 `Message` 也没有。因此「N 分钟前」只能按**本地收到该报文的时间**计算；它能挡住「数据取来后放了很久」，但**挡不住泵下发的陈旧值**。此限制如实记录，规则不假装比实际更强。
- **周期任务约束**：App 的 `iobUnits`（含 HTTP `/api/pump/current` 的字段）来自 `ControlIQIOBResponse`，由周期任务每 5 分钟请求一次；它不是「本次查询」，向导里不得拿它冒充本次查询（见第 7 条设计约束）。

**13）已知疑点（暂不处理）**

- `VicoCgmChartTest > toCgmDataPoint_appliesPumpLocalTimezoneCorrection` 失败：`shared/UnitsRenderer.kt` 的 `pumpTimeToLocalTz` 用「当前时刻」的时区偏移（`TimeZone.getDefault().getOffset(Date().time)`）而不是该时间点自身的偏移，跨 DST 会差 1 小时。用户判断为地域性问题（国内无夏令时，无法验证），记为疑点，**暂不修、不要动 `UnitsRenderer`**。

**11）建议值可改，改后留对照**

建议剂量可在结果页改写；改写后**结果页与确认页都**显示「建议 3.60 U / 实际 4.00 U」。只摆实际值等于让用户改完就忘。改写值必须落在泵步进与上下限上（`BolusWizardValidation.dose` 三态），不合法就停在结果页，**不替用户取整**。

**12）受众语气**

向导面向新手：把算出来的数当真，所以公式可见、数值可改、来源时间齐全；但界面不出现替用户下结论、替用户背书的话。预约（C 轮）面向老手：只摆事实，不给建议。同一个原则的两面。

**待用户最终确认**

- `-98` 三项（碳水 / 血糖 / IOB）维持 0：已按用户口径确认不报，此处仅作为配置开关的默认值记录。
- 传感器型号识别目前只靠 G6 传输器 ID / G7 配置码；识别不到走 40–400。若要支持更多型号，只在配置里加 `bySensor` 条目。

## §6 预设

> 口径以 2026-11-05 用户逐条拍板的 12 条为准；旧的「6 组 / 单组 5 条」「最近使用置顶」「成功次数」全部作废。**2026-11-06 修订：新增入口从确认页移到第 2 页「+」按钮（存当前输入值）与第 1 页底部「新建」（建空条目），均按序号自动命名；预设页改为「短按选中 + 底部应用」（见 §4.6.8 与 §6.2/§6.3）。**

### 6.1 字段与库位置

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Long PK | 自增 |
| `name` | String | **默认由系统按序号自动生成 `1..12`**；用户可在预设页手动改名。手动改名时**去首尾空格后不得为空、不得与其它条目重名（忽略大小写）** |
| `sortOrder` | Int | 显式序号（界面显示 1…N）；默认按创建顺序追加，仅用户操作时调整 |
| `immediateMilliunits` | Int | 立即段，**绝对值**（毫单位） |
| `laterMilliunits` | Int | 延后段，**绝对值**（毫单位）；**0 = 非延展** |
| `durationMinutes` | Int | 延展时长（分钟；非延展恒 0） |

- 不存碳水、不存血糖、不存 CIQ 状态，**也不存百分比**（字段只有上表 6 个）。
- **为什么存绝对值而不是百分比（2026-11-06 存储口径变更）**：
  1. 泵的 BLE 协议收的是绝对值：`totalVolume`（立即段）+ `extendedVolume`（延后段），没有百分比字段；泵本体 UI 的百分比只是它自己的界面换算。
  2. 泵历史记录同样是绝对值（`requestedNow` / `requestedLater`），预设存绝对值后与取证口径一致，核对时不用再换算。
  3. 百分比乘总量会遇到步进舍入：同一比例在不同总量下会得到不同处方（例如 70% 在 0.45U 与 0.50U 上分成不同的两段）。预设本质是「重放某个具体处方」，必须存最终要发出去的绝对值。
- **百分比只作为 UI 辅助**：输入页仍可按 0 / 50 / 75 / 100 等比例调整，但每次调整立刻由 `BolusForm.splitByPercent()` 换算成绝对值写进草稿并参与校验；界面同时显示绝对值和派生百分比（`0.4U / 0.6U（40% / 60%）`）。反推由 `BolusForm.percentOf()` 完成（half-up 到整数，**只显示**）。
- **存储**：mobile 模块独立 Room 库 `bolus_presets.db`，表 `bolus_presets`，**schema v2**（v1 为「总量 + 立即占比」，见下）。不塞进上游 `:db` 模块（那是同步/历史库，预设是 pumppan 本地功能）。
- **v1 → v2 迁移**（`BolusPresetMigration.kt`）：重建表（旧列不能留在 v2 schema 里），保留 `id` / `name` / `sortOrder`；非延展整段进立即段、延后段与时长归 0；延展按 `later = roundToIncrement(total × (100 − nowPercent) / 100)`、`immediate = total − later`，按**建库时当前型号的步进**（X2 50 mU / Mobi 10 mU）取整；时长由秒换算为分钟。转换函数 `convertLegacyPreset()` 有单测。**绝不允许直读旧列**，否则会出现 0 值或双倍剂量。`BolusPresetDatabase.getDatabase(context, increment)` 传入步进，仅在数据库首次打开（迁移时）使用。
- 代码：`bolus/preset/` 的 `BolusPresetEntity` / `BolusPresetDao` / `BolusPresetDatabase` / `BolusPresetMigration` / `BolusPresetStore`；UI 在 `BolusPresetSection.kt`（入口）与 `BolusPresetDialogs.kt`（编辑对话框，直接编辑绝对值）。

### 6.2 数量、排序与命名规则

- **上限 12 条（硬约束）**：超过时拒绝新建并提示「预设最多 12 条」，**不做自动裁剪**。旧 `min(配置上限, 单屏可容纳)` 口径作废。
- **一屏不滚动**：入口页用双列紧凑格渲染，12 条 = 6 行；预设区自身不出现内部滚动。页面整体的滚动沿用原布局（与 12 条无关）。
- **排序**：固定顺序 + 界面上可见的序号 1…N；条目菜单提供「上移 / 下移」（选择「改序号」而非拖动：X2 小屏上格内拖动命中区小、误触率高，上移/下移一次一格更可控）。
- **程序自身不重排**：不按最近使用置顶、不计数成功次数、不按创建时间自动排序；只有用户点「上移 / 下移」才改变顺序。删除后只把剩余序号压成 0…N−1，保留相对顺序，不改变用户可见的先后。
- **插入位置（2026-11-06 增补）**：第 1 页「新建」时，未选中 → 追加到末尾；选中 → 插到该条**正后方**。插入后同样把序号重排成 0…N−1（`BolusPresetStore.saveNewAutoAfter`）。
- **命名（2026-11-06 修订）**：
  - **默认自动命名**：第 2 页「+」与第 1 页「新建」都取 `1..12` 中**最小未被占用的整数字符串**（`trim` + `ignoreCase` 比较）。用户不介入命名，不弹命名框。
  - **手动改名**：只在预设页长按 → 编辑对话框内可改（新建出的空条目也会立刻进这个对话框）。此时**不允许空名**、**不允许重名**（trim 后、`ignoreCase` 比较，中文不受影响），重名提示改名，覆盖时排除自己。
  - 结论：原「用户自由命名 / 重名检测 / 空名拒绝」**仍然成立，但作用域收窄到"手动改名"**；自动命名路径上不涉及重名检测（序号必然唯一），空名不会出现。

### 6.3 与流程的接触点（2026-11-06 修订）

1. **选中与应用**（取代旧「点一条只预填」）：预设是**独立标签**（§4.8），不再是流程第 1 步；标签内列出全部预设（空态「暂无预设」），**短按只选中**（单选，再点同一条取消；切换选中不影响草稿）。选中后点页面底部**「应用」**，才把立即段 / 延后段 / 时长（**绝对值**）填成草稿初值，并**跨标签切到「大剂量」标签的确认页**（不经过输入页）。用户可在确认页「上一步」回输入页再改，**程序绝不自动回写**。预设侧不做校验/裁剪（含 Max Bolus 与时长），超限统一交确认页判断。未选中时「应用」置灰；条目为**空条目（未设置数值）**时置灰并在点击时提示「该预设尚未设置数值」，**不带 0 U 进确认页**。
2. **编辑 / 删除**：在「预设」标签内，长按条目或点右侧菜单 → **修改 / 上移 / 下移**；编辑对话框**直接编辑绝对值**（立即段 / 延后段 / 时长分钟），延展时在框内显示派生的「立即% / 延后%」作为次要信息；**删除移到标签底部「删除」按钮**，弹二次确认后执行，删除后序号重排 0…N−1 并**清空选中态**。**输注进行中不禁止**编辑/删除，编辑对话框里不出现任何输注状态判断。
   - 跨标签交接：`applyPreset` 只写唯一草稿槽位（`step = CONFIRM`、`source = PRESET`），来源标签记「预设」；退出流程时按来源回到「预设」标签（§4.8）。
   - 预设清单与草稿互不持有副本：草稿始终只有 `BolusTabSession.draft` 一份。
3. **两条新增路径（并存，职责不同）**：
   - **第 2 页「+」**（2026-11-06 修订，替代旧「保存为预设」）：位置在第 2 页底部正中；本页校验通过才可点（不通过置灰并提示「当前参数不完整」）。把**当前输入页的数值**存为预设、**追加到末尾**、自动命名（§6.2）、上限 12 拒绝、成功 toast「已存为预设」、满额 toast「预设已满」；**不弹对话框、不跳页、不覆盖**。
   - **第 1 页「新建」**（2026-11-06 增补）：位置在预设页底部左侧。建一条**数值为空**的条目（0 U）：未选中 → 末尾追加；选中 → 插到该条**正后方**；自动命名后**立即打开编辑对话框**让用户填数值。取消对话框时**保留空条目**，格内显示「未设置」。满 12 条时与「+」一样拒绝并提示。
   - **为什么并存**：预设页的「新建」解决「先建条目、再填数值」的清单管理场景（用户从预设页直接管理 12 条）；第 2 页的「+」解决「正在调剂量，顺手存下来」的场景（数据源是当前输入值，不能从预设页拿到）。两者都是「新建」，但**数据来源与入口时机**不同，不合并。
   - 原「确认页保存为预设 + 对话框改名 + 新建/覆盖单选」**全部作废**；「用当前草稿覆盖预设」**不实现**（不存在覆盖语义）。

**按型号分叉（2026-11-06 修订）**：`totalVolume=0` 的纯方波、`-98` 的 11 参延展路径、`maxExtendedSeconds` 校验 —— **X2 全部不可用**（固件忽略延展字段，真机 6851/6852 定论）；**Mobi 可用**（上游 501 真实抓包 + 泵侧回写：`total=0` 纯方波合法、8h/28800s 接受、延展段 0.25U 也被接受、`bitmask=12`、`-96` 取消有效）。Mobi 分支从「已作废」**恢复为 A 轮任务**；本项目**未真机验证**（配置 `verified=false`，仅用于 UI 实验提示与本地取证日志，**不参与能否发送的判定**）。

### 7.3 百分比 → 毫单位（按型号步进）

> **【按型号分叉】**：X2 不能在 App 侧发起扩展，本节拆分规则**不进入 X2 发起路径**（X2 仅在展示泵本体已发起的历史/状态时参考同一取整口径）；**Mobi 保留本节完整拆分规则**（A 轮任务，未真机验证）。下方「X2/Mobi = 50」只共用**步进网格**。
>
> **【存储口径】**：预设库不存百分比（§6.1）。本节只用于**输入页**把百分比辅助值换算成绝对值，以及历史/展示口径；换算出的绝对值才是入库与发送的唯一依据。

取整规则：立即段 = `roundIncrement(total × percent / 100)`（half-up，就近到该型号的步进网格；X2/Mobi = 50，未知型号 = 25）；延后段 = `total − 立即段`。总量为步进的倍数时两段都落在网格上且总和守恒；总量不是步进的倍数由 App 拦截（`INCREMENT_NOT_ALIGNED`）。

下表按 **X2/Mobi 的 50 网格**（0.05U，用户已核实 X2）给出：

| 总量 | 50% / 50% | 70% / 30% | 0% / 100% |
|---|---|---|---|
| 0.40U（400） | 200 / 200 | 300 / 100 | 0 / 400 |
| 0.45U（450） | 250 / 200 | 300 / 150 | 0 / 450 |
| 0.50U（500） | 250 / 250 | 350 / 150 | 0 / 500 |
| 1.00U（1000） | 500 / 500 | 700 / 300 | 0 / 1000 |
| 3.50U（3500） | 1750 / 1750 | 2450 / 1050 | 0 / 3500 |

> 25 网格（未知型号的 fallback）下同样的例子会是 400@70% = 275 / 125、450@70% = 325 / 125；这两个值在 X2 上打不出来，不要写进 X2/Mobi 的示例。

校验式（毫单位整数域，依据 7.1 / 7.4）：

- **精度**：总量、立即段、延后段都必须是该型号 `bolusIncrementMilliunits` 的整数倍（X2/Mobi = 50，未知型号 = 25）；UI 输入按同一步进量化。
- 普通（无延后）：`50 <= total <= 25000`（0.05U–25U，门槛本身为 50 的倍数）；`total > 激活配置文件 Max Bolus` 时只给「继续 / 返回」，不硬拒。
- **扩展（Mobi 可用、X2 不可发起；X2 只读泵本体发起的记录）**：`clientMinExtendedCheck <= 延展段 <= 25000`（默认 400 是**客户端校验**，非泵下限；501 已用 0.25U 成功）；**「立即」段允许为 0**（0:100 纯方波；X2 App 侧不支持，`total=0` 被 `statusTypeId=1` 拒）；`0 < 立即段 < minImmediateMilliunits` 由 `IMMEDIATE_BELOW_MINIMUM` 硬拦（Mobi 配置为 0，恒不触发）；延后段 > 0；时长 `minExtendedSeconds`..上限（15 分钟–2h/8h）。校正量只进 `totalVolume`（Now），绝不进 `extendedVolume`。
- UI 不再使用「总量 0.40U 门槛」这一自定规则；但 pumpx2 的 11 参构造器仍按 `totalVolume >= 50 || totalVolume + extendedVolume >= 400` 做客户端兜底校验（协议常量不改，Mobi 的 `total=0` 需延展段 ≥400 才能通过）。
- `nowPercent = 100` 必须归一化为 8 参普通路径；`nowPercent = 0`（纯延后）同样走 11 参扩展路径（`totalVolume > 0` 时为立即 0 + 延后全部）。

### 7.4 输注精度（`bolusIncrementMilliunits`，按型号分档）

| 型号 | 步进 | 依据 / 状态 |
|---|---|---|
| Tandem t:slim X2 | **50（0.05U）** | **用户已核实**（2026-11-05） |
| Tandem Mobi | **50（0.05U）** | **未真机核实，暂按 0.05U**；若核实为 0.025U，只需改配置 `models.MOBI.bolusIncrementMilliunits`，不改代码 |
| 未知型号（识别不出） | 25（0.025U） | 配置 `default`；25 网格是 50 的超集，避免误拦现役机型的合法剂量 |
| 美敦力 | 25（0.025U） | 仅作参考对照，不参与 Tandem 型号判定 |

- 步进**可配置**并按型号分档：`BolusLimits.incrementFor(model)` / `forModel(model)`，代码内硬默认 25；外置配置 schema 的 `models[型号]` 覆盖 `default`（见 [阈值配置外置-设计.md](阈值配置外置-设计.md) §4/§5）。
- 校验与拆分都读该值：`BolusForm.validate` 的 `INCREMENT_NOT_ALIGNED`、`splitByPercent(..., increment)`；`10` / `25` / `50` 均可工作。
- 显示按步进固定小数位、**不裁尾 0**：X2/Mobi → 两位（`0.05` / `0.10`）；25 → 三位（`0.025` / `0.050`）；10 → 两位（`0.01`）；100 → 一位（`0.1`）。固定位数是为了让「看到的位数」与泵能打出的最小步进一致。
- 用户个人观察（**未做对照实验，仅记录，不改校验门槛**）：0.1–0.2U 实测血糖几乎无变化，怀疑泵内部误差较大，精细度可适当放宽。

### 7.5 Max Bolus / Max Basal 读取结论（2026-11-05 核实）

| 链路 | 报文 / 字段 | 落地位置 |
|---|---|---|
| 请求 | `GlobalMaxBolusSettingsRequest()`（Dashboard 批量 + 安全限制页单独刷新） | `Dashboard.kt:280`、`SafetyLimitsActions.kt:380-383` |
| 响应 | `GlobalMaxBolusSettingsResponse.maxBolus` / `.maxBolusDefault`（千分之一单位） | `MainActivity.kt:1025-1028` → `dataStore.maxBolusAmount`、`dataStore.globalMaxBolusSettingsResponse` |
| 渲染 | 「最大大剂量 当前 20.0 单位 / 默认 10.0 / 范围 1–25」 | `SafetyLimitsActions.kt:191-204` |
| Max Basal | `BasalLimitSettingsResponse.basalLimit` / `.basalLimitDefault` | `MainActivity.kt:915-917` → `dataStore.basalLimitSettingsResponse`；渲染 `SafetyLimitsActions.kt:218-241` |

- **当前值是泵实时上报，不是本地持久化**：存在内存 `MutableLiveData`；`DataStore` 无 `reset/clear`，所以**断连后仍显示最后一次值**；进程重启后为 `null`，页面显示「加载中」。
- v2 **只读 `globalMaxBolusSettingsResponse`**（同时能拿到默认值）；必须区分「`null` = 未知」与「断连残留」，依据 `connected` 状态 + `staleWindow`。
- 超限判断用 **`>`**（大于 Max Bolus 才提示「继续 / 返回」）；旧 `BolusWindow.kt:485-495` 的 `validBolus` 用 `>=`（等于上限即拒绝），v2 不复用该写法。
- 「范围 1–25 / 1–15 U/hr」是 `strings.xml` 里写死的文案，不是泵字段；与说明书 7.7 一致，可继续使用。

### §9.1 【已作废】通知每秒刷新的耗电（2026-11-07 由 §4.9 取代）

> **作废说明**：§4.9.1 定案「不做实时输注量监控与显示」，通知 / 横幅已没有每秒变化的数值可绘；§4.6.4 的「1 s 重绘（上限 60 s）」与本节议题一并作废。现在的口径是「仅在证据 / 相位变化时 `notify`，立即段 10 s 轮询 / 延展段 5 分钟兜底，回包无变化不重绘」（§4.9.3）。以下为历史记录，不再作为实现依据。

**（历史现状）**：v2 常驻进度通知在 `DELIVERING / EXTENDED_RUNNING / CANCELLING` 相位下，由主线程 `Handler` 每 1000 ms 重新渲染并 `notify()` 一次（`BolusNotifications.REFRESH_INTERVAL_MILLIS = 1000`，仅靠 `setOnlyAlertOnce(true)` 抑制重复响铃）。

**为什么可能费电**：每秒唤醒主线程、重建通知并跨进程提交给 SystemUI，输注期间持续（延展段可达数小时）；而正文多数时候只有时间/剂量的小幅变化，用户观感上不一定能看出 1 s 与 5 s 的差别。

**候选方案（只列，不实现）**：
1. 只在相位或剂量数值变化时刷新，其余不重绘；
2. 刷新间隔降到 5 s 或 10 s；
3. 保留 1 s，但仅在用户可见期间（屏幕亮、通知栏展开）刷新。

**（历史结论，已作废）**：曾定为「待真机观察耗电后再定；当前不改，维持 1 s 重绘」。2026-11-07 起由 §4.9.1 / §4.9.3 / §4.9.4 取代：不存在每秒变化的内容，1 s 重绘取消，改为证据 / 相位变化时才 `notify`。

### §9.3 真实案例：忘记已打过，又打一笔（2026-09 现场，2026-11-09 记录）

> 记录口径：只写现场已取到的报文数据与用户原话，不做推演、不加评价、不给建议。

**一笔一笔的事实**

| 笔 | `bolusId` | 起针（`-91` timestamp） | 请求量 | 实输 `deliveredVolume` |
|---|---|---|---|---|
| 第 1 笔 | **6886** | 约 **08:59:31**（`595069171`） | 7 U | 7000（09:01:44 在链上见到回报） |
| 第 2 笔 | **6887** | 约 **09:07:20**（`595069640`） | 7 U | 7000（重连后补回的 `-91`） |

- 现场断链窗口：**09:05:25–09:33:10**（约 28 分钟）。第 2 笔（6887）起针与完成都落在窗口内，App 当时**无任何可见性**——既没有会话，也没有通知，更没有取消入口。
- **用户原话**：「**单纯的忘记了。。。已经打了一笔**」。不是「不确定有没有打进去」，而是**忘了已经打过**，于是又在泵上打了第二针。
- 后果（重连后补上状态时读到）：**IOB 21.9 U → 27.3 U**，耗材 **235 → 230 u**，短时间叠加 **14 U**（7 U + 7 U）。
- 事后取证的第二个发现：`-91`（`LastBolusStatusV2`）**只保留最后一笔**，**6886 被 6887 顶掉**，此后再未出现在任何报文里——App 侧**再也查不到第一笔**，连「我最近打过什么」都复不了盘。

**定性**

这不是「UI 不友好」级别的体验问题，而是**会导致重复给药的安全问题**：在用户已经忘掉上一笔的前提下，界面有没有把这一笔摆在眼前，直接决定他会不会再打一针。本案与 §4.9.8（非本 App 发起的输注，待实现）和 T1 取证（泵上 0.05 U，App 65 s 内 0 条 `44`、无会话/无通知/无取消入口）是**同一个缺口的两个侧面**。

**§9.3-A 的边界（必须写死，防止以后被做成拦截）**

- 用户此前明确：**不做判断、不给建议、只提示错误**。
- 因此 §9.3-A **只能是信息呈现**（把「最近一次大剂量」摆在输入区附近、保证在输入的那一刻看得见），**不得**变成：
  - **拦截**（禁用「输注」按钮、或按时间/剂量条件阻止发送）；
  - **二次确认**（「你确定要打吗」这类弹窗）；

### 12.1 两处 bug 的定性

| # | 现象 | 根因 | 本质 |

| 1 | 向导页 `mg/dL / mmol/L` 右侧「单位锁定」不保存，下次进入恢复未锁 | 锁与当前单位只存在内存 `BolusWizardState`，`clear()` 直接重建默认状态，进程重启也归零 | **长期偏好被当作本轮输入清掉**，缺持久化 |

### 12.2 两槽模型（`BolusSessionHolder`）

```kotlin
enum class BolusTarget { MAIN, EXTENDED }          // 取消 / 三态按目标分账
data class CancelDecision.Send(val bolusId: Int, val target: BolusTarget)
```

- 固定两槽：`session`（主笔，通常是刚发起的那笔）+ `extendedSession`（被顶掉的、仍在跑的扩展笔）。删除原来的只读 `priorExtended`。
- `begin()` 先调 `keepRunningExtended(previous, newBolusId)`：旧会话满足「未完成 + `isExtendedRunning` + id 不同」时**整体抬进第二槽**，保留 `bolusId` / 状态 / 预计结束 / 最后证据时刻。旧会话已结束或 id 相同（同笔恢复）则不抬。
- `setExtended` / `updateExtended` / `finishExtended(state, result, now)` **只改第二槽**，绝不覆盖主笔的 outcome。
- 取消节流与三态按目标分账：`cancelAttempts` / `lastCancelAtMillis` 改成 `Map<BolusTarget, …>`；`requestCancel(connected, now, target)`、`cancelStatus(now, target)`、`cancelRowStateFor(target, …)`、`cancelSentAtMillis(target)`。旧单参签名保留默认 `target = MAIN`，兼容动作菜单 / 通知 / 广播接收器。
- `isAnyBolusActive` 先看第二槽；`UNKNOWN` 与 `UNCONFIRMED` 都返回 `UNKNOWN`（既不能断言在输注，也不能断言没输注）；`clear()` / `clearSession()` / `resetCancelTracking()` 同清两槽。

#### 12.3.1 决定性现场：已落定的主笔被 46 复活（2026-11-11 01:32）

第一轮只修 `isExtendedLeg()` 时真机现象不变，说明类型标签不是唯一来源。临时 `BolusDiag` 日志给出完整链：

```
01:32:55.371 push main=[id=6926,imm=true,st=ACTIVE]  ext=[id=6923,imm=false,st=ACTIVE]   // 两槽正确分开
01:32:58.166 push main=[id=6926,imm=true,st=CANCELLED,fin=true] ext=[id=6923,...]        // 取消普通成功落定
01:32:58.175 strip main=[null] ext=[id=6923]                                             // 界面已只剩扩展
01:32:58.522 onExtendedBolus status=1 id=6923 main=[id=6926,...st=CANCELLED,fin=true]     // 46 报扩展仍在跑
01:32:58.526 push main=[id=6923,imm=false,st=ACTIVE] ext=[id=6923,imm=false,st=ACTIVE]    // ★ 两槽变同一笔
01:32:58.535 strip main=[id=6923,imm=false] ext=[id=6923,imm=false]                       // 两行都「扩展正在输注」
```

机理：`onExtendedBolus` 走到 `current == null || current.isFinished` 分支时执行 `holder.begin(..., hasImmediateLeg = false)`，把已落定的 6926 整体替换成 6923；而 `keepRunningExtended` 因旧主笔 `isFinished` 不抬升，第二槽仍是 6923 → **同 id 双占**。主槽的取消账本 `lastCancelAtMillis[MAIN]` 仍属 6926，10 秒后 6923 明明在跑却判 `CancelStatus.FAILED` → 「Bolus Not Stopped」。历史上泵端「大剂量超时」报警同源于此（App 侧对已不存在的对象反复取消 / 误判）。

修法（三层，皆不依赖硬编码槽号）：

1. `onExtendedBolus` 把 `current == null`（建主笔）与 `current.isFinished`（**写第二槽**）拆开，后者永不调用 `begin`。
2. 同函数 `else` 分支 `bolusId = it.bolusId ?: bolusId`：46 的 id 只在主笔还没有 id 时用于认领，绝不改写已有 id。
3. `BolusSessionHolder.coerceSingleOwner()`：主槽空、第二槽有值 → 抬成主槽；同 `bolusId` 双占 → 保留未落定的那个、清空第二槽。`begin()` / `set()` / `setExtended()` 后都会执行。
4. `begin()` / `set()` / `setExtended()` 换不同 `bolusId` 时清除对应 target 的取消账本，防止「新笔一进来就带着未停止」。

> 用户曾提议「干脆写死两槽，1 普通 2 扩展」；实现保留两槽语义但不硬编码序号，改用 **id 单主不变量** 达成同样效果——序号由 `hasImmediateLeg` 与 id 唯一性决定，泵换笔顺序不同也成立。

- 两级确认保留：点整条 `toggle expanded`；取消在途 / 失败强制展开；`bolusId` 变化时收回按钮（防串笔）。
- 取消三态的时间推进由 `LaunchedEffect` 每秒刷新 `now`（`STRIP_TICK_MS = 1_000L`）；失败时另有 `LaunchedEffect(mainCancelStatus, extendedCancelStatus)` 强制展开。

### 12.5 单位锁持久化（`BolusWizardRuntime`）

- `attach(context)`：`SharedPreferences("bolus_wizard_prefs")`，键 `bg_unit` / `unit_locked`；幂等，只补这两个字段，不覆盖用户已输入的文本。
- `update()` 与 `clear()` 之后都写回。`clear()` 改为保留 `bgUnit` + `unitLocked`，只清本轮输入 / 结果 —— **锁是长期设定，不是本轮输入**。
- `BolusWizardTab` 在 `LaunchedEffect(Unit)` 首行 `attach(LocalContext.current)`，进入向导即恢复上次选择。
