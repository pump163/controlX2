## K. 与设计文档不一致的地方（只列事实）

1. **子页数量**：设计文档按"9 个 60 秒页面"登记；代码实际有 60 秒刷新的手机页面为 **10 个**（Dashboard、Actions、Cartridge、Profile、CGMActions、Notifications、ControlIQSettings、SafetyLimits、Sound、QuickBolus），且 **Settings 页无任何泵查询**。其中 `CGMActions` 原先**完全漏登记**（现补为设计文档 §3.7 #17）；`QuickBolus` 原先只并入"7 个子页"一行（现单列 §3.7 #18）。
2. **向导请求集**：设计文档记"6 条（含 LastBG）"；代码 `BolusWizardTab.kt:131-146` 为 **5 条**，**不含 LastBG、不含 TimeSinceReset**。LastBG 只出现在 `BolusWindow.kt:109` 与手表 `BolusScreen.kt:197`。
3. **后台周期任务的断连行为**：设计文档记"断开时跳过"；代码是先 `postDelayed` 再发（`CommService.kt:168-169`），断连时仍执行，由 `command()` 在 `isConnected==false` 时丢弃，**不是跳过**。
4. **历史回补总闸范围**：设计文档记 `auto-fetch-history-logs` 控制"所有 HistoryLogRequest 回补流"；代码中流式 `onStreamResponse` 落库（`HistoryLogFetcher.kt:224-245`）**不受该开关约束**，开关只拦住 `HistoryLogStatus` 请示与缺口回补。
5. **IOB 选源**：设计文档按"本仓库恒 false → 38"表述；代码中 38 的响应**无消费者**，实际生效的 IOB 源只有显式 109（`Dashboard/CommService/向导/手表`）。即"选源"在代码里并不存在，只有一条有效源 + 一条无效源。**注意：这只是代码事实，不是结论**——38 与 109 是否等价、38 能否删，需按设计文档 §11 待验项 V1 实测；实测完成前两套并行照旧。
6. **首页请求条数**：设计文档"18 条"与代码一致（11 显式 + `NotificationBundle.allRequests()` 7 条，已在库源码 `NotificationBundle.java:52-61` 核对）。
7. **未登记的额外短周期**：`CartridgeActions.kt:181` 的 **15 秒**子屏轮询、`:129-134` 的 **5×1 秒** HomeMirror 连发、`BolusDialogs.kt` 的 **1 秒×60** 与 **500ms 双发**，设计文档策略表未覆盖。
8. **手表双重轮询**：手表批准后 `BolusApprovedPhase.kt:75-96` 自己起 1 秒×5，手机 `BolusEntryCoordinator` 同时也在轮询；两者可能对同一笔大剂量重复发音。
9. **缓存年龄语义**：设计文档要求 `Fresh/Stale(ageMillis)/Unavailable`；代码只有 `CacheSeconds = 30` 的"命中/过期"二值（`PumpCommHandler.kt:72,776`），且过期后直接真发，不区分 Stale 与 Unavailable。
10. **机型能力门控只拦"写"、不拦"读"**：`CGMActions.kt:108` 与 `QuickBolusSettingsActions.kt:87` 的 `canControl` 只用于禁用按钮、显示"不支持"文案；60 秒的 `HomeScreenMirrorRequest` / `CGMStatusRequest` / `PumpGlobalsRequest` 在 X2 上**照发**。设计文档 §3.5 #17 要求"不支持就不发"，二者不一致（本轮只记录，不改代码）。
11. **库注解不能兜底 QuickBolus**：`PumpGlobalsRequest`、`SetQuickBolusSettingsRequest`、`CGMStatusRequest`、`HomeScreenMirrorRequest` 的 `@MessageProps` **都没有 `supportedDevices`**（默认 ALL），所以 `supportsDevice()` 对 `SetQuickBolusSettingsRequest` 在 X2 上仍返回 `true`。"X2 不支持 QuickBolus 写入、Mobi 支持"这条事实**只由 App 规则 `canControlPump(model) = model == MOBI` 提供**（`shared/.../SupportedDevicesUtil.kt:24`），而且这条规则是全控制页通用的，不是 QuickBolus 专属。
12. **无 `MODEL_UNSUPPORTED` 概念**：代码里"该型号不支持"只能用"字段 `null` + 按钮置灰"表达，无法与"这次没查到 / 断连"区分；设计文档 §4.1.4 新增的 `Unavailable(MODEL_UNSUPPORTED)` 尚未存在。
13. **能力配置自述与实现不符**：`pump-capabilities.json:3` 声称"UI 显隐、校验、发送前检查只读此文件"，但实际机型门控是硬编码 `canControlPump(model) = model == MOBI`（`SupportedDevicesUtil.kt:24`）；且 `models` 段只有大剂量相关键，**没有 quickBolus / 声音 / CGM / IDP / 临时率**。新增一项仅 Mobi 的功能时，只改配置不会生效，必须改代码。
14. **手表侧零型号门控**：`wear` 模块检索 `canControlPump|supportsDevice|PumpCapabilities` **0 命中**。手表临时率（G3，`SetTempRateRequest` 为 MOBI_ONLY）、方案切换（G4）、CGM 动作（G7）在 X2 上都能直接发出；手机侧唯一的服务层门控是通知栏临时率按钮（`CommService.kt:966-970`）。

## L. 机型限制矩阵

### L.1 门控机制（代码事实）

- 型号判断入口：`canControlPump(model) = model == MOBI`，**硬编码白名单**（`shared/src/main/java/com/jwoglom/controlx2/shared/util/SupportedDevicesUtil.kt:24`）；带请求类的重载再加一道库注解收窄：`canControlPump(model, messageClass) = canControlPump(model) && supportsDevice(model, messageClass)`（同文件 `:26-27`）。

## N. 落地时的收敛顺序建议（按依赖）

1. 先做"数据槽 + 年龄"：把 `CacheSeconds` 的命中/过期二值扩展成 `Fresh/Stale(age)/Unavailable`，页面改读槽位（H4）。
2. 再做"节奏收敛"：C1、A5、E5 三处历史状态先合并；D4/D6/D7 三处大剂量轮询先合并。
3. 最后做"订阅化"：E1–E11 页面改为按可见性订阅查询器，不再各自 60 秒。
4. 手表侧（G1/G2/G6）在手机端收敛后改为纯订阅；手表宿主模式单独保留（M2）。
