# 底栏细条：多笔并存评估与单会话增强待办

> 记录时间：2026-11-10
> 状态：**P0 已实现（2026-11-10，`:mobile:compileDebugKotlin` 通过）**；多笔两行暂不实施（用户决定「持久化不扩」）
> 本文只记录判断与施工清单，未改动任何代码。

## 1. 需求

延展大剂量正在输注时，泵允许再发起一笔**立即**大剂量。此时两笔同时存在：

- 底栏细条应**分两行**显示；
- 两行应能**分别取消**（各自 `bolusId`、各自取消状态）。

## 2. 现状评估

单笔能力完整（首页卡片 / 底栏细条 / 大剂量页段二三处同源派生），
**两笔并存为 0% 实现**，卡点在三层单值结构，不是漏写：

| 层 | 代码位置 | 现状 | 后果 |
| --- | --- | --- | --- |
| 会话容器 | `bolus/state/BolusSessionHolder.kt:55` | `var session: BolusDelivery?` 单字段，`begin()` 直接覆盖 | 新立即发起时旧延展被覆盖，细条只剩一笔 |
| 取消状态 | 同上 `:65`、`:68`、`:187` | `cancelAttempts`、`lastCancelAtMillis` 各一份；`requestCancel()` 会把唯一 `session` 改成 `CANCELLING` | 取消 A 会污染 B 的状态，无法并行取消 |
| 派生 | `bolus/state/BolusStatusPresentation.kt:69` | `presentBolusStatus(delivery: BolusDelivery?)` 单参单返回 | 结构上表达不了两行 |

| 持久化 | `bolus/state/BolusSessionPersistence.kt` | `BolusSingleSession` 单笔，`schemaVersion=1`，`chain` 块为空壳 | 重启只能还原一笔 |

## 3. 已核实的事实

1. **泵发起的延展段，App 侧已能取消。**
   `performCancel` → `holder.cancelRowState()` → `requestCancel()` 全链路只判 `state` 与 `bolusId`，
   **不看 `bolusSource`**。旧记忆里「泵发起延展暂不开放 App 取消」是未落地的旧设计意图，以代码为准。
2. **`immediateLegDoneAtMillis` 已持久化**（`BolusSessionPersistence.kt:36/50/78`），
   重启后不会把「只剩延展」误判成「立即段在打」。
3. **`-91` 会顶掉前一笔**：断链重连后只能补回最后一笔，前一笔事后不可追溯（设备侧行为，非 App 缺陷）。
   这是「持久化不扩到多笔」的现实依据之一。
4. **两笔并存的已知缺陷早已列入真机测试点**（「延展期间叠加立即输注」验证项）。

## 4. 决策记录

| 事项 | 决定 | 理由 |
| --- | --- | --- |
| 持久化扩到多笔 | **不扩** | 泵侧 `-91` 本身会顶掉前一笔，扩了也常还原不全；`schemaVersion` 升级与回归成本高 |
| 多笔两行 + 分别取消 | **暂不做**，列入待办 | 需重构 holder / 控制器 / 派生 / 渲染四层，风险集中在报文按 `bolusId` 路由 |
| 单会话增强 | 见第 5 节，可增量做 | 不动结构，收益集中在判定正确性与可见性 |

## 5. 单会话前提下可提高的方面

### P0 — 判定正确性 ✅ 已实现（2026-11-10）

1. **`isExtendedRunning` 不再依赖 `expectedEndAtMillis`** ✅
   实现：`BolusDelivery.isExtendedRunning` 改为
   `state == ACTIVE && endObservedAtMillis == null && (!hasImmediateLeg || immediateLegDoneAtMillis != null)`。
   原有 8 处调用点自动受益（形态限制、开关置灰、细条、通知、`46` 归零判据）；
   `expectedEndAtMillis` 降为纯展示字段。
2. **延展结束补证** ✅
   `BolusPollScheduler.needsExtendedPoll` 不再因 `expectedEndAtMillis == null` 直接停轮询，
   改为「纯方波 / 立即段已结束 / 已知预计结束」三者任一即可；
   同时新增页面门控：`tick(..., extendedPollAllowed)`，只有「大剂量」页开着才发 `46`
   （`BolusEntryCoordinator.bolusPageVisible` ← `BolusV2Section` 的 `DisposableEffect`）。
   立即段 `44` 不受门控，细条与通知的新鲜度不受影响。
   已知残留：普通大剂量在 `45` 归零且 `expectedEndAtMillis == null` 时会同时置 `endObservedAtMillis`，
   该情形无法再区分「双波立即段结束、延展仍在跑」，只能等待 `46` 补上预计结束时刻。

### P1 — 可用性（部分实现）

3. **细条补「预计 HH:mm 结束 / 剩余量」** — ⏸ 暂不做（2026-11-10 用户决定）
   蓝牙断连会吞数据，细条再堆信息反而增加误读与轮询负担；等连接稳定性有把握后再议。
   若恢复：时长与时刻统一走 `UnitsRenderer.shortTime24()`，`expectedEnd` 为 null 时只显示「输注中」。

4. **细条容器 `Row` → `Column`（单条视觉不变）** ✅ 已实现
   外层改 `Column`，单笔视觉与单行一致，将来多笔可直接叠行；`heightIn(min = 48.dp)` 保留。

5. **取消两级确认** ✅ 已实现（替代原「二次确认弹窗」方案）
   默认只显示状态，**点整条才露出「取消」按钮**，再点按钮才发 `-96`。
   - 取消在途（`SENDING`）：锁定展开、不可收起；
   - 失败（`FAILED`）：自动展开并显示原因；
   - 换会话（`bolusId` 变化）：自动收回按钮，避免误点上一笔。
   `requestCancel` 现有的 15 秒 3 次节流保留；大剂量页段二的取消行不受影响。

### P2 — 一致性

6. **通知与细条同源核对** ✅ 已核对（无需改动）
   - 页面 / 细条 / 段二：同一份 `presentBolusStatus` + `bolusStatusText`；
   - 通知（V2 `PumppanBolusNotifier` 与 legacy `BolusNotifications`）：相位同用 `delivery.state` + `delivery.isExtendedRunning` 判定，文案分属通知通道（措辞不同属合理差异）；
   - `isExtendedRunning` 判据改后通知自动跟随，不存在两套判定。
   结论：相位判定已同源，保留两套文案。

7. **段二、动作表、细条共用阻塞原因** ✅ 已核对一致
   - 细条 `BolusStatusStrip`：`bolusCancelBlockedReason(...)`；
   - 动作表 `BolusActionMenu`：同一函数；
   - 段二不直接渲染原因，状态句走 `presentBolusStatus` → `bolusStatusText`，取消入口落在 `BolusActionMenu`，链路闭合。
   无需新增改动。

### P3 — 体验（单会话下最接近「两行」的效果）

8. **覆盖时保留上一笔延展快照，只做提示** ✅ 已实现
   - `BolusSessionHolder.begin()` 覆盖前，若旧会话「未结束且 `isExtendedRunning`」，存只读快照 `priorExtended`；
   - 每次 `begin()` 重置，`clear()` / `clearSession()` 清空，**不持久化**；
   - 细条主文案下补一行：有预计结束时刻用 `bolus_v2_prior_extended_with_end`（`HH:mm`），否则用 `bolus_v2_prior_extended`；
   - 该行**只提示、不参与取消**：没有独立 `bolusId` 路由与取消节流，直接拿它发 `-96` 会污染当前会话；
   - 文案不含「请到泵上操作」——泵发起的延展段 App 已能取消，避免误导。
   - 不改取消链路，不伪造第二笔会话。

## 6. 将来做多笔的施工清单

1. `BolusSessionHolder`：`sessions: List<BolusDelivery>`，取消节流与取消三态**移入每条**。
2. `BolusSessionController`：报文按 `bolusId` 路由（`45 bolusId=0` 只结束对应立即段；`47`/`-91`/`-95` 只作用于匹配 `bolusId`）；`begin()` 改 upsert。
3. `presentBolusStatus` → 新增 `presentBolusStatuses` 返回列表，单笔版本保留给段二。
4. `BolusStatusStrip` → `Column` 多行，每行独立文字 + 独立按钮 + 独立原因。
5. 配套排查：`BolusActionMenu` 取消行、`BolusV2Section` 段二、向导 IOB 否决、`allowsNewFlow`。
6. 持久化维持单笔（本决策），文档写明「重启只还原最新一笔」。

## 7. 验收要点（实施时）

- 延展在跑 + 新立即发起：细条两行、各自按钮可点、取消一行不影响另一行状态。
- 泵发起延展 + App 发起立即：同上（已确认取消不看来源）。
- 重启后：只还原最新一笔，旧笔不出现在细条，且不误拦新的大剂量。
- `expectedEndAtMillis` 为 null 的延展：开关仍禁用、第二步仍打回延展形态。
