## 1. 断连取证对改造的 6 条硬影响

1. **链路生死只能由连接回调决定**，不能由「多久没回包」推断。实测 App 层静默 47→57s 时连接仍在（§13 事实 3）。因此 `SUSPECT` 只允许做「限流/降级」，**不得触发重连、不得升级探活**。
2. **断开瞬间就要停表**：现在要等 `PUMP_COMMUNICATIONS_SUSPENDED`，而 `onPumpDisconnected` 是更早、更可靠的信号，必须接上 `markLinkDown()`。
3. **重连后必须留静默窗口**：库会走 `initializeConnection → sendBaseCommands`，这段本身就在占用链路；App 在窗口内再补查就是纯叠加。常态 5s、边界 15s。
4. **边界抖动的判据是「短命连接」，不是「断开次数」**：样本 11s / 35s，正常中位 101.5s。判据必须用 `connectedForMs`，且**时间戳只能取自连接回调，不能取自 DiagMonitor（已关）**。
5. **App 侧最大的放大器是「写并发 / 写失败」，不是查询频率**：任一写失败（授权 uuid 除外）会走 `noteWriteFailure` 计数，10s 内连续 3 次就 `cancelConnection`（`PumpCommHandler.kt:1103-1113`）。批量一次发 16 条 WITH_RESPONSE，正是「3 连失败」最容易凑齐的姿势。→ **写闸优先级高于降频**。
6. **屏灭降频优先级最低**：15:41–18:13 屏灭 + 无业务流量 + 3 小时 0 断，已证伪「屏灭需要保活」。不要再为屏灭做保活/心跳，也不要把它当第一优先级。

## 2. 推进顺序（依赖关系，不是愿望清单）

```
S1 链路事件接线 ──┬─→ S2 协调器真实 SHADOW ──→ S4 逐域接管 ──→ S6 退场/复核
                 └─→ S3 写并发闸（最高杠杆）──→ S5 EDGE + 数据保持
```

### S1 链路事件接线（最小改动，先行）
- `PumpCommHandler.kt:128-134` 构造端口时传 `linkPolicy` 里的 `linkSilentAfterMs`（当前 90s）；
- `onPumpDisconnected`（:714）→ `queryPort.markLinkDown()`；
- `onPumpConnected`（:685）→ `markLinkUp()` + 记录 `quietUntil = now + quietAfterReconnectMs`；
- 端口增加 `quietUntil` 判定：窗口内 `request()` 直接拒绝（记 `QUIET`）。
- 验收：断开后首个 tick 全部 `LINK_DOWN`；重连静默窗内 0 条下发；`disconnectedRequestCount` 恒 0。
- **状态：已完成（2026-11-11 21:20 真机验证）**。做法与计划有两处差异：① 静默窗直接复用已有 `states.connectedSettleMs`（8s），没有新增 `quietAfterReconnectMs`，避免多一个配置键和一个消费者；② 策略注入走 `CommService.newPumpCommHandler()` 统一工厂，三个创建点（服务启动/结束找泵/重新找泵）共用，`pumpcomm` 不引用 mobile 的 `QueryPolicy`。
  实测（关蓝牙 8s 再开）：`21:19:59.773 onPumpDisconnected` → `21:20:11.758 initializeConnection`（`markLinkUp(quiet=8s)`）→ 从 `21:20:12.391` 起连续 `query suppressed ... reason=QUIET`（15 个 opCode × 多轮），最后一次 `21:20:18.487`，与窗口截止 `21:20:19.758` 吻合；窗口后请求恢复正常（`lastRequestAtMillis` 持续前移，`maxInFlight=1`、`disconnectedRequestCount=0`）。8s 窗口只可能来自 asset 注入 → 同一入口的 `linkSilentAfterMs=90000` 也已随之注入端口。

### S2 协调器进入真实 SHADOW
- **构造点必须在 `PumpCommHandler` 内**：`queryPort` 是它的私有字段（`PumpCommHandler.kt:128`），协调器要共用同一个端口实例，否则会出现两个端口、两套在飞状态；构造后 `QueryCoordinatorHolder.attach()`，`CommService`（或 handler 自己的 Handler）只负责 5s 节拍调 `tick()`；
- 仍然 0 下发，只产 `Plan`；`DEFAULT_ACTIVE_DOMAINS` 保持空集（先全量观测，不接管任何域）。
- 验收：`/api/query/stats` 出现 `coordinator` 段；连续 30 分钟对比「shadow 计划条数」与「legacy 实际下发条数」，算出多下发率与重复率。
- **必须同时修的一个计时缺陷**：`QueryCoordinator.tick()` 现在是「ordered 非空就推进 `lastPlannedAt`」（:129-131），不看 `sent`。一旦切 ACTIVE，被 `QUIET`/`IN_FLIGHT`/`THROTTLED` 全部拒掉的域名也会被记为「已发」，下轮要再等一个完整 `intervalMs`——在重连期和边界抖动期正好会造成「该查的没查、指标空窗」。改成「按域统计 sent>0 才推进，或 SHADOW 模式照旧」。
- **状态：已完成（2026-11-11 21:41–21:50 真机）**。构造点按模块可见性做了调整：协调器在 `mobile`、端口在 `pumpcomm` 私有，所以由 `PumpCommHandler.queryPortForOrchestration()` 暴露同一实例，`CommService.startQueryObservation()` 构造协调器并起 5s 节拍（`QUERY_TICK_MS=5_000`），`onDestroy` 调 `stopQueryObservation()`。这样端口只有一个，在飞登记与静默窗不会被拆成两份。
  实测：`recentPlans` 相邻两条 `at` 差 5005 / 5001 / 5004 ms；`link={linkState:OK, linkSilentAfterMs:90000, inQuietWindow:false, maxInFlight:3}`（90000 由此可直接读到，不再只靠 S1 的推断）；`observedEngine` 仍 `LEGACY`（影子不接管，符合预期）。
  计时缺陷已按「按域 sent」修：ACTIVE 只推进真正发出去的域，SHADOW 仍按 `ordered` 全推进（影子要模拟真实节奏，才看得出「本该发多少」）。观测域取 `pollingDomains()`（9 个已登记域去掉 `BOLUS_PRECHECK`/`BOLUS_OUTCOME`）——后两者是一次性任务域，`BOLUS_OUTCOME.intervalMs=1s`，算进固定节拍会把「本该发多少」虚高。
  新增 `skipped` 输出（域 → 跳过原因）后立刻抓到一个真缺口：**`PUMP_STATE` 有请求清单（3 条）却不在策略 JSON 的 topics 里，协调器永远排不到它**。补 topic（60000/15000/`P1_STATE`/`onlyWhenVisible`）后，单次计划从 6 域 9 条变成 7 域 12 条，`PUMP_STATE` 稳定出现在计划里，其余未迁移域仍如实报 `NOT_MIGRATED`。

### S3 写并发闸（断连场景下最高杠杆，先于逐域接管）
- 端口加**全局在飞上限**（**定为 3**）与**同请求窗口去重**；批量下发按 200ms 错峰；
- 保留现有「写失败 ≥3 次/10s 才剪线」与 `readCooldownMs=500`；
- 只读冷却期内，`linkState` 对外仍报 `OK`（冷却不是链路故障，避免误降级）。
- 验收：24h 写入失败总数、`WRITE_CUT` 次数对比；人走开复现 5 分钟，不应出现「3 连失败 → 剪线 → 重连」循环。
- **状态：已完成（2026-11-11 21:46 真机）**，但形态从「拒绝式闸门」改成三层，理由是拒绝会静默丢数据：首页一次批 16 条，若靠 `maxInFlight` 直接拒，挡掉的那部分没有重试路径，页面数字会缺。
  1. **批量错峰 200ms**：`dispatchBulkPaced()` 第 0 条立即发，其余按 `index*200ms` 排队；每条执行前重判 `isBolusCommand` 与连接前置条件。三个批量分支（直接透传 / bust-cache / cached）全部走它，缓存命中仍立即回包、不占带宽。
  2. **全局在飞上限 3**：`PumpCommandPort` 侧兜底，`IN_FLIGHT_TTL_MS=10s` 清陈旧登记。
  3. **同请求 250ms 去重**：键为 opCode+cargo，超时重发与不同 cargo 不受影响。
  实测：`send command (paced)` 时间戳 21:46:58.302 → .414 → .620 → .821 → 59.020 → 59.220 → 59.420 → 59.620，等差 200ms 左右；同一请求不再成对出现，`reason=DUPLICATE` 10 次（挡掉第二条批量链），`IN_FLIGHT=0`、`BUSY=0`。
  **一个必须记下的返工点**：`dispatchBulkPaced()` 最初是直接 `pump.command()`，绕过了端口——错峰生效但去重不生效，21:41 的日志里同一请求仍相隔 21ms 连发两遍。改成走 `queryPort.request()` 后才真正闭合。原因是泵回 ACK 只要 20–40ms，单飞（在飞期间拒绝）挡不住「两条链各发一遍」，必须有时间窗去重。

### S2/S3 复测暴露的上游问题（结论修正，留给 S5/S6）
- 复测方式：`cmd bluetooth_manager disable` 8s 后 `enable`。
- 结果：`21:47:50 onPumpDisconnected` → `21:48:08 CONNECTION_TIMEOUT`（伴随 `SET_MTU_FAILED, mtu 23`，一次 `Set MTU` 写失败）→ 库立刻 `immediateConnectToPeripheral`，连接一直悬着 → `21:49:26.554 onPumpConnected`。
- **成因已由当事人纠正**：这段时间用户本人走开了，泵随人离开手机，属于「距离过远」，不是库的重连缺陷。连接一直处在 pending 状态（`BluetoothPeripheral: connecting`），人回到范围内后由 autoConnect 直接接上——**这正是期望行为：不额外扫描、不反复重连骚扰链路**。
- 与查询器改动无关：断开期间端口 `linkState=DOWN`、`lastRequestAtMillis` 为空，一条查询都没下发；`sourceCounts` 也没有新增。
- 对验收口径的影响：「回来 ≤60s 能连上」这条要按「**人回到范围内**的时刻」起算，不能用「适配器恢复」起算。本次 autoConnect 从挂起到接上是 78s，但其中绝大部分是人不在范围内，不能算作重连时延。
- 另：本次重连后 8s 静默窗内没有出现 `reason=QUIET`，因为断开期间 Dashboard 自己的 60s 定时器跳过了 fetch（`Dashboard skipping fetch while pump disconnected`），窗口内没有查询尝试——不是 S1 失效，是恰好没有流量。要验 S1 仍需在窗口内有页面刷新。

### S4 逐域接管（一次一个，禁止批量开）
建议顺序（按「有保底 + 页面易摘 + 风险低」排）：
1. `PUMP_VITALS` / `IOB` / `BASAL` / `BOLUS_LAST`（P0_FLOOR，页面只读卡片）
2. `NOTIFICATIONS`（有独立页面与红点）
3. `CONTROL_IQ` / `SAFETY_LIMITS` / `PUMP_GLOBALS`
4. `CGM`
5. `DASHBOARD_BATCH`（合并收益最大，也最易双发，必须最后）
6. `HISTORY`（走 Worker，最后处理）

每域固定动作：页面 60s 刷新区改成「仅可见时订阅」→ `activeDomains += 该域` → 删页面写死定时器。
验收：`sourceCounts` 里该页面来源归零、coordinator 计数接上、`opCodeDuplicateCounts` 不升。

### S5 EDGE 抖动识别 + 数据保持

- 验收：泵放远处走动复现短命连接，观察 `EDGE` 生效、无补查、首页数字不跳。

## 4. 本轮明确不做

- RSSI 实时采证（依赖侧单回调，需改库重发 aar）；
- 屏灭保活心跳（已被 3 小时 0 断证伪）；

- 修改库的 `reconnectDelay`（同 aar 依赖）。

## 5. 回滚与风险

- S1：传参可回退默认 30s；事件接线删掉即回旧行为；
- S2：纯观测，无下发；
- S3：上限与间隔进配置，可整段关闭；
- S4：每域独立开关，`activeDomains` 单点控制，双发可立即回退该域；
- S5：只读状态机 + 配置，无下发副作用。
- 最大风险在 S4：旧页面定时器没删干净就加域 = 双发。固定用 `/api/query/stats` 的 `sourceCounts` 与 `pageSourceCounts` 验，不靠肉眼。

## 6. S4 附带项：细条显隐口径（2026-11-11 定版，待与大剂量改动同批实现）

**定位**：`BolusStatusStrip` 目前把 `UNKNOWN`/`UNCONFIRMED` 也算作「正在输注」，而重启后的会话恢复正好落在这两个状态，于是没有真实输注也先画一条细条，等首轮 44/46 回包落定才消失。

**现场证据**（2026-11-11 21:18–22:22，日志 `bolus strip:`）：

| 时刻 | 可见性 | 状态 | bolusId |
|---|---|---|---|
| 22:18:54.952 | visible（持续 45s） | UNCONFIRMED | null |
| 22:19:44.272 | visible（持续 7s） | UNCONFIRMED | null |
| 22:21:37.401 | visible | UNKNOWN | null |
| 22:21:47.399 | visible（共 54s） | UNCONFIRMED | null |
| 22:22:31.547 | hidden | — | — |

`ext` 全程 `null(null)`：不存在第二笔延展，观察到的「先延展后普通」是 `UNKNOWN → UNCONFIRMED` 的文案跳变。

**定版规则**：

1. 可见条件收紧为「**有 bolusId 且状态属于 ACTIVE / CANCELLING**」；`UNKNOWN`、`UNCONFIRMED`、空 bolusId 一律不显示。
2. 会话恢复路径不再提前 `pushState()` 触发渲染，等首轮查询回包后再落状态。
3. 判定依据仍是确定性字段（bolusId + 泵返回状态），不用 App 侧计时或估算。
4. 定位不变：细条是**便利**不是约束——泵上发起的大剂量仍要提醒、仍可在手机取消；只在证据不足时不打扰。

**为什么不能只删 UNKNOWN**：`UNCONFIRMED` 同样无 bolusId（本次两次闪现都是它），只删一个仍会复现。

**验收**：重启后 60s 内 `bolus strip: visible` 出现次数必须为 0；泵上真发起一笔大剂量后 ≤2s 出现可见且 bolusId 非空；取消后 ≤2s 消失。

### 7.2 协调器机制（本轮定版）

- **`pendingFrom` 分拍续发**：一批超过在飞上限（3）撞 `BUSY` 立即 break，下标留到下一拍；`IN_FLIGHT/THROTTLED/DUPLICATE` 视为已覆盖前进；`pendingFrom` 非空时该域不受 `NOT_DUE` 约束。
- **BUSY 短退避已删除**：曾试 `Thread.sleep(120ms)×4`，实测无效（回包几百 ms 到数秒，退避只卡 `serviceLooper`，`rejected` 涨到 42）。现在撞 `BUSY` 立刻让位。
- **订阅意图缓存**：页面可能早于协调器 `attach`（首页是启动首屏）。`QueryCoordinatorHolder` 用 `visibleSubs` 存意图，`attach` 时补灌；窗口意图同理用 `pendingWindows`，`attach` 时按剩余时长补开。
- **窗口（window）语义**：`BOLUS_OUTCOME` 这类 `maxWindowMs` 域，只有窗口开着才允许按其 1s 间隔下发；窗口默认 60s、自动到期，关窗后该域直接 `WINDOW_CLOSED` 跳过。作用是把「确认期 1s 一问」限定在确认期，而不是常态 1s。

### 7.3 首页三档（实测计划）

- `DASHBOARD_BATCH`(60s) = `ControlIQIOBRequest()`（电量/储药由 `PUMP_VITALS` 保底域负责，避免同 opCode 每拍双发）
- `DASHBOARD_DETAIL`(120s) = LastBolusStatus + CurrentBasalStatus + HomeScreenMirror + GlobalMaxBolus
- `DASHBOARD_CGM`(300s) = CGMStatus + EGV + ControlIQInfo + HistoryLogStatus（API/CGM 会话门控）
- 实测：60s `BATCH requests=1 sent=1`；120s `BATCH+DETAIL requests=5 sent=3`，下一拍 `DETAIL requests=4 sent=1` 补齐；300s `CGM requests=2 sent=2`（会话 STOPPED 门掉两条糖查询）；`rejected=0`；切页后 `visible` 只剩单域，返回后 `nextDue` 重新拨表。

### 7.5 wear（本轮不改，按硬约束；原因已按代码复核更正）

本轮用户明确「wear 不动」，作为硬约束执行。但**之前记在此处的理由有一处是错的，已按代码更正**：

1. **wear 有两种角色，互斥**（`shared` 的 `DeviceRole`）：`PUMP_HOST`（手表自己持泵链路，起 `WearPumpCommService`）/ `CLIENT`（手表只显示，起 `PhoneCommService`，命令经 `/to-pump/*` 交给手机 `CommService` 执行）。切角色时 `switchDeviceRole()` 会先 `stopService` 两个服务、清 bond、再把 `pumpFinderServiceEnabled` 设成与角色匹配，所以两态不可能并存——这一点与用户判断一致。
2. **「三个页面 60s 是手机 App 关闭时的唯一驱动」不成立**：两个 app 各自都有 5min 保底——
   - `mobile/.../CommService.kt:190` `periodicUpdateIntervalMs = 60_000 * 5`；
   - `wear/.../WearPumpCommService.kt:115` 同样是 `1000 * 60 * 5`。
   所以 CLIENT 态由手机的 5min 保底、HOST 态由手表的 5min 保底驱动；三个页面的 60s 是**页面打开时的额外驱动**，不是唯一驱动。这也解释了为什么「把保底域塞进 `dispatchedDomains`」会把 5min 变成 60s 的担忧只是半个问题：真正要定的是「页面打开时 60s 该不该降到手机端那套分档」。
3. **「只改配置文件就能切 wear 节奏」目前做不到**：`QueryCoordinator`/`QueryPolicy(Loader)`/`QueryCoordinatorHolder` 全在 `:mobile`（`wear` 只依赖 `:shared`，且 `settings.gradle` 里没有独立 query 模块）；wear 的三个 60s 是页面里的 `intervalOf(60)` 常量，不读任何 policy/capabilities 文件（`wear/src/main/assets` 下只有 `paperwork.json`）。所以 wear 侧要「按配置发查询」，**前提是先有 wear 能用的调度器**（把 query 层下沉到 `:shared`/新模块，或在 wear 内做一份轻量实现），配置才有消费者。
4. **上游没有 per-model 的查询间隔**：`mobile`/`wear` 两处都是写死的 5min 常量，页面是写死的 60s；`pump-capabilities.json` 的 `default`/`MOBI` 只区分命令与剂量限制，不含 interval。用户说的「Mobi 续航差所以上游把查询拉长」目前是设计意图，**代码里没有落地**。

**待决策（用户提议的方向，本轮不实现）**：把查询策略做成 `平台 × 泵型号` 的 2×2 配置——`mobile`/`wear` 各分 `slimX2`/`mobi` 两个档案，先按上游现有时间填值，真机调参只改配置。落地需要三块前置：

- 配置放 `shared/src/main/assets`（AAR 的 assets 会合并进两个 APK，一份文件两端都读得到）；
- wear 侧需要一个读这份配置的调度器（当前没有）；
- 泵型号要能到 wear：现在型号是**菜单里手选的偏好**（`PumppanPrefs` 的 `AUTO/MOBI/SLIM_X2`，`PumppanPumpModel`），不是自动识别；CLIENT 态可由手机下发，HOST 态 wear 本地没有这个偏好，需要新增。

在这三块之前改 wear 页面，只是把 60s 搬个位置，不产生可验收的收益；故本轮保持原状。

### 7.6 「点大剂量标签先显示正在输注」修复（2026-11-12，仅代码，未编译未真机）

### 7.7 冷启动「卡在正在向泵申请」的真因：连接对账在链路就绪前发起（2026-11-12 12:25/12:31/12:36/12:44 四次真机）

现场：冷启 → 点「大剂量」→ 页面停在「正在向泵申请，请稍候」；泵上无大剂量；60s 后才松手。
切「向导」再切回就正常（向导会补一次真实状态查询）。

日志时间线（12:25 那次）：
- `12:25:41 pump-connected`（ACL 建链，readyState=UNKNOWN）
- `12:25:44 对账发起 CURRENT` → `12:25:46 步骤 CURRENT 超时（2000ms）`
- `12:25:46→49 EXTENDED / EXTENDED_V2` 同样超时 → `12:25:49 对账整体超时（5000ms）` → 落 UNKNOWN
- `12:25:53` 才出现第一条真实回包（battery）；即 `pump-connected` 与「命令通道可用」之间约 10s
- `12:25:59 / 12:26:09 / 12:26:19` 每 10s 一条 `44（UNCONFIRMED）`，零结果清不掉占位
- `12:26:49 发出 -98 后 60000ms 仍无开始证据，落 UNKNOWN` 才松手

真因：`finish()` 的 else 分支在「三条全超时」时调 `holder.begin(UNCONFIRMED)`，造出一个**既无
bolusId 也无 startedAt 的对账占位**。占位被当作「可能已在输注」，入口页因此落到只读/申请态；
而对账本身一次证据都没拿到，等于整段 60s 卡顿都来自「没问到」被当成「不知道」。

四处改动（均已编译、装机）：
1. `BolusReconciler.finish()`：`responded.isEmpty() && holder.session == null → IDLE`，不造占位；
2. `BolusSessionController.onCurrentBolusEmpty()`：`CONFIRMING/UNCONFIRMED` 分支里，当
   `bolusId == null && startedAtMillis == null`（对账占位特征）时 `holder.clear()` 静默移除，
   `outcome = Pending`；真实 `-98`（有 startedAt）仍按原逻辑继续等；
3. 对账改「静置期」放行：`onPumpConnected` 只登记 `reconcileDueAtMillis = now + 10s`，
   由 ticker 到点发起（`bolus: 链路静置期满，开始连接对账`）。曾先试「等首包」，
   实测冷启时若没有任何请求就没有首包，对账永不发起，故改为定长静置期；
4. 空转重试封顶：`BolusReconciler.retryIfDue(now)` + `hasPendingRetry()`，
   一条都没回应时隔 10s 重试，最多 3 次（`MAX_EMPTY_ATTEMPTS`），之后放弃本次连接对账。

实测：
- 12:31 版（改动 1+2）：对账仍全超时，但 `落定 IDLE`、不造占位；点大剂量页直接是
  「当前没有进行中的大剂量」+「新的大剂量」草稿页，日志无 `进入大剂量页`（无会话提前 return）。
- 12:36 版（试「等首包」）：`首包已到` 后三条仍全超时——首包只是状态推送，不代表命令通道可用。
- 12:44 版（静置期 10s）：`12:44:03 pump-connected` → `12:44:14 静置期满` →
  四步（44/46/46v2/48）全部在半秒内回包 → `12:44:14 对账落定 ACTIVE`：泵侧 `44` 自报
  DELIVERING、`bolusId=6938`，首页 IOB 14.75U、细条「普通正在输注」。入口页显示
  「大剂量正在输注 / 取消大剂量」，与泵侧自报一致；随后 `44（ACTIVE）` 10s 一拍正常。
  （该笔是否为 12:15 那支 15U 的残留由泵侧决定，App 只按证据呈现。）

### 7.10 大剂量 / 向导入口的一次性 kick（2026-11-12 13:5x）

- `QueryCoordinator.requestNow(domain, coalesceMs=2000)`：不看 `nextDueIn`、不看窗口是否开着，
