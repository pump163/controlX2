# 查询器策略 · 设计（2026-11-10 第 4 轮）

> 前序：`查询层收敛-设计.md`（§4.5 策略外置、§4.7 查询出口、§4.8 全量收口、§4.9 事件驱动）。本文只写「策略怎么定、谁来执行、断连怎么办」，不重复已经落地的出口与白名单。

## 0. 本轮定位

目标一句话：**发现单发遗漏，只改一处。** 除了查询器做不了的事（签名、确认、取消、控制副作用），所有只读查询都归一个协调器。

用户已锁定的四条前提：

1. 策略进配置文件，不写死在程序里；
2. 可按泵类型 / 固件版本 / 工作态分别制定；
3. 60 秒固定基线，泵主动推的消息作为策略应用条件；
4. 必须有兜底。

## 1. 现状缺什么

### 1.1 单位错了：页面批 ≠ 数据域

`pump-query-policy.json` 的 `topics` 现在是 `DASHBOARD_BATCH` / `NOTIFICATIONS` / `ACTIONS` 这类**页面批**。页面批必然重复：

- `HomeScreenMirrorRequest` 被 5 个页面共用，每个页面各查一次；
- 首页与通知页都要通知，各查一遍；
- 页面可见性只影响「谁在看」，不影响「该不该查」。

只要单位还是页面，「漏发只改一处」就做不到——漏的是数据域，改的是页面。

### 1.2 端口只知道「发没发」，不知道「有没有」

`PumpCommandPort.Result` 只有 `sent / reject / opCode`。调用方拿不到数据，也拿不到「为什么没有」。安全判定（大剂量前检查）必须能区分三态：**有 / 无 / 未知**，不能把「被拒绝」「超时」「断连」当成「没有」。

### 1.3 配置项齐了，消费者只有一个

`QueryPolicy` 已有 `topics / freshness / states / budget / events / reconnect / switches / diagnostics / applyPendingOn`，但真正接上的只有 `CgmQueryGate` 的两个 `states` 开关。`budget`、`events`、`reconnect`、`applyPendingOn` 全部没有消费者。

`pump-query-policy.json` 顶部 note 仍写「第 0 步仅登记，不接任何消费者」，已过时。

## 2. 数据域模型（本轮核心改动）

### 2.1 域定义

查询单位从「页面批」改为「数据域」，页面只做订阅。

| 数据域 | 内容 | 主要订阅者 | 保底 |
|---|---|---|---|
| `PUMP_VITALS` | 电池、储药、胰岛素状态、`TimeSinceReset` | 首页、控制页、通知条、手表 | **是** |
| `IOB` | `ControlIQIOB` / `NonControlIQIOB` | 首页、大剂量向导、控制页 | **是** |
| `BASAL` | 当前基础率 | 首页、控制页 | 否 |
| `BOLUS_LAST` | 上一次大剂量状态 | 首页、大剂量向导 | 否 |
| `CIQ_STATUS` | `ControlIQInfoV1/V2` | 首页、控制页 | 否 |
| `CGM` | `CGMStatus`、`CurrentEGVGuiData` | 首页、图表、大剂量向导 | 否（已有门控） |
| `NOTIFICATIONS` | 7 条报警类 | 首页红点、通知页 | 否（事件驱动） |
| `PUMP_SETTINGS` | `PumpGlobals` | 声音 / 快捷大剂量设置 | 否 |
| `SAFETY_LIMITS` | `GlobalMaxBolusSettings` / `BasalLimitSettings` | 首页、安全上限页 | 否 |
| `PROFILE` | `ProfileStatus` / `IDPSettings` / `IDPSegment` | 个人方案页 | 否 |
| `CARTRIDGE` | `LoadStatus` | 储药器页 | 否 |
| `HISTORY` | `HistoryLog` | 历史回补 | 否 |

`STATUS_BATCH` 拆成 `PUMP_VITALS`；`DASHBOARD_BATCH` 拆成 `IOB` / `BASAL` / `BOLUS_LAST` / `CIQ_STATUS`。旧名字保留为兼容别名，一个过渡期内两边都认。

### 2.2 页面订阅

页面不再持有 `dashboardCommands` 这类完整清单，只声明：

```kotlin
val subscriptions = listOf(PUMP_VITALS, IOB, BASAL, BOLUS_LAST, CIQ_STATUS, CGM)
```

协调器把「多个订阅者同时到期」的域合并成**一次批量下发**（pumpx2 支持一个往返带多条）。一个域只查一次，结果广播给全部订阅者。

### 2.3 合并规则

- 同一 tick 内到期的域 → 合成一批，受 `budget.burst` 约束；
- 事件触发的域 → 优先于周期域（它代表「数据刚变」）；
- 保底到期 → 优先于一切，且不占预算。

## 3. 三层职责

| 层 | 管什么 | 明确不管 |
|---|---|---|
| `QueryCoordinator`（新增） | 到期判定、域合并、优先级、预算、断连状态、待补队列、数据年龄、订阅广播 | 具体请求类、字段、协议 |
| `PumpCommandPort`（已有） | 单飞、超时、节流、链路可用性 | 优先级、调度、数据语义 |
| 调用方（页面 / 向导 / 事件处理器） | 用途：显示 / 安全判定 / 对账 | 频率、重试、去重 |

协调器**不做全局单例**，由 `MainActivity` 注入，与端口实例一一对应（沿用现有「实例注入、不搞单例」的约定）。

## 4. 保底策略

### 4.1 为什么保底不能靠「配置写对」

电池、IOB、储药这三类要防四种情况：配置写错、页面不可见、预算耗尽、断连恢复中。任何一种发生，用户都会看到「数据是十分钟前的」而没有任何提示。

### 4.2 硬下限

```json
"PUMP_VITALS": {
  "intervalMs": 300000,
  "floorIntervalMs": 60000,
  "floorPriority": "P0_FLOOR",
  "onlyWhenVisible": false
}
```

三条硬规则：

1. `now - lastSuccessAt >= floorIntervalMs` → **强制发**，不看预算、不看可见性、不看优先级；
2. 保底只覆盖关键域，且合并成一批（3–4 条），**不是把 7 条通知全塞回去**；
3. 保底失败（断连 / 超时）要记数据年龄，UI 显示「最后更新于 xx」，**不假装新鲜**。

### 4.3 优先级与降级

现有 `degradeOrder: ["P2_DECORATIVE", "P1_STATE", "P0_CONFIRM"]` 容易被读成「先降 P0」。改为：

```json
"budget": {
  "perMinute": 10,
  "burst": 20,
  "protectPriority": ["P0_FLOOR", "P0_CONFIRM"],
  "degradeOrder": ["P2_DECORATIVE", "P1_STATE"]
}
```

`protectPriority` 里的域**不进降级**、**不被预算拒绝**；`degradeOrder` 只列可降级的。

### 4.4 三态结果

协调器对调用方返回：

```kotlin
sealed class QueryOutcome {
    data class Fresh(val value: Message, val ageMs: Long) : QueryOutcome()
    data class Stale(val value: Message?, val ageMs: Long) : QueryOutcome()
    data class Unknown(val reason: RejectReason) : QueryOutcome()
}
```

`Unknown` 必须带原因：`DISCONNECTED` / `TIMEOUT` / `THROTTLED` / `BUDGET`。安全判定只接受 `Fresh`；`Stale` 与 `Unknown` 一律按「不确定」处理。

## 5. 断连（数据链路不稳）

### 5.1 真正的风险

不是「查得少」，而是**断连窗口里堆请求，重连瞬间倾泻 → 单飞互撞 → 超时重发 → 更堵**。现有代码只有 `PUMP_COMMUNICATIONS_SUSPENDED → pauseSends(5s)` 与零散的 `SEND_FAILED`，没有整体状态。

### 5.2 状态机

| 状态 | 进入条件 | 行为 |
|---|---|---|
| `LINK_OK` | 最近一次响应在 `linkSilentAfterMs` 内 | 正常调度 |
| `LINK_SUSPECT` | 超过 `linkSilentAfterMs` 无响应，或连续 2 次 `SEND_FAILED` | 暂停周期域，只放行探活 |
| `LINK_DOWN` | 连接状态 false / 通信挂起事件 | `FROZEN`：不累计到期、不扣预算、**不清数据年龄** |
| `RECOVERING` | 连接状态恢复 | 探活 → 分批补 |

### 5.3 恢复序列

1. 探活 1 条最小请求（`ApiVersion` 或 `CurrentBattery`），`probeDelayMs` 后发，`probeTimeoutMs` 超时判失败；
2. 失败 → 指数退避（3s → 6s → 12s → 24s → 30s 上限），**不重试整包**；
3. 成功 → 按 `maxBatchAtOnce` 分批补：先 `P0_FLOOR`，再 `P1_STATE`，**`P2_DECORATIVE` 直接跳过，等下一个周期**；
4. 补完 → 回到 `LINK_OK`，恢复常规节拍。

### 5.4 待补队列

断连期间：

- **事件补查不进队列**（避免重连瞬间全量倾泻）；
- 只把「有订阅者正在等」的域记一条待补，同域只保留一条，重连后合并；
- 保底域优先出队。

## 6. 大剂量前置检查：委托，但走一次性任务

「输注前查有没有延展 / 立即大剂量在跑」不是轮询，是**带 deadline 的一次性查询链**：

1. `ExtendedBolusStatus`（46 / -74）→ 有无延展；
2. `CurrentBolusStatus`（44）→ 有无立即；
3. 需要时再查 `LastBolusStatus` + 泵能力限制（`pump-capabilities.json`）。

放查询器的四条要求：

- **P0 + deadline**（建议 5 秒），超时返回 `Unknown`，**不能返回「没有」**；
- **可抢占**：保底域与 P0 任务优先占用链路，装饰性查询让路；
- **结果短时缓存**（30 秒），用户连点重开向导不重复查；
- **协调器不可用时 fail-closed**：拒绝进入向导，不做直发兜底。

唯一继续独立发的仍是**取消**（原约定：多发保证无条件取消）。

**实现（2026-11-10，试点 A 第一步）**：

- 请求清单移到 `QueryDomainRequests.BOLUS_PRECHECK`（参数快照 + 血糖 + IOB + 立即大剂量 + 延展大剂量），向导只写任务名，页面不再列请求；此后增减请求只改那一处。
- 三态 `BolusInfusionCheck { NONE, DELIVERING, UNKNOWN }`。`UNKNOWN` 有独立文案（「无法确认泵上的输注状态」），不冒充「有延展在跑」，也不冒充「没有」。
- 发送仍走 `sendPumpCommands(BUST_CACHE, ...)`：出口本来就在 `PumpCommHandler.command()` 的只读白名单分支，因此**没有新增消息类型**。为回执单独加一条协议消息收益不抵成本；deadline 由「响应到达时刻 ≥ 本次发起时刻」承担，断连时 `pumpConnectedPrecondition` 直接丢弃 → UI 收不到响应 → `UNKNOWN`，天然 fail-closed。
- 单测 `BolusInfusionCheckTest` 3 条。

## 7. 策略分层与合并顺序

`pump-capabilities.json` 已按型号分档案，策略层照同样思路叠加，顺序固定且可诊断：

```
default
  → byModel.X2 / .MOBI
  → byApiVersion.minApi        （pumpx2 的 apiVersion）
  → byState.suspended / delivering / closedLoopOff / disconnected
```

合并结果写进 `QueryPolicy.diagnostics.appliedOverlays`，并在 `/api/query/stats` 的 `effective` 段暴露，避免「改了配置不知道哪份在生效」。

工作态层接「泵主动推的消息作为策略应用条件」：

- 收到 `BOLUS_CHANGE` → 大剂量域切高频 N 秒；`44` 回到 `bolusId=0` → 切回低频；
- 收到 `ALARM` → 通知域高频 5 秒；
- 收到 `PUMP_COMMUNICATIONS_SUSPENDED` → 全域 `FROZEN`。

## 8. 配置结构（schema v2 草案）

在现有文件上增量演进，不推翻：

```json
{
  "schemaVersion": 2,
  "default": {
    "topics": {
      "PUMP_VITALS": {
        "intervalMs": 60000,
        "floorIntervalMs": 60000,
        "floorPriority": "P0_FLOOR",
        "minIntervalMs": 15000,
        "onlyWhenVisible": false,
        "requests": ["CurrentBatteryRequest", "InsulinStatusRequest", "TimeSinceResetRequest"]
      },
      "IOB": {
        "intervalMs": 60000,
        "floorIntervalMs": 60000,
        "floorPriority": "P0_FLOOR",
        "requests": ["ControlIQIOBRequest", "NonControlIQIOBRequest"]
      }
    },
    "budget": { "protectPriority": ["P0_FLOOR", "P0_CONFIRM"], "degradeOrder": ["P2_DECORATIVE", "P1_STATE"] }
  },
  "overlays": {
    "byModel": { "X2": { "...": "..." }, "MOBI": { "...": "..." } },
    "byApiVersion": [{ "minApi": 7, "topics": { "...": "..." } }],
    "byState": { "delivering": { "...": "..." }, "closedLoopOff": { "...": "..." } }
  },
  "oneShot": {
    "BOLUS_PRECHECK": {
      "maxWaitMs": 5000,
      "cacheMs": 30000,
      "requests": ["ExtendedBolusStatusRequest", "CurrentBolusStatusRequest"],
      "priority": "P0_CONFIRM"
    }
  }
}
```

保底域清单（按首页最小显示状态核对）：`PUMP_VITALS`、`IOB`、`BASAL`、`BOLUS_LAST` 各 60 s；`CGM`、`CONTROL_IQ` 各 300 s。这六项是首页常驻字段，屏蔽不屏蔽都在，所以周期不能被预算或可见性降掉；血糖与 CIQ 允许低频（泵会主动推 `CGM_CHANGE` / `CONTROL_IQ_INFO`），但保底仍然是「最长空窗」。

保底语义：`floorIntervalMs` 是「最长允许的空窗」，实际周期取 `min(intervalMs, floorIntervalMs)`；到期就发，不看预算 / 可见性 / 优先级。所以 `PUMP_VITALS` 的 `intervalMs` 与 `floorIntervalMs` 都写 60 s，两者不等时才体现「省电期」与「保底期」的差别。

`requests` 字段让「域包含哪些请求类」也进配置——这是「漏发只改一处」的最后一步：新增请求只加一行 JSON，不改 Kotlin。

风险：请求类是编译期类型，配置里只能放 simpleName，运行时按白名单反查。白名单缺失要显式报 `diagnostics.missingKeys`，不能静默跳过。

## 10. 验收标准

- 每一次只读查询都能在 `/api/query/stats` 里看到「域 / 来源 / 用途」三个维度；
- 断连 30 秒再恢复：不出现同一 opCode 连续 `IN_FLIGHT`；恢复后第一分钟请求数不超过 `budget.perMinute + burst`；
- 保底域在任意 60 秒窗口内至少成功一次；断连期间数据年龄持续增长且 UI 可见；
- 大剂量前置检查在断连时返回 `Unknown`，向导拒绝进入，不显示「无进行中输注」；
- 新增一个请求类，只改配置文件即可出现在首页，不需要改 Kotlin。

## 11. 回滚

- 第 1 步：`QueryKey` 改回纯 opCode，删 cargo 摘要函数；

- 第 3–7 步：协调器按域灰度，任一域可单独切回页面直发（`switches.pageRefreshEnabled`）。

## 13. 来自蓝牙断连实测的基线（2026-11-11）

本节把 `docs/bug/断连诊断包分析-20261111.md` §8 的真机实测，折算成查询器参数。
原则一句话：**链路不稳时不查、恢复后少查，先把「不堆请求」做对，再谈降频。**

### 13.1 四条实测事实（可直接当判据）

| 事实 | 数据 | 对查询器的含义 |
|---|---|---|
| 连上后对端会自降到低功耗档 | 15/0/5 → 30/29/2，t+24s 发生 | 查询间隔不能依赖「HIGH 会一直保持」，调度要假设参数可能被对端降档 |
| 低功耗档的余量只剩约 200ms | `(latency+1)×interval×2 = 1.8s` vs `timeout=2s` | 任何「心跳/保活」都必须按 LOW 档算，不能按 2s 算 |
| **App 层无回包 ≠ 链路死** | 19:04:52–19:06:20 `LINK_SILENT`，App 层 47→57s 无包，连接未断、`inc` 未增 | `linkSilentAfterMs` 不能用「App 多久没收到包」直接判 `SUSPECT` |
| 断连期间链路确实不可用 | 走开 5m49s，`conn=False`，期间任何查询无意义 | `LINK_DOWN` 必须冻结，不累计到期、不扣预算 |

补充两条本次确认的底层行为：

- 连接失败重试是**固定 5 秒**（`onConnectionFailed`），成功连上重置退避（`reconnectDelay=250`）；
- 一次连接尝试实测 **0.87 s** 完成（`CONNECT_START 19:03:40.725 → CONNECTED 19:03:41.593`），
  但连接成功后库还要跑 `initializeConnection → waitForResponseStabilization → sendBaseCommands`，
  这段时间链路是忙的。

### 13.2 由此确定的参数（替代 §5 里的直觉值）

| 参数 | 建议值 | 依据 |
|---|---|---|
| `linkDownEnter` | 收到 `DISCONNECTED` / 连接状态 false **立即** | 不需要「连续 N 次失败」才判死；断开事件本身是确定的 |
| `linkSuspectEnter` | 连续 2 次 `SEND_FAILED`，**或** App 层无响应 ≥ **90 000 ms** | 实测正常空窗可到 57s（保底 60s 周期 + 抖动），阈值必须高于保底周期，否则 `SUSPECT` 常态化 |
| `linkSuspectExit` | 任一响应到达 | 与现有端口实现一致，不改 |
| `quietAfterReconnectMs` | **5 000** | 连接成功后库在跑初始化与基础命令，此时补查会与初始化抢链路 |
| `probeDelayMs` | **1 000** | 实测连接本身 0.87s 完成，探活不必等太久 |
| `probeTimeoutMs` | **5 000** | 单条只读查询正常是秒级；超 5s 视为可疑（配置校验下限即 5s） |
| `maxBatchAtOnce` | 3–4 条 | 与 `budget.burst` 对齐，恢复期一次只补一小批 |
| 保活心跳 | **不做** | 见 13.3 |

### 13.3 为什么「别拼命查」是有依据的，而不是省事

- 屏灭 + 无业务流量 + 近距静止，**连续 3 小时零断开**（239/239 采样，`inc` 未因静默增长）。
  说明链路存活**不依赖 App 周期性发包**，监督超时看的是链路层有无包（含空包）。
- 因此「用查询当保活」既无效又昂贵：断连的真实起因是人走开（RF 路径），
  多发查询只会在边界处制造更多失败与重连竞争。
- 唯一仍需守住的是**余量**：若将来真加心跳，间隔必须 < 当前参数下的监督窗口
  （LOW 档 `2s × (latency+1)`，不是 2s）。这条是硬约束，但当前参数下**不需要心跳**。

### 13.4 断连与恢复的动作序列（照实测校准）

```
DISCONNECTED
  → LINK_DOWN：冻结所有域，待补队列只记「有订阅者的域」，同域合并为一条
  → 事件补查一律不入队（避免重连瞬间倾泻）

CONNECTED（实测 0.87s 完成连接）
  → 静默 quietAfterReconnectMs(5s)：等库的初始化与基础命令跑完
  → 探活 1 条（CurrentBattery），3s 超时
      ├ 失败 → 退避 3s→6s→12s→24s→30s 上限，不重试整包
      └ 成功 → 分批补：P0_FLOOR → P0_CONFIRM → P1_STATE，P2_DECORATIVE 直接等下一周期
  → 回到 LINK_OK，恢复常规节拍
```

### 13.5 与验收口径的关系

本次把蓝牙侧的验收改成了「回到范围 ≤60s 能连上」（断连包文档 §8.9）。
查询器的对应验收应同步改成：

- 断连期间 `/api/query/stats` 里**不应出现新增的 `IN_FLIGHT` 或 `SEND_FAILED`**（说明冻结生效）；
- 恢复后第一分钟请求数 ≤ `budget.perMinute + burst`；
- 恢复后首个成功响应的时刻，距 `CONNECTED` 不超过 `quietAfterReconnectMs + probeDelayMs + probeTimeoutMs`
  ≈ 9 秒（即「不拖后腿」，不额外延长用户看到数据的时间）。

### 13.6 待落地的三处

1. `linkSilentAfterMs` 与 `reconnect.*` 已按实测改好：30 000 → **90 000**、`probeDelayMs` 3 000 → **1 000**、`probeTimeoutMs` 15 000 → **5 000**、`maxBatchAtOnce` 2 → **3**（`pump-query-policy.json`）；
2. `quietAfterReconnectMs`、`probeDelayMs`、`probeTimeoutMs` 三个字段进 schema；
3. 协调器从 `SHADOW` 转 `LIVE` 时，`LINK_DOWN` 冻结与恢复序列必须同时生效——
   只冻结不恢复，会让用户看到「连上了但数据不动」。
## 14. 边界抖动（range-edge flap）：不加重链路负担

### 14.1 实测现象

信号在可达极限附近时，会出现「连上十几秒又断」的短周期抖动，本次实测样本：

| 时间 | 表现 | 存活时长 |
|---|---|---|
| 18:57:46 → 18:57:57 | 连上 11s 后再断 | 11 s |
| 15:41:12 断开 | `connectedForMs=35029` | 35.0 s |
| 15:34:07 断开 | `connectedForMs=1452.4s` 前一段正常 | — |
| 4 小时值守 17 次断开 | 中位存活 101.5 s | — |

危害不在「断」本身，而在**每一次重连都会触发一整套初始化**：
`initializeConnection → waitForResponseStabilization → sendBaseCommands`（库内不可关），
若 App 侧同时在补查，就会在边界处形成「初始化 + 补查」叠加，表现为重发、超时、数据回跳。

### 14.2 判定：什么时候算「边界抖动」

在**滑动窗口**里看断开密度与存活时长，满足任一条即进入 `EDGE`：

| 条件 | 阈值 | 依据 |
|---|---|---|
| 窗口内断开次数 | `≥ 3 次 / 5 分钟` | 正常时 3 小时 0 次；17 次集中在走动时段 |
| 单次存活过短 | `connectedForMs < 30 000` 连续 2 次 | 抖动样本 11s / 35s；中位 101.5s 说明正常连接应远超 30s |
| 重连后再次断开 | 距上次 `CONNECTED` < 60 000 ms 又断 | 同一位置的反复连断 |

退出：连续 **180 000 ms（3 分钟）**无断开，且此间至少一次成功响应 → 回 `LINK_OK`。

### 14.3 EDGE 期间的行为

原则：**保持最低限度的可观测性，其余全部让路。**

- 周期域：只保留 `P0_FLOOR`（`PUMP_VITALS` / `IOB` 各 60s），其余域**不累计到期**（与 `LINK_DOWN` 同款冻结，但不叫冻结，叫「不计时」）；
- 事件补查：**一律丢弃**，不排队、不延后（排队只会在回稳瞬间倾泻）；
- 重连后补查：不做，只等 `stableAfterMs` 后按常规节拍自然到期；
- 探活：降到 **1 条 / 60s**，不发独立心跳；
- 重连静默窗口：`quietAfterReconnectMs` 从 5s 提到 **15s**（给库的初始化留余量，避免与其抢链路）。

### 14.4 数据跳动：宁可显示旧值，也不显示假值

抖动期间最容易出的体验问题是「数字来回跳」：断连时 UI 把字段刷成 `--` / `0`，连上后又刷回真值。

规则：

1. 断连与 `EDGE` 期间**保留最后一次成功值**，只更新时间标签（「最后更新于 xx」）；
2. `Unknown` 与 `Stale` **不得渲染成 0 或空**（与 §4.4 三态一致）；
3. 同一字段短时间内收到两次差异过大的值时，按「新值 + 数据年龄」展示，不做静默平滑。

### 14.5 与底层退避的关系（不要对着干）

库的重连退避是 `reconnectDelay`：成功即重置为 250ms、失败按 1.5 倍递增、连接失败另走固定 5s。

边界抖动的典型序列是「成功 → 立刻重置 250ms → 又断」，抖动被这个重置机制放大。
App 侧无法改库（需重发 aar，单独立项），能做的是**不要在抖动期叠加自己的请求**：
不补查、不重放、不并发探活。这样即使底层快速重连，链路也只有一个初始化序列在跑。
