## 0. 结论先行

1. 目标形态是**多窗口（1 / 7 / 14 / 30 天）的 TIR 汇总页**：区间占比 + 覆盖率 + 均值/糖化 + AGP 分位带 + 逐日曲线 + 低血糖风险。
2. **数据前提已经满足**：§74 已拍板 C 方案（历史库全量保留、不裁剪），30 天窗口可行；**若未来有人改回有界裁剪（3h/6h），本目标直接不可行**。
3. 与现有内存机制不冲突：`InitialHistoryLogCount=5000` 只是首次追赶跨度、`recentSeqIds=LruCache(256)` 只做流式去重、`itemLruCache=LruCache(500)` 只缓存解析结果，**都不需要改**。
4. 上游 TIR **只做了 24h**（288 点、70–180 单区间、无 TBR/TAR/GMI、无多天报表），这是本地实现最直接的理由；**是否向上游递进由用户决定**，本文不预设。
5. 本轮 docs-only：不编译、不出包、不碰 `D:\Programming\apk`。

### 2.2 数据前提：C 方案刚好满足 30 天

- Room 表 `pumpdata_historylog` 全量保留（除调试 `deleteAll()` 外无清理），**30 天窗口可用**。
- 量级下限：CGM 约 `288 行/天 × 30 ≈ 8640 行`，再叠加基础率、大剂量、报警、校准等事件；查询应走时间窗，不要 `getAll()` 全表。
- **反向约束（必须写进任何裁剪提案）**：3h/6h 有界裁剪会让 30 天窗口**直接不可行**；即使窗口放大到 24h，也仍不足以支撑 7/14/30 天。若未来再提裁剪，本目标与 §74 的 TIR 约束一起作为否决理由。

### 2.3 缺口清单（实现前必须逐项拍板）

1. **CGM 缺失段**：传感器停用、换传感器、蓝牙断连都会产生空洞。
   - 占比计算：空洞**不计入**分母（只统计有效读数），否则 TIR 会被系统性拉低；
   - 覆盖率另算：`有效读数时间 / 窗口墙钟时间`，两者不能混为一个百分比。
2. **按泵时钟对齐**：`HistoryLogItem.pumpTimeSec` 是泵的**墙上时钟秒**（自 2008-01-01 起，无时区），`pumpTimeLocal()` 用 UTC 偏移换算；`pumpTime` 字段已标 `@Deprecated`（时区编码含糊）。实时读数用 `CurrentEGVGuiDataResponse.bgReadingTimestampSeconds`，两套时间源需要定义**以泵时钟为准**还是换算到本地时钟。
3. **跨天时区 / 夏令时**：窗口边界与「按天分组」必须先定口径（泵本地日 vs 手机本地日）；DST 会让某天多/少 1 小时，覆盖率分母需按实际时长算，不能用固定 86400 秒。
4. **CGM 类型合并口径**：`DashboardCgmChart.kt` 第 30–35 行 `CgmReadingHistoryLogs` 已含 `CgmDataFsl2HistoryLog` / `CgmDataFsl3HistoryLog`；需确认多条 FSL 流（换传感器/双 CGM）是否去重、以哪条为准，去重键沿用 `["seqId","pumpSid"]`。
5. **5 分钟采样的权重**：逐点等权 vs 时间加权。等权在长空洞后会高估有数据时段的比例；时间加权需要相邻点时间差，且要处理跨传感器切换。
6. **查询方式**：DAO 已有 `getItemsForTypesSince(pumpSid, typeIds, minPumpTimeSec)`（按时间窗），比现有 `getLatestItemsForTypes(... LIMIT)` 更合适；聚合应在内存完成还是新增汇总表，需评估 30 天数据量。
7. **多泵 / 重新配对**：`pumpSid` 是蓝牙名末 3 位，换泵或重配对会产生新的 `pumpSid`；跨 `pumpSid` 是否合并统计需拍板。

## 3. 分期建议

### 档 1：多窗口 + 五区间占比（低成本，现有表上可做）

- **范围**：1 / 7 / 14 / 30 天窗口切换；五区间（Very Low / Low / In Range / High / Very High）占比；阈值可配（默认 ADA：<54、54–69、70–180、181–250、>250 mg/dL）。
- **改动面**：
  - 数据层：复用 `getItemsForTypesSince`，新增纯 Kotlin 聚合函数（不建表、不迁移）；
  - UI：在趋势页/首页卡片新增窗口切换 + 区间条；
  - i18n：约 14–18 个 key（窗口 4、区间 5、标题/副标题 3、百分比与计数模板 2、空态 1–2）。
- **验收**：同一窗口下五区间百分比之和为 100%（允许 0.1% 舍入）；与逐条手工计数一致；30 天窗口在真机上查询不卡顿（目标 < 1s）。
- **前置**：缺口 1（空洞不计入分母）、缺口 5（等权/时间加权）拍板。

### 档 2：覆盖率、时段分布、均值与变异度

- **范围**：CGM 使用时间占比 + 监测次数；AGP 分位带（50% 中位线 / 25–75% / 10–90%）；MBG、eHbA1c、CV/SD/中位数；LBGI 分档。
- **改动面**：聚合函数扩展 + 分时段分桶（按 5 分钟槽位对齐 24h）；UI 图表（折线/带状）；i18n 约 15–20 个 key。
- **风险**：分位带与时段分桶对时钟对齐最敏感（缺口 2、3、4）；eHbA1c 与 LBGI 公式需注明来源，避免「看起来专业但算错」。
- **验收**：覆盖率与「有效读数时间 / 窗口时长」独立复核一致；AGP 三条带单调（10–90 包含 25–75）；LBGI 分档与标尺阈值一致。

### 档 3：可视化与导出

- **范围**：堆叠条（区间占比）、多窗口并列对比、逐日曲线；导出（CSV 优先，PDF/图片待定）。
- **改动面**：仅 UI + 导出模块；i18n 约 10 个 key。
- **风险**：导出涉及隐私（血糖数据），默认只存本地、不自动上传；PDF 需要引入渲染库，优先 CSV。

## 4. 与已决事项的关系

- **依赖 C 方案**：§74 定稿「全量自动拉取、不裁剪」是本目标的唯一可行前提；有界裁剪（A/B）已排除，理由在此再加一条：**30 天窗口**。
- **与内存机制无冲突**：
  - `InitialHistoryLogCount = 5000`：首次追赶的 seqId 跨度，不是容量上限，30 天统计不受影响；
  - `recentSeqIds = LruCache(256)`：流式去重，只影响拉取，不影响统计；
  - `itemLruCache = LruCache(500)`：解析缓存，统计时按需解析即可（30 天约 8640 条，缓存命中率会下降，但不影响正确性）。
- **上游 TIR 未完成**：仅 24h / 288 点 / 70–180 占比 / 无 TBR/TAR/GMI / 无多天报表（`upstream-pr-candidates.md` §8）。这是**本地实现理由**，不是「上游已有、我们只是换皮」；**是否向上游递进（改 dev/main、提 PR）需用户决定**，本文不预设。
- **术语沿用 §75 词表**：统一用「历史记录」「本地数据库」「消息缓存」「调试日志文件」，不写「历史日志」。
