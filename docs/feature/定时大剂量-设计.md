# 定时大剂量（链式预约）设计 · C 轮

> 状态：**讨论稿 · 全部未实现**（2026-11-07）
> 定位：在已完成的立即大剂量流程（A 轮 v2）之上，追加「首次输注确认后倒计时，到点由 App 发起第二笔立即大剂量」的链式预约能力。
> 风险等级：**高级 / 危险**。本能力刻意利用胰岛素叠加，方向与闭环算法的限制相反；任何实现必须先过 §9 安全门。
> 本文只写设计与未决项，不含代码；所有阈值均标「建议键 / 待确认」，不写成已落盘事实。

---

## §1 能力边界

| 能做 | 不做 |
|---|---|
| 立即大剂量（普通/校正），链式最多 3 笔 | 延展大剂量、双波、方波预约 |
| 以「泵确认已开始输注」为倒数锚点 | 以系统时间/点按时刻为锚点 |
| 允许倒数中与提醒框中改剂量 | 自动改剂量、按血糖自动计算 |
| 到点由 App 通过既有 `-94`→`-98` 通道真发 | 依赖泵排队（泵不排队，第二笔是全新 `bolusId`） |
| 超时/未确认一律放弃 | 静默补发、失败重试、后台自动执行 |

**前提依赖**：A 轮 v2 的发送通道、输注期状态与 60 s 确认阶梯（`大剂量功能设计-v2.md` §4.9.2）、横幅与通知（§4.9.4）、进程级持久化（§4.9.5，**尚未实现**）。

### 1.1 风险清单

| # | 风险 | 事实依据 |
|---|---|---|
| **R-1** | **泵侧没有任何累计保护**。Max Bolus 只限制单笔；连续两次 `-98` 之间泵不做任何节流。累计层完全是 **App 自造的限制**，不得把 Max Bolus 当作「总量受控」的安全边界。 | `InitiateBolusRequest` 字段只有 `totalVolume / bolusID / bolusTypeBitmask / foodVolume / correctionVolume / bolusCarbs / bolusBG / bolusIOB / extendedVolume / extendedSeconds / extended3`（pumpx2 `InitiateBolusRequest.java:31-41`），**没有任何累计/周期字段**；客户端 `BolusLimits.MAX_BOLUS_MILLIUNITS = 25_000` 只在单笔校验（`BolusLimits.kt:142`，`BolusForm.validate`）；`BolusSender.buildRequest` 只校验单笔 `BolusSendPlan`（`BolusSender.kt:105-135`）。快照里的 `maxBolusEventsExceeded / maxIobEventsExceeded` 只是状态回传，未见其用于拦截发送（未验证，**不能作为安全依据**）。 |
| R-2 | 链式叠加会持续抬升 IOB，低血糖风险由用户自行判断 | 机制本身（R1）；`-98` 不提供任何自动血糖门控 |
| R-3 | 进程被杀/Doze 导致错过或延迟发送 | 见 §8；依赖 A §4.9.5 |
| R-4 | 上一笔尚未结束时发起，泵可能返回 `REVOKED_PRIORITY`（`statusTypeId=2`）或直接拒绝 | 属**失败路径的一种**，按普通发送失败呈现，不做特殊分支（§7/§10） |
| R-5 | 每次发起都要走常规 `-94` 授权 | **不是特殊权限**，随 A 轮发送链路一并生效（§10） |
| R-6 | **不能假设 CGM 趋势一定存在**：用户当前不是 Dexcom，血糖在独立 App，泵内可能完全没有 CGM 读数 | 见 §5.2 三级降级；现有 `cgmReading/cgmDelta` 与 `bgValue/bgTimestamp` 两个数据源都可能为空 |

## §2 已定规则（用户拍板，照录不改口径）

| # | 规则 |
|---|---|
| R1 | **机制**：第一笔立即大剂量开始输注后起一个**倒数**（不是系统时间），到点由 App 发起事先设好的第二笔立即大剂量。刻意利用胰岛素叠加（1+1>2），反向于闭环算法的限制，属高级/危险能力。 |
| R2 | **计时起点**：等泵确认已开始输注（`-97` 成功 + `45 statusId=2`/DELIVERING 之类证据），不是点「输注」那一刻。 |
| R3 | **链式**：允许，最多 3 次（默认值，放配置）。 |
| R4 | **单笔上限**：不超过 Max Bolus。 |
| R5 | **提前提醒**：到点前 30 秒，可自定义，上限 5 分钟；提醒时同时检查连接状态。 |
| R6 | **超时或不点确认 → 必须放弃本次预约**，不得自动执行。 |
| R7 | **倒数中可以改剂量**，并且鼓励改（看血糖趋势就该改）；提醒框里再改也生效。 |
| R8 | **二次确认**：点确认后再弹一个警告，必须重复确认才输注。 |
| R9 | **开关与安全门**：默认关闭、放在 Debug「危险指令」组内、每笔两次确认、剩余时间常驻通知可见且可取消。 |
| R10 | **错过提醒（2026-11-07 定）**：接受「错过即作废、不补发」，但必须提醒：闹钟能触发则立即通知；闹钟失效则下次打开 App 对账时补通知。发送前先查泵历史 `280` 判「未发出/状态未知」，一条链只提醒一次，详见 §8.1。 |
| R11 | **累计上限（C1，2026-11-07 定）**：**不加**基于 U 数的累计上限；只保留次数上限（默认 3）与每笔两次确认。跑起来后再评估。 |
| R12 | **提醒时点（C4，2026-11-07 定）**：T−30 s **只发通知、不弹框**；**到点才弹确认框**。**（秒数暂定，预期按 C16 重定）** |
| R13 | **确认窗口（C5，2026-11-07 定）**：到点后 **60 秒**内不确认即作废；**不认晚确认**；要打须重新预约。**（秒数/超时策略暂定，预期按 C17 重定）** |
| R14 | **到点断连（C6，2026-11-07 定）**：宽限 **0**，连不上按作废处理，并按 R10 发「到点时未连上泵」提醒。 |
| R15 | **链尾（C11，2026-11-07 定）**：第三笔完成后整链结束，不自动续。 |
| R16 | **锁屏交互（C12，2026-11-07 定）**：锁屏只提供「取消」「打开 App」；**确认必须在 App 内完成**。 |
| R17 | **泵发起打断（C9，2026-11-07 定）**：泵上开始另一笔输注（泵发起或其它来源）时，预约**立即作废**，弹窗/通知明确告知「预约已作废：泵上已开始另一笔输注」，**不提供「继续」选项**；风控优先。 |
| R18 | **血糖门控（C13，2026-11-07 定）**：**不加低血糖/CIQ 硬门控**；血糖数据只作提醒，真实低血糖由泵/CIQ 自身处理。 |
| R19 | **链记录实际量（C10，2026-11-07 定）**：`-91` 到达则**异步补记**实际 `deliveredVolume`；未到达只记请求量并标「实际量未知」。 |
| R20 | **整链语义（2026-11-07 定，通用规则，非 C9 专属）**：**链是一条命**——任一环节终止即整链作废，剩余预约全部取消；已成功发出的那笔不撤回、不补打；界面/通知须说「本次预约已全部取消，共 N 笔未执行」；不得出现「第二笔已打、第三笔还挂着」的半截状态；状态机有显式 `CHAIN_ABORTED` 终态并记录原因。 |

### 2.1 提醒文案（中文定稿；英文后译）

> 最后一次大剂量输注 xxU 于 XX 时已输注。您预约了 XX 点输注立即大剂量 XXU，请检查您的 1 活性胰岛素 2 血糖趋势 3 是否已经用其它方式输注，默认取消本次预约。

- 下方输入框：**「[预约大剂量 U 数]」，可更改**。
- 按钮：**「取消」（默认）**、**「确认」**。

### 2.2 二次确认文案

> 您上次大剂量输注 xxU 于 XX 时已输注，本次将增加 XXU，请检查您的 1 活性胰岛素 2 血糖趋势 3 是否已经用其它方式输注！

### 2.3 「可选」的定义

本文的「可选」一律指**使用者的判断与调整可选**——是否继续、改多少、是否取消，由使用者自行取舍；**不是信息的可见性**。三条提醒项（活性胰岛素 / 血糖趋势 / 是否已用其它方式输注）**恒常呈现，不可省略**；数据有多少显示多少。

## §4 状态机

```
IDLE
 └─(首笔已确认开始 + 已设预约)──► COUNTING
COUNTING ─(剩余 = advanceNotice)──► NOTIFIED（通知提醒，连接检查）
COUNTING ─(剩余 = 0)──► ALERTING（提醒框：可改剂量）
ALERTING ─(用户确认)──► WARNING（二次确认）
WARNING ─(再次确认)──► SENDING（-94 → -98）
SENDING ─(-97 成功/45 证据)──► ACTIVE（本笔作为新的 bolus 会话）
SENDING ─(NACK/-97 失败)──► FAILED（本笔终止，且整链 `CHAIN_ABORTED`，不重试）
SENDING ─(超时无证据)──► UNKNOWN（本笔终止，且整链 `CHAIN_ABORTED`，不重试）
ALERTING ─(超时 / 用户取消 / 断连)──► ABORTED（整链 `CHAIN_ABORTED`）
COUNTING/NOTIFIED ─(用户取消 / 断连 / 泵上被其它输注打断 / 进程错过)──► CHAIN_ABORTED
COUNTING ─(首笔取消/结束证据提前到达 且未到点)──► 保留或放弃（§6 待定）
```

**整链终止（R20）**：上述任一终止都落到 `CHAIN_ABORTED`，**剩余预约全部取消**，不得留下「第二笔已打、第三笔还挂着」的半截状态。已成功发出的那笔保持原状，不撤回、不补打。终态记录终止原因（用户取消 / 超时 / 断连 / 泵上被打断 / 进程错过 / 发送失败）。

- **确认后的分支与常规发起复用同一条路径**：`-94` 取权限 → `-98` 发起 → 等 `-97` / `45` / `-91` 确认阶梯。不写第二套流程；唯一差别是**触发时机由倒数决定**，不是由手指决定。
- 上一笔未结束时发起，泵若返回 `REVOKED_PRIORITY`（`statusTypeId=2`）或直接拒绝，按**普通发送失败**呈现（见 §7），不额外前置探测。
- **ACTIVE 之后是否允许再链下一笔**：只取决于 `chainCount < scheduledMaxChainCount`（R11：无累计上限）。
- 第二笔开始时，链的下一段倒计时以**第二笔的开始证据**为新锚点（R2）。
- `ABORTED` 不再自动恢复；用户要重新预约必须重新走首笔流程（或后续另行设计「重新预约」，见 §7）。
- 状态全部为**新增**，A 轮既有 `BolusDelivery` 不动；仅通过 `bolusId` 关联链记录。

## §5 链式闸与决策界面（方案，待用户确认）

### 5.1 安全边界（与 §1.1 R-1 同一条）

- **Max Bolus 只限制单笔**；泵在两次 `-98` 之间**没有累计节流**；累计层完全是 **App 自造的限制**，不存在泵侧兜底。
- 因此：**不展示「本次累计 X U」**，也**不以「请求量之和」作为判据**。
- **IOB 不作为界面指标，也不作为门槛。** 泵侧 IOB 口径不透明（延展段是否计入、CIQ 是否已调整、刷新周期如何都不明确），数值滞后，摆在确认框里会造成「很精确」的错觉，属于误导。

### 5.2 决策界面显示（按数据可得性三级降级）

**前提约束：不能假设 CGM 趋势一定存在。** 用户当前用的不是 Dexcom，血糖在另一个独立 App 里，泵内可能根本没有 CGM 读数。因此：

- **二级（泵内无 CGM，手输血糖 + 时刻）与三级（无血糖无趋势）是常态形态**，不是过渡方案；C 轮全部交互与文案以这两级为验收基准。
- **一级（泵内有 CGM）保留为增强路径**：仅当用户设备本身有 CGM 时才启用，不作为默认假设。
- 「独立血糖 App 的数值能否进泵」**不在本轮范围，远期再议**（不记为 TODO，也不列为未决项）。

提醒框与二次确认中，下面三条提醒**恒常完整呈现**，不因有无数据而隐藏：

1. 活性胰岛素（IOB）
2. 血糖趋势
3. 是否已经用其它方式输注

数据本身按可得性显示：有 CGM 就给数值 + 箭头 + 读数时刻；只有手输就给输入框；都没有就明写「当前无血糖数据」。**三条提醒文字始终完整展示**。

#### 5.2.1 分级判定（按优先级，从上到下）

| 级别 | 判定条件（按现有字段） | 说明 |
|---|---|---|
| **一级：泵内有 CGM** | `cgmReading != null`（`DataStore.kt:116`） | 即使 `cgmDelta/arrow` 为空，也仍属一级（值在泵内），只是箭头显示「未取得」 |
| **二级：泵内无 CGM，有 LastBG** | `cgmReading == null` 且 `bgValue != null`（`DataStore.kt:101`） | LastBG 是指血/回传值，**无趋势**；可另提供手动输入覆盖/补充 |
| **三级：两者都空** | `cgmReading == null && bgValue == null` 且用户未手输 | 不显示任何推算值 |

- 判定必须在**到点提醒打开时重新计算**，不能沿用预约创建时的级别。
- 二级/三级是**验收基准**；一级是增强路径，测试以「无 CGM」为默认场景，另加「有 CGM」用例。
- 手动输入只影响二级/三级的「当前值」显示；一旦泵内有 CGM（一级），以 CGM 为准，手输值仅作参考、不得覆盖。
- 两者都空即三级；**不得**用链记录里的旧血糖、上次预约的值或「上次大剂量量」来推算当前血糖。

#### 5.2.2 各级显示与文案

| 级别 | 显示 | 文案要求 |
|---|---|---|
| **一级** | 血糖值 + 趋势箭头 + 读数时刻与距今多久 | 例：「当前血糖 6.8 mmol/L（CGM，读数距今 2 分 10 秒）↗ 上升」 |
| **二级** | 不显示箭头；显示 LastBG/手输血糖 + 时刻 +「**无 CGM 数据，趋势不可用**」 | 手输区标注「可填可不填，不影响继续」；空白时不得显示任何默认值 |
| **三级** | 只显示「**无法提供血糖与趋势**」 | 不显示任何推算值、不显示「平稳」、不显示箭头占位符；判断权交回用户；仅在文案提示「请自行确认血糖与趋势」 |

- **禁止**在无趋势时使用「趋势平稳」「箭头缺失=平稳」等暗示性表达；无数据就写「未取得/不可用」。

#### 5.2.3 手动输入（二级/三级）

- 字段：`manualBgMgdl` + `manualBgAt`（输入时刻），随**本次预约/链记录**保存。
- 生命周期：从预约创建到本次链结束（DONE/ABORTED）；不进入全局 DataStore，不跨预约复用。
- 持久化：随链记录一起落盘（依赖 A §4.9.5），进程重建后可恢复；链结束或作废后清除（**不因「读数过期」清除**，过期只影响提示）。
- 不写入泵：App 无法、也不应把该值写进泵；「独立血糖 App 数值能否进泵」不在本轮范围，远期再议（见 §5.2 前言）。
- 二级中可留空；三级中也可留空（此时按「无血糖数据」显示，**不提示错误、不阻断、不影响继续**）。

#### 5.2.4 原有字段的保留

用户原文两段文案（§2.1 / §2.2）**保持原样**；IOB 只作为文案里的检查清单项出现，App 不读取、不计算、不展示 IOB 数值。

### 5.3 真正生效的闸（收敛为两条）

| # | 闸 | 默认 | 性质 |
|---|---|---|---|
| G1 | **次数上限** `scheduledMaxChainCount` | 3 | App 自造（非泵限制） |
| G2 | **每笔两次确认**（提醒框 + 警告框） | 强制 | 交互闸，不可配置关闭 |

- **「血糖/趋势过期即作废」已撤销**：血糖、趋势、读数年龄仅作为**信息呈现**，不构成 G3，不参与能否预约/确认/输注的任何判定；但提醒项本身恒常展示，不因数据缺失而隐藏。
- 血糖数据超过 `scheduledMaxBgAgeMs` 时，只在使用者能注意到的位置标注「读数已 X 分钟」，**不作废、不弹拦截、不改变流程可执行性**。
- 已删除「IOB ≥ 阈值禁止再链」与「按需启用的 U 数累计门槛」的备选方案（R11）。
- 任何闸触发都按 R20 处理：**整链终止**，不只是「拦下一笔」。

### 5.4 独立设计约束：累加值 ≠ IOB ≠ 体内剩余

| 量 | 是什么 | 可用于 | **不可用于** |
|---|---|---|---|
| **本链各笔剂量之和（累加值）** | 用户确认过的**请求量**相加，不含衰减、不含实际输注 | 仅作内部记录/审计 | 不得当作体内剩余胰岛素；不得作为安全提示、放行/拦截判据；不得显示为「累计 X U」 |
| **泵回 IOB** | 泵按其不透明口径给出的活性胰岛素估计，刷新滞后，口径（延展/CIQ 调整）不明 | 仅作为文案清单项的提醒语（用户自行到泵上查看） | 不得在 App 内计算、展示数值或作为门槛 |
| **体内实际剩余胰岛素** | 真实生理量，**无任何可用数据源**（`45` 无 `deliveredVolume`，D7） | 无 | 不得用累加值或 IOB 冒充 |

反面案例（禁止复现）：
1. 连续预约 3 × 5 U，界面显示「本次累计 15 U」——实际体内可能仅剩 3–5 U，用户会误判为「已经很多」而取消仍需要的剂量，或误判为「有 15 U 兜底」而放松警惕。
2. 把 IOB 数字摆在确认框里并保留两位小数——用户会以为它精确、实时、已计入延展与 CIQ 调整，从而替代自己的趋势判断。

正确做法：只按 §5.2 的三级降级显示「当前血糖 + 趋势（若有）+ 读数年龄」，把 IOB 留在文案的检查清单里，让用户看泵或凭趋势自行判断。

### 5.5 独立设计约束：数据缺失不得改变可执行性（提醒仍须完整）

> **血糖/趋势的缺省、过期、不可用，都只影响「显示什么」，不得影响「能不能预约、能不能确认、能不能输注」。**

- **提醒不可省**：三条提醒项（活性胰岛素 / 血糖趋势 / 是否已用其它方式输注）在提醒框与二次确认里必须固定出现，数据缺失时也不得隐藏或删减。
- 三级（无血糖无趋势）**完全可用**，只显示「无法提供血糖与趋势」，但三条提醒文字仍完整展示，判断权交回用户。
- 手动输入血糖保留（可填可不填，属使用者判断的一部分）；留空不报错、不阻断。
- 读数超过 `scheduledMaxBgAgeMs` 只标注「读数已 X 分钟」，**不作废、不弹拦截**。
- 提示语只用中性陈述（「读数已 X 分钟」「无 CGM 数据，趋势不可用」），**不得写成劝退或诊断口吻**（禁止「建议取消」「风险过高」「请勿继续」「趋势平稳」等表达）。
- 禁止把「没有数据」包装成「数据正常」；无数据就明确写「未取得/不可用」。

### 5.6 待确认点

1. `scheduledMaxBgAgeMs` 是否保留（它只控制「读数已 X 分钟」的标注阈值，不参与判定）；默认 10 min 是否合适。
2. 二级中 LastBG 无手动输入时，`bgTimestamp` 是否直接用于年龄标注（语义需核实）。
3. ~~是否需要按需启用的 `scheduledAppDoseCapMilliunits`~~ **已定：不加 U 数累计上限**（R11）。
4. CGM/手输时刻字段的落点（仅内存 / 随链记录持久化）与跨进程重建方式。
5. 三级（无任何血糖数据）为常态之一，验收用例必须覆盖「三级全程可预约、可确认、可输注」。

## §6 「以最新为准」的数据流

- 唯一事实源：`appointment.doseMilliunits`（**单字段**）。
- 倒数页可编辑 → 写回该字段；提醒框可编辑 → 写回同一字段；二次确认文案与最终 `-98` 都从该字段读取。
- 不允许「倒数页一份、提醒框一份、发送参数再一份」；任何副本都视为实现错误。
- 到点发送前做一次快照，发送后不再接受修改（避免发送中途改值）。
- 已经确认后用户又改剂量：视为新的确认，必须重新走二次确认。

## §7 失败路径矩阵（方案）

> 所有终止均按 **R20** 处理：**整链作废**，剩余预约全部取消；已发出的那笔不撤回、不补打。提示须写「本次预约已全部取消，共 N 笔未执行」。

| 场景 | 显示 | 是否保留待办 | 是否补发 | 备注 |
|---|---|---|---|---|
| 到点断连 / 未连上 | 「未连接，本次预约已作废」+ R10 提醒「到点时未连上泵」 | 否 | 否 | 宽限固定 **0**（R14），不再提供可调宽限 |
| 到点用户不点 / 超时后确认 | 「已超过预约时间，本次预约已作废」 | 否 | 否 | R6/R13：60 s 内不确认即作废，**不认晚确认**，要打须重新预约 |
| 二次确认时取消 | 「本次预约已取消」 | 否 | 否 | 取消是默认动作 |
| 泵上开始另一笔输注（泵发起或其它来源） | 「预约已作废：泵上已开始另一笔输注」 | 否 | 否 | R17：立即作废，**不提供「继续」**；风控优先 |
| `-94` 权限失败 | 「未能获取输注权限，未发送」 | 否 | 否（不自动重试） | 与常规发起完全一致（§10） |
| `-97` 明确拒绝 | 显示泵返回错误 | 否 | 否 | 同 A §4.9.2「拒绝≠超时」 |
| 发送成功但 60 s 无开始证据 | 「无法确认是否已开始，请查看泵」 | 保留只读记录 | 否 | 重发=加倍给药 |
| 进程被杀 / 手机重启导致错过 | 「已错过预约 X 分钟，未发送」+ **错过提醒通知**（文案按 §8.1，含未连上变体） | 否（转为历史记录） | 否 | 恢复后**绝不补发**；见 §8.1 |
| 到点确认时上一笔仍在输 | 按 v2 §4.9.9 通用规则：确认页提示「泵上有一笔 X U 正在输注」；被拒后按普通发送失败呈现，不重试、不补发 | 否 | 否 | 不预探上一笔状态；见 v2 §4.9.9 |

「已经晚了多久」不再作为确认依据：窗口内确认视为正常；超过 `scheduledConfirmTimeoutMs` 只显示「已作废，需重新预约」，不显示「已晚 X」。

## §8 计时器存活（手机侧）

泵不排队；第二笔是全新 `bolusId`，必须由 App 在那一刻真发 `-98`。因此**计时器只能活在手机侧**，不存在「交给泵定时」的路径。

| 场景 | 方案 | 状态 |
|---|---|---|
| 进程存活、App 在前台 | 进程内 `elapsedRealtime` 倒数 + 到期回调 | 未实现 |
| 息屏 / 后台 | 前台服务持有计时（与 `CommService` 同进程或独立前台服务），必要时在临近到点时持有短时 wake lock；通知每秒/每 15 s 更新剩余（刷新频率待定，建议 ≤1 次/秒且仅前台可见时） | 未实现 |
| Doze / OEM 冻结 | 不能用纯 `Handler` 兜底；需 `AlarmManager`（`setExactAndAllowWhileIdle`）或前台服务常驻。Android 12+ 精确闹钟需 `SCHEDULE_EXACT_ALARM` 权限，需在文档/设置中说明 | 未实现，待验证 |
| 进程被杀（用户划掉/系统回收） | **依赖 A 轮 §4.9.5 的进程级持久化（当前硬缺口）**：链记录须落盘（`chainId`、`doseMilliunits`、`anchorWallClock`、`deadlineWallClock`、`chainCount`、`state`）；重建后只能显示「已错过/待确认」，**不得补发** | 未实现；与 A §9.2 硬缺口 #2 同一依赖 |
| 手机重启 | 同上；`elapsedRealtime` 会重置，跨重启只能用墙钟重建「是否已错过」，进程内仍用 `elapsedRealtime` 防跳变 | 未实现 |

**明确写死**：不假装绕过 A 轮持久化；A 轮 §4.9.5 不落地，C 轮在进程被杀场景就只能「记录错过 + 不发送」。

### 8.1 错过提醒机制（**未实现**）

两种触发路径，最终都只提醒、不执行：

| 路径 | 触发条件 | 行为 |
|---|---|---|
| A. 闹钟仍能触发 | 进程被杀但未被 force-stop，`AlarmManager` 到点广播仍到达 | 发现无法完成确认流程 → **立即发通知** |
| B. 闹钟也失效 | 强制停止、设备重启、厂商清理等 | 下次打开 App 对账时发现「已过期未执行」→ **补发通知** |

**发通知前先对账泵历史（`280`）**，按结果选文案：

- 确认未发出：「您预约的 20:15 输注 4.00 U 大剂量未能执行，请检查泵的大剂量输注历史记录。」
- 无法确认（可能已发出）：「您预约的 20:15 输注 4.00 U 大剂量状态未知，请检查泵的大剂量输注历史记录。」
- 到点未连上泵（R14）：「您预约的 20:15 输注 4.00 U 大剂量因未连接泵而未执行。」

**通知属性**：

- 普通优先级、可清除、**不常驻**；
- **同一条链只提醒一次**：需持久化「已提醒」标记（与 A 轮持久化同源），进程重建/重复对账都不得重复出通知；
- 点击进入**大剂量历史页**；
- **不复用** 「Confirm Bolus」高优先级渠道（那用于确认/输注中），另建或复用低优先渠道。

**明确不做**：不因错过而补发、不自动重试、不改泵状态。时间与剂量取实际值（预约时刻、实际预约 U 数）。
