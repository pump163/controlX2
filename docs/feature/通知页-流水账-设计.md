> 状态：**草案 / 设计候选**，未写任何代码。等查询器（`查询层收敛-设计.md`）落地后再议。

## 0. 一句话结论

X2 上的通知页只显示"当前活跃报警"，大剂量流水、已消除报警、耗材动作都得去泵的历史记录里翻。等查询器落地后，**在 X2 上把这一页按机型切换到第二视图"流水账"**（Mobi 保持原样），用**内存环形缓存**把能抓到的报文整理成时间线，**明确标出缺口段**，并用泵历史记录做一次轻量对账。

三个硬前提：

1. **不自行发泵查询**——本页的查询一律经查询器（`PumpQueryService`）；查询器策略无法覆盖的极个别场景才单独写独立查询，且必须在本文写明理由。数据只来自已有报文流与事件通道。
   > 用户 2026-11-10 定调：**泵通知由泵本体的查询流管理**，我们只做透传、不替泵承担通知管理的义务，也**不留证据**——断连/缺口的责任因此更轻。
2. **不参与任何既有职责**——角标、滑动消除、耗材流程拦截全部沿用原逻辑；
3. **不是医疗记录**——到达时间、可能不全、进程结束即丢失，页面必须自己说清。

## 1. 形态定案：按机型分派两个页面，不是页内切视图

用户口径（2026-11-09）：**不是页内切换，而是两个页面按机型分派。**

| 机型 | 通知页 | 说明 |
|---|---|---|
| `MOBI` | **原通知页（报警面板）** | 行为完全不变；**不提供**任何流水账开关 |
| `TSLIM_X2` | 按配置显示 **报警面板** 或 **流水账**，另一个隐藏 | 配置页切换，即时生效 |

依据：**一台手机只会连一台泵，两个泵不可能同时使用，App 也不支持同时连接**，所以"两个页面"不会同时需要，不存在冲突。机型判定仍走既有唯一来源 `determinePumpModel`（`com.jwoglom.pumppan` 侧 `PumpCapabilities` 为能力唯一入口，见 `查询层收敛-设计.md` §3.4）。

实现上是 **同一个导航槽位（`LandingSection.NOTIFICATIONS`，`Landing.kt:675`）按机型 + 配置渲染不同 Composable**，而不是新增一个导航项：

- 新增 `PumppanNotificationPageRouter`（`com.pumppan.controlx2.ledger`，纯新增，无上游副本）返回 `ALARM` / `LEDGER`；
- 原 `Notifications.kt` **整份保留**，只在 Landing 的渲染分派处加一行入口（属 §4.4.3 接入点表，需**补一行 B 类登记**后才能动）；
- 流水账页本身是新文件，不进 `com.jwoglom.*`。

> 为什么不用页内 Tab：用户明确"两个页面切换、隐藏旧的"。页内 Tab 会让"报警面板"和"流水账"同时活在一个滚动容器里，角标点击的落点、滑动消除的手势、置顶逻辑都会互相干扰。

**红线（写死）**：

- 本页**不直接发**任何 `Request`；页面打开/刷新/下拉都不自行发泵指令。通知类数据经查询器的 `NOTIFICATIONS` topic 获取（策略见 `pump-query-policy.json`）。查询器无法覆盖的极个别场景才单独发，并写明理由。数据不够就显示"暂无/可能不全"，不许"顺手查一下"。
- 不进 `NotificationBundle`；不参与角标；不参与耗材拦截。
- 不写库、不写盘、不导出。进程结束即丢失。

## 4. 条目模型

```kotlin
enum class LedgerKind { ALARM, ALERT, REMINDER, MALFUNCTION, BOLUS, TEMP_RATE, SUSPEND_RESUME, BASAL, AUTO_INSULIN, SUPPLY, GAP }
enum class TimeSource { PUMP, ARRIVAL }      // 泵上报时间 / 手机到达时间
enum class Origin { REALTIME, STREAM, DB }   // 实时报文 / 历史流 / 本地库回放

data class LedgerEntry(
    val key: String,             // 主键，见下
    val kind: LedgerKind,
    val subtypeId: Int?,         // 协议枚举 id（alertId / bolusId / tempRateId / typeId）
    val groupId: String?,        // 按"笔"聚合用，如 "BOLUS:1234"
    val arrivalAtMillis: Long,   // 本机收到那一刻（必有）
    val pumpTimeSec: Long?,      // 泵时间（仅历史日志有）
    val timeSource: TimeSource,
    val origin: Set<Origin>,
    val seqId: Long?,            // 历史日志序号（有则可对账）
    val pumpSid: Int,
    val title: String,
    val detail: String?,
    val amountUnits: Double?,    // 输注量
)
```

### 4.1 主键与去重

- **有 `seqId` 的条目**：`key = "HL:<pumpSid>:<seqId>"`。同一笔报文经"历史流"和"本地库回补"两次到达时，**后到者合并 `origin`，不产生第二条**。
- **无 `seqId` 的实时条目**：`key = "RT:<pumpSid>:<typeId>:<stateHash>:<arrivalBucket>"`，其中 `arrivalBucket` 为 1 秒粒度，同一状态在同一秒内重复到达只算一条（抑制轮询造成的重复）。
- **同一笔的多条报文**（例如一次大剂量会有"请求/激活/完成/摘要"多条）：**全部入库，用 `groupId` 折叠展示**（见 §6）。
- 报警：**活跃报警不进流水**，由 `NotificationBundle` 实时派生；只有"已消除/已确认"（`AlertClearedHistoryLog`、`AlarmClearedHistoryLog`、`ReminderDismissedHistoryLog` 等）才作为历史条目进流水。这样**报警区与角标永远同源**，不会出现"角标说 1、页面说 2"。
- **"不进缓存"的准确含义 = 不写库**：本文的"缓存"一律指 §10 的**内存环形缓冲**；流水条目**只在内存**，不写 Room、不写 DataStore、不写文件。这是硬规则，不是优化。

### 4.2 时间显示规则（到达时间 ≠ 发生时间）

- 绝大多数实时报文**没有可信时间戳**，只能用 `arrivalAtMillis`。
- 历史日志有 `pumpTimeSec`（泵侧 wall-clock，`HistoryLogItem.kt:28` 注释已写明："local wall-clock seconds since 2008-01-01"）。
- **默认策略（二选一已定为"并用"）**：
  - 有 `pumpTimeSec` → 显示**校正后的泵时间**，来源标 `PUMP`；
  - 无 → 显示**到达时间**，来源标 `ARRIVAL`，并在该条目上打"到达"小标记。
- **校正方式**：以同一窗口内（最近 30 分钟、≥3 个样本）`arrivalAtMillis - pumpTimeInstant` 的**中位数**作为时钟偏移 `offset`；`显示时间 = pumpTimeInstant + offset`。`|offset| > 5 分钟` 时页面顶部显示一条横幅："泵时间与手机时间相差 N 分钟（已校正）"。
- **不允许**把到达时间伪装成发生时间：断连后补回的条目会整体偏晚，必须靠 `timeSource` 标记让人看得出。

## 5. 报警区（置顶，不进流水缓存）

X2 上通知页是**唯一的泵报警入口**（该页在 X2 上只读），所以流水账页的**第一屏必须先是报警**：

- 报警区放在列表**最顶部**，**不随流水滚动消失**（`stickyHeader` 或固定在首项），带红色左边条 + "N 条活跃报警"标题。
- 数据源与报警面板**完全相同**：`DataStore.notificationBundle` → 复用 `NotificationItem` 组件渲染。**必须传 `dismissAllowed = canControlPump(model)`**——X2 恒 false，不得因换页放开（Mobi 保护）。
- 报警为空时，该区显示一行"无活跃报警"，不隐藏（否则用户会以为整页坏了）。
- **刷新归属**：报警区数据由查询器的 `NOTIFICATIONS` topic 驱动（`onlyWhenVisible` 由本页订阅决定），**不依赖 `Notifications.kt` 是否被组合**——否则切到 LEDGER 后报警区会冻结。
- **验收判据（2026-11-09 实测已通过）**：泵发起报警 → 手机报警区出现该条目；在泵上取消 → 手机报警区**同步消失**。手机不产生报警、不保留已取消的报警——**纯镜像**，与 §0 硬前提 1 的「不留证据」一致。
- **角标落地一致性**：角标点击进入流水账页时，页面滚到顶部、报警区高亮 1 秒（一次性动画），确保"角标点进来就能看到报警"。
- **不可折叠、不可淘汰、不可被挤掉**：报警条目不参与 `groupId` 折叠（§6）、不进内存缓存淘汰池（§10）、不因流水条目数量被挤出首屏；报警区固定占据首屏，流水区在其下方独立滚动。这是 v2「不遮挡报警」约束在新页上的延续（§12.1）。

条目类型范围（聚焦输注/报警/耗材；CGM 警报归报警区，CGM 历史不做）：

| 分区 | 内容 |
|---|---|
| 报警区（实时，置顶） | `Alert` / `Alarm` / `Reminder` / `Malfunction` / AAM |
| 流水区（内存，时间倒序） | 大剂量、临时率、暂停/恢复、基础率变更、自动输注（Control-IQ）、耗材动作、**已消除报警** |
| 缺口段（流水内分隔） | 断连窗口（见 §7) |

## 6. 排序与分组

- **分区内排序：时间倒序**（新的在上），时间取 §4.2 的"显示时间"。
- **按笔聚合**：`groupId` 相同的多条（一次大剂量、一次临时率）**折叠成一张卡**，默认显示首末状态与总量，点开展开逐条报文；展开状态不持久化。
- 同一笔内部的排序仍为时间正序（请求 → 激活 → 完成）。
- 缺口段作为**独立分隔条目**插在流水里，占据"两个相邻条目之间的时间差"这个位置，保证时间线连续、不被跳过。

## 7. 缺口段：把"可能不全"落到具体区间

**不允许**只写一句"数据可能不全"。必须生成**具体缺口条目**：

```
09:05:26 – 09:33:10  无数据（断连）27 分 44 秒
```

### 7.1 生成规则

1. **断连窗口**：`DataStore.pumpConnected` 由 `true → false` 记开始，`false → true` 记结束；窗口 ≥ `GAP_MIN_MS`（建议 60 秒）才产出一条 `GAP`。
2. **沉默窗口**：连接态为 `true` 但连续无任何报文超过 `2 × DASHBOARD_BATCH.intervalMs`（即 120 秒）时，产出一条 `GAP`，原因标 `无数据（链路静默）`；恢复后闭合。
3. **序号缺口**：同一 `pumpSid` 的 `seqId` 不连续（例如 1001 → 1015 之间缺 13 条）时，产出一条 `GAP`，原因标 `无数据（历史日志缺 N 条）`。**只标缺口，不补查**。
4. **合并**：窗口重叠或首尾相接（间隔 < 30 秒）的缺口**合并成一条**，避免刷屏。
5. 缺口条目**不进入对账**、不参与任何统计。

### 7.2 呈现

- 流水区里用一条**灰色分隔条**，不是普通卡片；文案固定包含"起止时间 + 时长 + 原因"。
- 原因枚举只有三种：`断连` / `链路静默` / `历史日志缺 N 条`。不确定时写"无数据（原因未知）"，不猜。

## 8. 与泵历史记录的对账（轻量、只读）

**比什么**：本页内存条目的 `seqId` 集合 ←→ 本地历史库 `pumpdata_historylog` 同 `pumpSid`、同一时间窗内的 `seqId` 集合。

**怎么判**：

| 判定 | 条件 | 展示 |
|---|---|---|
| 一致 | 两边 `seqId` 集合相等 | "对账一致（N 条）" |
| **抓到了但泵没有** | 内存有 `seqId`、库里无，且该 `seqId` 落在库的**已覆盖序号区间**内 | "疑似误报 N 条"——多半是解析/映射错误，需人工看 |
| **泵有但我们漏了** | 库里有 `seqId`、内存无 | "遗漏 N 条"——多为断连期或实时流丢失，属预期 |
| 无法对账 | 条目无 `seqId`（实时条目） | 单列计数，不进上面的判定 |

**注意（必须写在页面上）**：这里的"泵有"其实等于"**我们抓过并落库的部分**"。`HistoryLogFetcher` 的回补本身可能不全（断连期不补、弱信号会暂停），所以对账只能证明"内存 vs 库"的差异，**不能证明"泵上真实发生过什么"**。页面文案必须写"对账基准：本地已抓取的历史记录"。

对账**只读、只计数**：不做修复、不回写、不触发补查。

## 9. 配置项

全部走 `PumppanPrefs`，前缀 `pumppan-`，与既有约定一致（`pumppan-bolus-ui` 默认 false 的先例）。

| 键 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `pumppan-notif-page` | `ALARM` / `LEDGER` | **`ALARM`** | **仅 X2 生效**。语义是"X2 上默认显示哪个页面"。Mobi 侧**不显示此项**，避免出现"Mobi 显示流水账"这种无意义状态 |
| `pumppan-ledger-max-entries` | 100–2000 | `500` | 内存缓存条数上限 |
| `pumppan-ledger-time-mode` | `PUMP` / `ARRIVAL` / `BOTH` | `PUMP` | 有泵时间时显示哪个；`BOTH` 同时显示（"发生 09:12 / 收到 09:31"） |
| `pumppan-ledger-show-gaps` | true/false | `true` | 缺口段显示开关（关掉也只是隐藏，仍计数） |

**默认 `ALARM` 的理由**：X2 上这一页是**唯一的报警入口**，且只能看不能消；流水账的时间语义与完整性尚未标定。默认接管等于把"未经验证的视图"放在安全关键位置。用户可在配置页一键切到 `LEDGER`，切换**即时生效**（下次渲染即换页，无需重连/重启）。

**回退**：因为这个开关本身就是"选页面"，`ALARM` 即回退态；另外在流水账页右上角提供**一次点击回报警页**的入口（跳配置或直接切），避免"找不到哪里关"。默认值取 `ALARM` 时，回退是**默认状态**，不需要额外操作。

**不提供的开关**（写死）：

- 不做"显示/隐藏报警区"——报警是硬职责，不允许被关掉；
- 不做"按类型过滤流水"（第一版）——过滤会让人误以为"没发生"，而实际是"被滤掉"；
- 不做"Mobi 显示流水账"——用户口径明确排除。

## 10. 内存缓存与生命周期

| 项 | 规则 |
|---|---|
| 存储 | 单个 `ArrayDeque` + `HashMap<key, LedgerEntry>`，**只在内存** |
| 容量 | 默认 500 条（可配 100–2000） |
| 淘汰 | 超限时**从最旧的非展开/非置顶条目开始淘汰**；`GAP` 条目与普通条目同权（它也是信息） |
| 报警 | **不进缓存**（活跃报警来自 `NotificationBundle`） |
| 生命周期 | **进程结束即丢失**；不写库、不写盘、不导出、不跨进程共享。**理由**：通知是泵本体的职责，我们只透传、不留证据，断连/缺口的责任因此更轻 |
| 线程 | 只在既有报文回调线程内追加；**不新增线程、不新增定时器**（渲染侧由 Compose 驱动） |

页面必须显式标注：**"本页仅内存缓存，重启 App 即清空；数据可能不全。"**

## 12. 风险、冲突与未决

### 12.1 与既有定案的关系（**已裁决 2026-11-09，不构成冲突**）

`大剂量功能设计-v2.md:284-293`（2026-11-09 位置定案 + 补语境）写着：

> **通知页保持「报警」单一职责，不做任何改动，与上游对齐。实时输注状态不放通知页。**

**裁决依据（语境补全后）**：该句的出处是想在这页加一个**大剂量入口**（理由「空着也是空着」），核对该页职责后发现它是**报警播报 + 消除面板**，加常驻入口/卡片会**遮挡报警**，故判定不改。因此它约束的边界是——**不往里加常驻卡/入口、不把报警挤下去**；**不涵盖「按机型切换整页」**。

**本文如何满足这条边界（逐条对上）**：

| v2 的边界 | 本文的做法 |
|---|---|
| 不往原报警面板里塞常驻卡/入口 | 原 `Notifications.kt` 整份保留、一行逻辑不改；流水账是**另一个页面** |
| 不把报警挤下去 | 新页报警区**置顶、不随滚动消失、不参与折叠、不参与缓存淘汰**（§5、§4.1） |
| 不污染角标 | 角标仍只读 `NotificationBundle`；流水条目**不进** bundle、不计角标 |
| 不破坏消除与耗材拦截 | X2 本就 `dismissAllowed=false`；`CartridgeActions` 仍读同一份 bundle，与页面无关 |

**结论**：X2 上允许以配置开关显示流水账页（Mobi 原样）。`大剂量功能设计-v2.md` 该段已回写"已裁决，不构成冲突"。

### 12.2 其他风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| 到达时间被误读为发生时间 | 断连补回后整体错位，用户据此判断"刚打了 2U" | 时间来源标记 + 校正横幅 + `BOTH` 模式 |
| 报警被流水淹没 | 漏看报警 | 报警区置顶且不随滚动消失；角标点击强制回顶 |
| 内存增长 | 长时间挂后台条目堆积 | 500 条上限 + 严格淘汰 |
| 与查询器耦合过紧 | 查询器一改，本页数据源断裂 | 只订阅查询器的**稳定 topic 语义**（`NOTIFICATIONS` / 报文流 / 事件通道），不依赖其内部实现 |
| 用户以为这是医疗记录 | 拿它对账用药 | 页头固定声明"非医疗记录、仅内存、可能不全" |

### 12.3 未决

1. X2 实测中 `BolusDeliveryHistoryLog` 一次大剂量出几条（决定折叠形态）。
2. 断连期泵侧是否缓存事件、重连后是否补发（决定"循序号缺口"是否真的代表丢数据）。
3. `pumpTimeSec` 与手机时钟的实际偏移分布（决定校正是中位数还是固定值）。
4. 页面刷新是否需要"手动重扫本地库"按钮（第一版**不做**，避免引入新查询的错觉）。

## 13. 明确不做

- **不编辑、不删除、不合并用户可见条目**（折叠只是展示，不是删除）；不做"手动消除报警"（X2 本就不支持）。
- **不回写泵**：不发 `DismissNotificationRequest`，不发任何请求类。
- **不当医疗记录**：不导出、不分享、不做报表、不作为用药依据。
- **不落库、不落盘**：不建表、不写文件、不进 `NotificationBundle`。
- **不做 CGM 历史日志**（见 §11.4）；CGM 警报仍在报警区（§11.1）。理由不是机型，是内容形态与范围。
- **不自行发查询**：不用"打开页面"或"下拉刷新"去催数据；一律经查询器（§0 硬前提 1）。
- **不替换能力**：角标、滑动消除、耗材拦截三条职责一行不改。
- **不碰 `wear/`**。
